## 摘要

收藏网页、保存视频和下载资料并不等于真正拥有知识。内容一旦分散在不同平台、不同登录状态和不同文件夹里，回头查找时仍然要重新搜索、重新观看、重新判断。Auto Obsidian MD 想解决的不是“把链接复制进 Obsidian”，而是把资料转化为结构稳定、来源清楚、可以继续检索和编辑的本地 Markdown 笔记。

项目采用本地优先的方式运行。用户可以导入网页、RSS、视频链接、字幕、PDF、图片、音频、视频和本地目录，处理流程负责采集、去重、正文提取、OCR、转写、摘要、标签和目录路由，最终输出到普通文件夹、Obsidian vault、HTML、CSV 或 Notion。桌面应用 Ingest Studio 将这些能力放进统一界面，命令行和 Docker 则保留批量处理与开发调试入口。

这个项目集中开发于 2026 年 6 月 1 日至 7 月 1 日。后续提交主要用于版本说明、超时处理和本机环境收尾，不改变这段集中开发周期的口径。

## 1. 为什么不是一个简单的网页剪藏器

网页剪藏通常只处理一篇文章，而真实资料来源远比网页复杂：视频可能只有字幕或音轨，PDF 可能是扫描件，平台收藏依赖登录状态，本地目录里又可能混有 Markdown、TXT、图片和媒体文件。如果每种来源各写一套独立脚本，最终会出现重复下载、输出格式不一致、失败任务无法恢复和来源信息丢失等问题。

因此项目先建立统一的入库流程：

```text
来源发现 → 采集与去重 → 正文提取或转写 → 清洗与结构化 → 摘要与分类 → Markdown 输出
```

不同平台只负责把内容送入同一条队列，后续处理不再关心它最初来自网页、视频还是本地文件。这样做的价值不是追求支持来源数量，而是让每一种输入最终遵守同一份笔记契约。

## 2. 从采集到 Markdown 的完整链路

### 2.1 多来源采集

在线内容包括普通网页、RSS、抖音收藏、B 站、YouTube、TikTok、播放列表和可下载音频；本地内容包括 PDF、Markdown、TXT、字幕、图片、音频、视频和整个目录。采集层只负责识别来源、保存必要元数据并生成任务，不在这一阶段混入摘要和分类逻辑。

### 2.2 提取、OCR 与转写

文本网页和文本型 PDF 可以直接提取正文；图片与扫描内容需要 OCR；音视频则按配置交给 Whisper 或 FunASR。转写能力是可选依赖：只处理现成文字资料时，不需要为了“功能完整”强制安装体积较大的音视频组件。

### 2.3 摘要、标签与目录路由

基础流程在没有模型时也能生成带来源信息的笔记。启用 OpenAI-compatible 模型服务后，系统再生成摘要、核心知识点、行动项、主题标签和建议目录。模型负责整理表达，但来源地址、文件位置和任务状态仍由程序保存，避免一篇笔记只剩下无法追溯的总结。

### 2.4 多种输出目标

Markdown 是默认输出，因为它可以进入 Obsidian、Logseq、Git 或普通文件夹，也能被后续程序继续读取。除此之外，系统支持 HTML、Excel 兼容 CSV、Notion，以及通过 Obsidian Local REST API 写入 vault。输出方式不同，但核心内容结构保持一致。

## 3. 可靠队列比“跑通一次”更重要

批量处理最常见的问题不是某个解析器完全不可用，而是运行到一半时网络中断、登录态失效、外部程序超时或某条内容格式异常。如果任务只存在内存里，程序关闭后就无法知道哪些已经成功、哪些需要重试。

项目使用 SQLite 保存任务队列和状态，并在来源层做去重。任务可以处于等待、运行、完成、失败或跳过状态；失败项能够单独重试，也可以记录跳过原因。桌面端展示当前进度，命令行则提供结构化状态输出。这样即使一次导入包含多种来源，用户也不需要因为一条失败记录重新处理全部内容。

这个设计让我进一步理解：个人工具同样需要可靠性。只要工具开始接触几十条、几百条资料，幂等、重试、超时和可恢复状态就不再是“企业系统才需要的复杂设计”。

## 4. 从命令行脚本到 Windows 桌面应用

最初的处理能力更适合通过命令行组合，但普通用户不应该为了导入资料而理解 Python 环境、参数文件和外部程序路径。Ingest Studio 使用 Tauri 构建 Windows 桌面端，将导入、运行、队列、账号、依赖和日志集中到一个界面里。

桌面端并不是简单地给命令行套一层按钮。它还需要解决：

- 如何定位随安装包分发的本地处理后端；
- 如何把长任务进度转换成用户能理解的状态；
- 如何区分必需依赖和可选依赖；
- 如何让便携版、安装版和开发环境使用彼此隔离的工作区；
- 如何把错误日志改写成可执行的处理建议。

依赖中心集中检查 Edge、yt-dlp、ffmpeg、平台下载器、转写工具和模型配置。能够自动准备的依赖由程序处理，需要用户登录或填写密钥的部分则明确保留人工步骤，避免“全自动安装”变成不可解释的系统修改。

## 5. 登录状态与本地隐私边界

部分平台内容只有登录后才能访问。项目使用系统 Microsoft Edge 的独立 profile 完成登录，不在项目配置中保存平台密码。任务运行时按需使用当前登录状态，并在任务结束后清理临时 Cookie 文件。

队列、缓存、日志、账号资料和输出默认保存在本机。配置文件、API Key、Cookie、账号目录、缓存和备份都不应该提交到 Git。诊断功能输出的是脱敏后的环境状态，不自动上传完整日志。

本地优先不代表完全离线：如果用户启用了外部模型，提取出的正文或转写文本仍会发送到用户配置的模型服务。项目需要把这条边界明确告诉用户，而不是仅用“本地工具”掩盖外部调用。

## 6. 验证方式与当前边界

项目同时保留 Python 单元测试、桌面端构建检查、Rust 检查和 Windows 发布流程，覆盖采集器、队列、Markdown 写入、账号状态、依赖检测、诊断、备份和版本一致性。GitHub Actions 在版本标签推送后构建 Windows 安装包，使发布过程不依赖某一台开发电脑上的临时环境。

当前项目仍然存在客观边界：平台页面变化、验证码和风控可能影响采集结果；不同转写工具对硬件和环境的要求差异较大；模型摘要的质量依赖用户选择的服务；新机器上的平台账号仍需重新登录。这些问题不能通过增加一个“自动修复”按钮彻底消除，更合理的方式是提供健康检查、清晰状态和可恢复流程。

## 7. 项目收获

Auto Obsidian MD 让我把“写一个能处理内容的脚本”和“做一个可以长期使用的本地工具”区分开来。真正耗时的部分往往不是调用一次解析器或模型，而是来源适配、任务状态、重复处理、依赖管理、隐私边界、桌面交互和发布验证。

最终沉淀下来的核心思路是：先保证资料能够可靠进入本地，再谈模型如何帮助整理；先保存来源与状态，再生成摘要；先让失败可见、可重试，再追求支持更多平台。知识库的价值不在于收藏数量，而在于内容能否被重新找到、核对和继续使用。
