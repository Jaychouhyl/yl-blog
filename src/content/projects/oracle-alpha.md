OracleAlpha 是我把量化学习、全栈工程和风险控制放到一起练的一套系统。它不是“策略展示页”，也不是收益宣传页，而是一个自用研究工作台：从行情数据、因子研究、回测验证，到信号、风控、纸面/实盘执行边界，都尽量用工程化方式串起来。

## 背景与目标

最初只是一些量化脚本和图表。真正开始变成项目，是因为我发现脚本很难回答几个问题：一个因子怎么验证，回测和真实执行是不是同一套逻辑，风险规则怎么被测试守住，系统出了问题怎么追踪。

所以 OracleAlpha 的目标不是证明某个策略可以赚钱，而是把“想法 -> 验证 -> 风控 -> 执行 -> 复盘”做成一条可复现的链路。它的价值在工程纪律：可测、可审计、可回滚，也能诚实展示不理想的回测结果。

## 技术栈与架构

整体是 Vue 3 前端、FastAPI 后端、Python 量化引擎和 SQLite 本地持久化。前端负责看板、信号、回测、因子、风控、交易、研究和告警等栏目；后端用模块化路由把引擎能力包装成 API；量化引擎负责因子计算、打分、回测、缓存和风控。

我选择模块化单体而不是微服务，是因为这是单人自用系统。一个进程、一个端口、一个本地数据库，更适合快速迭代和排查；内部通过 router、service、model 和引擎适配层划清边界，未来真要拆也有路径。

## 我负责的部分

- 前后端主流程：看板、信号、回测、风控、交易、研究、告警、系统设置等页面与 API。
- 量化引擎工程化：因子、打分、回测、数据缓存、Walk-forward 验证和趋势扫描观察工具。
- 安全边界：默认 paper、自动交易默认关闭、实盘订单必须经过硬护栏与人工审批。
- 工程质量：pytest / Vitest 本地测试、结构化日志、Alembic 迁移、健康检查和指标接口。
- 文档与复盘：把项目定位、安全设计、技术架构和心得拆成可公开阅读的文章。

## 难点与取舍

最难的不是加功能，而是给系统设边界。量化项目很容易变成“今天又加一个指标”，但真正有价值的是知道哪些指标不能进默认策略。比如一些短线形态和玄学观察项，在快速验证里看起来不错，但带手续费和样本外验证后并不稳定，于是只保留为观察工具，不驱动真钱。

交易模块也做了保守设计：系统可以读账户、看持仓、生成订单意图，但实盘下单必须经过护栏和人工确认；系统不实现入金、出金、转账或银行账户绑定。这个边界牺牲了一些“全自动”的炫技感，但更符合学习项目应该有的风险意识。

## 结果与收获

这个项目让我从“会写功能”往“会做系统”推进了一步。以前我更关注页面或算法本身，现在会同时考虑数据从哪里来、接口怎么定、错误怎么降级、状态怎么持久化、日志能不能解释问题，以及某个能力会不会被滥用。

它也让我对量化研究更诚实：回测不理想就如实显示，样本外跑不过就不上默认策略。一个能承认“不通过”的系统，比一个永远报喜的系统更可信。

## 后续优化

- 继续加强样本外验证和成本敏感性分析，减少“看起来有效”的伪改善。
- 把研究报告、自然语言选股和每日晨报保持在只读边界内，避免 AI 影响执行链路。
- 增强数据质量闸和告警系统，让陈旧数据、缺口数据、异常行情更早暴露。
- 如果未来要多用户或长期运行，再考虑把 SQLite 切换到更适合并发的关系型数据库。

## 说明边界

- 仅供学习研究，不构成投资建议。
- 不声称策略已经稳定跑赢市场。
- 配置 live key 不等于允许自动实盘交易；真钱动作必须有人在环上。
- 玄学、新闻、AI 和趋势观察项都不直接驱动真实下单。
