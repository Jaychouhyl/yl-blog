知识图谱已经能够查询节点、关系和路径，为什么还需要 RAG？反过来，向量检索可以找到语义相关的文档片段，为什么还要维护 Neo4j？这两个问题指向同一个事实：文本相似度和结构关系解决的不是同一种信息需求。

NeoKG 的问答界面和部分联调属于我直接参与的前端范围；向量化、图查询、上下文组织和模型调用属于团队后端或我后期阅读理解的内容。本文重点整理 Graph RAG 的基础链路和设计取舍，不把完整问答后端写成个人独立实现。

## 先理解普通 RAG

RAG，即 Retrieval-Augmented Generation，通常包含四个阶段：

```text
文档切分与向量化
  → 根据问题检索相关片段
  → 把片段放进模型上下文
  → 生成带有检索依据的回答
```

Embedding 会把文本转换成高维向量。语义相近的文本在向量空间中通常距离更近，因此系统可以用相似度找到可能相关的片段。pgvector 让 PostgreSQL 能够保存和检索这些向量。

向量不是文字的压缩备份，也不能直接解释每个维度。它适合做候选召回，最终仍需要保留原始片段、文档 ID 和位置，才能展示引用并核对答案。

## 文档为什么需要切分

整份长文档直接计算一个向量，会把多个主题混在一起；切得太碎，又会丢失段落之间的上下文。切分策略通常需要考虑标题层级、段落边界、长度和重叠窗口。

基础取舍包括：

- 块太大：召回结果包含大量无关内容，占用模型上下文。
- 块太小：指代和前后条件丢失，片段本身无法理解。
- 重叠太少：跨边界信息被切断。
- 重叠太多：相似片段重复进入结果。

知识图谱可以为切分提供额外线索，例如把片段关联到识别出的实体和原始章节，但它不能消除切分质量问题。

## 向量相似不等于关系明确

用户询问“系统 A 通过哪些组件依赖系统 B”时，相关片段可能分散在多份文档中。向量检索能找到包含 A、B 和组件描述的文字，却不一定能稳定恢复完整多跳关系。

图查询更擅长回答：

- 某实体直接连接哪些节点；
- 两个实体之间有哪些路径；
- 某类关系经过了几跳；
- 哪些节点属于同一社区；
- 当前结论由哪些明确关系组成。

但图谱也可能遗漏文本细节。如果抽取阶段没有建立某条关系，单独查询图数据库就无法召回原文中的相关描述。因此 Graph RAG 更合理的方向是把文本证据和结构证据组合，而不是让其中一方替代另一方。

## Graph RAG 的一条基础链路

结合项目接口和后期复盘，可以把问答流程理解为：

```text
用户问题
  → 识别问题中的实体和意图
  → 向量检索相关文本片段
  → 在 Neo4j 查询实体邻域或路径
  → 合并、去重并限制上下文
  → 模型生成回答
  → 返回引用、实体和关系
```

实体识别是关键连接点。问题中的名称可能是别名或简称，必须映射到图谱中的稳定节点；映射错误会让图查询从错误实体出发。没有明确实体的问题则更适合先使用文本检索，不必强行调用图数据库。

## 上下文组织比检索数量更重要

向量检索和图查询都可能返回很多候选。如果把全部内容直接塞进提示词，不仅增加成本，还会让模型面对重复或冲突证据。

上下文组织需要考虑：

1. 文本片段与问题的相关度。
2. 图中关系与目标实体的距离。
3. 来源是否可信且可以访问。
4. 多个片段是否来自同一原文。
5. 关系方向和实体类型是否一致。
6. 总内容是否超过模型上下文预算。

排序结果不等于可信度。一个片段语义非常相似，也可能来自过期材料；一条图关系结构明确，也可能缺少来源。系统应保留证据类型和出处，而不是只给模型一段已经混合的文字。

## 回答必须能够回到证据

RAG 的目标不是让回答听起来更专业，而是让结论更容易核对。前端至少应该展示：

- 使用了哪些文档片段；
- 涉及哪些实体和关系；
- 引用能否回到原始文档；
- 没有足够证据时是否明确说明；
- 图谱和文本证据发生冲突时采用了什么处理方式。

我在问答页面和接口联调中更关注加载、结果和异常状态。流式输出可以降低等待感，但不能替代证据展示。首个 token 很快出现，也不代表答案准确；相反，检索、图查询和重排需要时间时，界面应该明确当前阶段。

## 幻觉不能只靠提示词解决

模型可能生成检索材料中不存在的细节，也可能把两条真实关系组合成错误结论。降低风险需要多层约束：

- 只把可追溯材料作为回答依据；
- 结构化传递实体、关系和来源；
- 要求无法确认时明确保留不确定性；
- 对关键事实进行规则或数据库校验；
- 建立固定问题集比较回答、引用和图路径；
- 不让自然语言回答直接触发高风险写操作。

Graph RAG 不是“有图谱就不会幻觉”。错误图数据同样会给模型提供错误依据，因此图谱构建质量和引用机制仍然是基础。

## 哪些问题不需要 Graph RAG

如果用户只是查找一段明确文字，普通全文搜索或向量检索可能已经足够。如果数据规模很小、关系简单，维护图数据库和实体映射会增加不必要复杂度。

Graph RAG 更适合：

- 问题需要跨文档、多跳关系；
- 实体和关系具有稳定业务含义；
- 用户需要沿节点继续探索；
- 回答需要同时展示文本与结构证据；
- 图谱能够持续维护和校验。

技术选择应该来自问题，而不是为了使用一个热门名词。系统如果无法保证实体质量和来源可追溯，先改善普通检索往往比直接增加 Graph RAG 更有效。

## 后期复盘得到的认识

向量检索解决“哪些文字可能相关”，图查询解决“对象之间怎样连接”，语言模型负责把证据组织成用户容易理解的表达。三者职责不同，组合时也需要清楚的输入输出契约。

NeoKG 让我第一次把图谱交互与问答入口放在同一套页面中理解。对前端来说，回答不应该停留在一段文字，而应该能返回文档、节点和关系；对后端来说，检索成功也不是终点，最终仍要验证证据是否真实到达用户页面。
