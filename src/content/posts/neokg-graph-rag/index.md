知识图谱已经能够查询节点、关系和路径，为什么还需要 RAG？反过来，向量检索可以找到语义相关的文档片段，为什么还要维护 Neo4j？这两个问题指向同一个事实：文本相似度和结构关系解决的不是同一种信息需求。

接着上一篇的路径与社区分析，这篇从团队项目的问答代码出发，整理我对检索、图证据和流式交互的理解。文中会区分普通 RAG 的原理、固定版本中的实际路径，以及还需要补齐的设计，不把后期学习写成个人独立完成的后端成果。

## 先理解普通 RAG

RAG，即 Retrieval-Augmented Generation，通常包含四个阶段：

```text
文档切分与向量化
  → 根据问题检索相关片段
  → 把片段放进模型上下文
  → 生成带有检索依据的回答
```

Embedding 会把文本转换成高维向量。语义相近的文本在向量空间中通常距离更近，因此系统可以用相似度找到可能相关的片段。pgvector 让 PostgreSQL 能够保存和检索这些向量。

向量不是文字的压缩备份，也不能直接解释每个维度。它适合做候选召回，最终仍需要保留原始片段、文档 ID 和位置，才能展示引用并核对答案。

## 文档为什么需要切分

整份长文档直接计算一个向量，会把多个主题混在一起；切得太碎，又会丢失段落之间的上下文。切分策略通常需要考虑标题层级、段落边界、长度和重叠窗口。

基础取舍包括：

- 块太大：召回结果包含大量无关内容，占用模型上下文。
- 块太小：指代和前后条件丢失，片段本身无法理解。
- 重叠太少：跨边界信息被切断。
- 重叠太多：相似片段重复进入结果。

知识图谱可以为切分提供额外线索，例如把片段关联到识别出的实体和原始章节，但它不能消除切分质量问题。

以上是切分设计的通用知识。当前导入代码对模型整理出的每个 `Document.content` 生成一个向量；问答再从文档表中取一条记录。这里没有看到显式的固定窗口 chunk、重叠分段或片段重排流程，因此不能把前面的原理图直接当作 NeoKG 已实现的切分方案。

## 向量相似不等于关系明确

用户询问“系统 A 通过哪些组件依赖系统 B”时，相关片段可能分散在多份文档中。向量检索能找到包含 A、B 和组件描述的文字，却不一定能稳定恢复完整多跳关系。

图查询更擅长回答：

- 某实体直接连接哪些节点；
- 两个实体之间有哪些路径；
- 某类关系经过了几跳；
- 哪些节点属于同一社区；
- 当前结论由哪些明确关系组成。

但图谱也可能遗漏文本细节。如果抽取阶段没有建立某条关系，单独查询图数据库就无法召回原文中的相关描述。因此 Graph RAG 更合理的方向是把文本证据和结构证据组合，而不是让其中一方替代另一方。

## Graph RAG 的一条基础链路

沿 `/api/chat/ask` 阅读，当前代码的实际路径比一般的 Graph RAG 架构图更具体：

```text
用户问题
  → 为问题计算向量
  → 按向量距离从文档表取 Top-1
  → 用文档 ID 查询相邻关键词
  → 把文档正文、证据图和历史消息组成提示词
  → 调用模型并以 SSE 返回回答文本
```

图查询匹配的是 `DocumentNode → HAS_KEYWORD → KeywordNode` 的一跳关系，不是先识别问题里的任意实体，再自动寻找多跳路径。这里连接文本与图谱的关键是**文档 ID**：关系表召回的文档必须能够对应图中的 `docId`。如果同步状态不同，即使文本召回成功，图证据也可能缺失。

更完整的方案可以增加实体识别、多文档召回、证据去重与引用返回；但它们是继续学习和设计的方向，不是这段调用链已经证明的能力。Graph RAG 这个名称描述一种结合思路，不会自动附送所有检索功能。

## 把向量距离算一次，就不容易把分数看反

当前 `DocumentMapper` 使用 `vec <-> 查询向量` 升序排序，并取 `LIMIT 1`。在 pgvector 中，`<->` 表示 **L2 距离**，越小越近；它不是余弦相似度，也不是“正确率”。运算符定义可核对 [pgvector 的查询说明](https://github.com/pgvector/pgvector#querying)。

下面用二维坐标算一遍排序，坐标是教学数据，不来自真实 Embedding，也不代表实际文档含义：

```python
from math import dist

query = (0.0, 0.0)
documents = {
    "A": (1.0, 0.0),
    "B": (0.0, 2.0),
    "C": (3.0, 4.0),
}
ranked = sorted(
    ((name, dist(query, vector)) for name, vector in documents.items()),
    key=lambda item: item[1],
)
assert ranked == [("A", 1.0), ("B", 2.0), ("C", 5.0)]
print(ranked)
```

这个例子只能证明 A 在给定坐标中最近，不能证明 A 能回答某个问题。当前 SQL 没有距离阈值：只要存在可排序的候选，取第一名并不等于通过了相关性审核。就像一场只有三位选手的比赛，总会有第一名，但名次本身不说明达到了什么标准。

因此这里可以继续学到三个基础区别：**召回**找候选，**重排**比较候选与问题的匹配，**证据核验**判断能否支持具体结论。当前路径确认了 Top-1 召回，不应顺手声称已经具备后两层的完整实现。

## 上下文组织比检索数量更重要

扩展到多文档、更多图关系后，候选数量会变多。如果把全部内容直接塞进提示词，不仅增加成本，还会让模型面对重复或冲突证据。当前虽然只召回一篇文档，但拼接的是整段 `content`，一篇长文同样可能占用大量上下文。

上下文组织需要考虑：

1. 文本片段与问题的相关度。
2. 图中关系与目标实体的距离。
3. 来源是否可信且可以访问。
4. 多个片段是否来自同一原文。
5. 关系方向和实体类型是否一致。
6. 总内容是否超过模型上下文预算。

排序结果不等于可信度。一个片段语义非常相似，也可能来自过期材料；一条图关系结构明确，也可能缺少来源。系统应保留证据类型和出处，而不是只给模型一段已经混合的文字。

源码在构造请求时截取历史记录列表的最近 5 项，但“记录项数”“完整对话轮数”和“token 预算”仍然不是一回事。历史怎么保存、每项多长、当前文档多长，需要一起考虑。给列表加一个长度上限，不会自动限制整份提示词的大小。

## 回答必须能够回到证据

RAG 的目标不是让回答听起来更专业，而是让结论更容易核对。若要形成可核对的问答产品，前端应该能够展示：

- 使用了哪些文档片段；
- 涉及哪些实体和关系；
- 引用能否回到原始文档；
- 没有足够证据时是否明确说明；
- 图谱和文本证据发生冲突时采用了什么处理方式。

这些是验收目标，而非当前页面的已完成清单。所读后端把证据图放入提示词，发送给前端的 SSE 数据则是回答文本；`AiChat.vue` 主要把片段追加到聊天消息，没有配套的结构化引用列表。因此“模型见到了证据”和“用户能点击引用核对证据”之间，还隔着一个返回契约与展示环节。

举一个虚构场景：两篇文档都包含“图数据库”关键词，一篇讲存储，另一篇讲可视化。共享关键词支持“主题有联系”，不支持“后一篇方案依赖前一篇方案”。模型即使把这段话解释得很流畅，也没有因此多出一条依赖关系。

以后若完善引用，至少要让引用 ID 对应实际文档或片段，并验证回答里的引用确实存在、内容确实支持该句结论。引用不是在句尾加一个 `[1]` 就成立，也不能靠模型临时编一个链接补齐。

## 流式片段不是一轮完整回答

当前页面使用 `EventSource` 接收消息：尝试解析 JSON，取文本字段；不能解析时按普通文本追加。这解释了页面如何连续显示回答，但不意味着它收到了节点、关系与引用的独立事件。

进一步看后端，更新 Redis 历史记录的代码位于流的 `map` 回调内，每收到一项模型流结果就添加一条问答记录。如果返回项是文本增量，一次回答可能被保存为多条记录；后续截取最近 5 项，也就不能直接解释为保留了最近 5 轮完整对话。这是按源码位置得到的边界分析，未调用模型复现。

从中我学到：**当前显示的文本、一次回答的完成状态、下一轮使用的历史，是三种状态。** 更清楚的设计是前端逐步展示、后端按一次回答聚合历史，并区分正常结束与中途失败。它是改进思路，本篇没有替原系统实现这些行为。

| 能观察到的结果 | 可以确认什么 | 还不能确认什么 |
|---|---|---|
| 收到第一个文本片段 | 流开始产出文本 | 回答完整、证据正确 |
| 连接关闭 | 当前连接结束 | 正常完成还是中途异常 |
| 提示词包含证据图 | 模型输入包含图数据 | 用户已收到可点击引用 |
| 文档召回成功 | 找到一个候选 | 候选足以支持答案 |

流式输出可以降低等待感，但不是质量证明。专业的问答交互既要关心“字有没有出来”，也要关心“这句话凭什么成立”。

## 幻觉不能只靠提示词解决

模型可能生成检索材料中不存在的细节，也可能把两条真实关系组合成错误结论。降低风险需要多层约束：

- 只把可追溯材料作为回答依据；
- 结构化传递实体、关系和来源；
- 要求无法确认时明确保留不确定性；
- 对关键事实进行规则或数据库校验；
- 建立固定问题集比较回答、引用和图路径；
- 不让自然语言回答直接触发高风险写操作。

Graph RAG 不是“有图谱就不会幻觉”。错误图数据同样会给模型提供错误依据，因此图谱构建质量和引用机制仍然是基础。

## 哪些问题不需要 Graph RAG

如果用户只是查找一段明确文字，普通全文搜索或向量检索可能已经足够。如果数据规模很小、关系简单，维护图数据库和实体映射会增加不必要复杂度。

Graph RAG 更适合：

- 问题需要跨文档、多跳关系；
- 实体和关系具有稳定业务含义；
- 用户需要沿节点继续探索；
- 回答需要同时展示文本与结构证据；
- 图谱能够持续维护和校验。

技术选择应该来自问题，而不是为了使用一个热门名词。系统如果无法保证实体质量和来源可追溯，先改善普通检索往往比直接增加 Graph RAG 更有效。

## 后期复盘得到的认识

向量检索解决“哪些文字可能相关”，图查询解决“对象之间怎样连接”，语言模型负责把证据组织成用户容易理解的表达。三者职责不同，组合时也需要清楚的输入输出契约。

回看这四篇，知识图谱的学习主线其实很连贯：第一篇保证实体与关系对得上，第二篇保证接口与画布对得上，第三篇保证算法名称与查询语义对得上，第四篇保证回答与证据对得上。对前端来说，回答不应该停留在一段文字；对后端来说，检索成功也不是终点，最终仍要验证证据是否真实到达用户页面。
