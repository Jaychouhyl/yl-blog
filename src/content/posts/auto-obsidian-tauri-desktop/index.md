前两篇分别整理了资料入库和任务可靠性；到这里，问题变成了：怎样让用户不打开终端，也能知道任务正在做什么、失败在哪里？Python 很适合快速连接网页解析、OCR、音视频处理和 Markdown 写入能力，但长期使用时，用户不应该每次都查找参数、观察终端日志，再手动确认输出目录。

Auto Obsidian MD 使用 Tauri 构建 Ingest Studio，把导入、任务队列、账号、依赖、日志和设置放进 Windows 桌面应用。这个过程让我意识到，桌面化不是“给脚本加一个界面”，而是给已有能力建立稳定的产品边界。

## 先理解 Tauri 的基本结构

Tauri 通常由两部分组成：

- 前端使用 HTML、CSS 和 JavaScript 生态构建界面，本项目使用 TypeScript。
- 原生外壳由 Rust 提供窗口、文件系统、进程和打包能力，并调用系统 WebView 渲染前端。

与把完整浏览器运行时一起打包的方案相比，Tauri 更依赖操作系统已有的 WebView，因此安装包通常更轻。但“体积更小”并不代表工程更简单。前端不能随意获得所有系统权限，文件访问、进程启动和命令调用需要明确配置边界。

项目原有的内容处理能力主要位于 Python。桌面端需要在 TypeScript 界面、Rust 外壳和 Python 处理程序之间建立通信：界面提交命令，原生层启动本地处理进程，界面通过状态查询和进度轮询展示结果。这里不需要先把 Python 改写为 Rust；复用已有能力，再明确两边的调用契约，比为了技术栈整齐而重写一遍更有价值。

## 进程通信为什么比函数调用复杂

同一进程内调用函数，返回值通常只有成功或异常；桌面端调用长期运行的本地任务，还要面对进程没有启动、运行中退出、输出格式损坏和用户主动取消等情况。

在项目中，可以把这条调用链分成三个方向看：

```text
发起工作：TypeScript → Tauri 命令 → Rust 启动 Python
查询进度：Python 写进度文件 ← Rust 读取 ← TypeScript 定时查询
核对结果：Python 更新 SQLite → 队列查询 → 界面展示任务与输出路径
```

Rust 桥接层返回 `ok`、`code`、`stdout` 和 `stderr`。对于状态、队列等提供 `--json` 的查询，原生命令会解析标准输出中的 JSON，再交给界面使用；长时间执行的队列任务则还有独立的进度查询。

**当前实现不是 Python 通过事件总线持续推送进度。** Python 将操作进度写到 `cache/operation-progress.json`，Rust 提供读取命令，前端约每 500 毫秒轮询一次。日志保留给排查，进度文件回答“这次操作走到哪里”，SQLite 回答“每个任务最终是什么状态”。三者各有用途，不能用一句“处理完成”的日志替代全部判断。

这也是接口契约的基础概念：调用双方约定字段和行为，而不是依赖某一句可随时修改的提示文案。下载器可以换，界面最好仍然只需要理解稳定的命令结果、进度和队列数据。

## 一个进度对象，为什么还不能代表全部结果

下面按项目的进度字段构造一份教学示例；数字和时间仅用于说明，不是真实运行截图或性能记录：

```json
{
  "operation": "queue",
  "stage": "process",
  "current": 2,
  "total": 5,
  "percent": 40,
  "status": "running",
  "message": "已处理 2/5 条",
  "updated_at": "2026-06-28T10:00:00Z"
}
```

它表示当前操作正在处理队列，已推进到一批五条任务中的第二条，但还有几个问题不能直接从 `40` 得出答案：

1. **40% 不等于已经花掉总耗时的 40%。** 两篇短网页和一段长视频的处理成本不同，数量比例不能直接当作剩余时间。
2. **已处理数量不等于成功数量。** 队列回调会在单条任务返回结果后推进计数，其中可能包含失败项，最终还要看任务状态与输出。
3. **最近一次进度不等于进程仍然健康。** 程序退出后文件可能仍在；`updated_at` 可以帮助辨认新旧，但不是工作进程的存活证明。

前端有按操作开始时间过滤旧进度的逻辑，这是为了减少上一轮结果干扰当前显示。不过，当前进度结构并没有独立的任务 ID 或运行 ID，不能由此推导出已经支持多批任务并行隔离。先讲清现有边界，比画出一个永远准确的进度条更实在。

## 把失败分清楚，提示才有用

“点击按钮后没成功”可能对应完全不同的故障：

| 层次 | 例子 | 需要继续核对的方向 |
|---|---|---|
| 进程启动 | 处理程序没有找到 | 安装资源和程序路径 |
| 返回结果 | 查询预期得到 JSON，却收到无法解析的文本 | 命令协议和标准输出内容 |
| 业务任务 | 程序启动成功，但某条资料提取失败 | 队列记录、来源和依赖条件 |

因此 `ok`、退出码和业务状态要一起理解。队列命令在处理完一批任务后，可能因为其中存在失败项返回非零退出码；这不意味着前面成功生成的笔记也都失败了。界面不应把局部失败简单翻译成“整批什么都没做”。

反过来，进程返回成功也不能保证笔记内容足够完整，第一篇介绍的降级笔记就是一个例子。把这几层分开之后，用户才知道是该检查安装、补齐依赖，还是只重试某一条资料。否则一个“未知错误”，就把排查工作整包退还给了用户。

## 依赖中心解决环境差异

内容处理会接触多种外部能力，例如浏览器、yt-dlp、ffmpeg、OCR、平台下载器和语音转写工具。开发电脑上已经安装并加入 PATH 的程序，换一台机器后可能完全不存在。

桌面应用需要区分三类依赖：

1. **随程序提供的必需组件**：缺少时应用无法完成核心流程。
2. **能够自动准备的工具**：可以下载或引导安装，但要明确版本和来源。
3. **按功能启用的可选依赖**：例如音频转写，不使用对应能力时不应强制安装。

依赖检测不能只判断文件是否存在，还要考虑程序能否启动、版本是否兼容、路径是否可访问。自动安装也不应该无限扩大权限范围。需要用户登录、填写密钥或确认系统修改的步骤，应保留清楚的人工操作。

这里的基础知识是环境可复现性：程序能在开发电脑运行，不代表交付物在新机器可运行。依赖清单、版本约束、健康检查和构建流程共同组成可复现环境。

## 登录状态不等于保存账号密码

部分平台收藏或受限内容需要登录。最危险的简化方案是要求用户把账号密码或长期 Cookie 直接写进配置文件。这样虽然容易调用，却增加了泄露和误提交风险。

项目使用系统 Microsoft Edge 的独立 profile 完成需要人工参与的登录。程序利用已经建立的浏览器状态访问内容，而不是自行保管平台密码；任务结束后清理临时 Cookie 文件，账号目录、配置、密钥和缓存也不进入 Git。

这里需要区分几种敏感信息：

- 密码和 API Key 属于长期凭据；
- Cookie、token 和浏览器 profile 可以代表登录身份；
- 日志可能间接包含本地路径、请求地址和内容标题；
- 输出笔记本身可能包含私人资料。

隐私设计不能只检查有没有密码。任何能够恢复身份、定位文件或暴露内容的信息，都应该有明确的保存位置和生命周期。

## “本地优先”不等于“完全离线”

队列、缓存、账号资料和 Markdown 默认保存在本机，这是本地优先。但如果用户启用了外部模型进行摘要，正文或转写文本仍然会发送到配置的模型服务。

因此界面需要告诉用户当前步骤是否会访问网络、发送什么内容、由哪个服务处理。更稳妥的默认行为是：不开启模型也能完成基础入库，模型只增强摘要、标签和目录建议。

这属于威胁建模的基础思路：先识别资产，再识别数据会经过哪些边界。对这个项目而言，资产包括登录状态、原始资料、生成笔记和模型密钥；边界包括浏览器、本地进程、文件系统和外部模型接口。

## Windows 发布不是编译成功就结束

开发模式可以依赖仓库目录和本机环境，安装版却必须找到正确的资源、工作区和处理程序。便携版、安装版和开发环境如果共用同一个数据目录，还可能互相覆盖配置或污染测试结果。

发布验证至少应该覆盖：

- 新环境能否启动应用；
- 本地处理端能否被正确定位；
- 必需资源是否进入安装包；
- 带中文和空格的路径能否正常使用；
- 更新或卸载是否保留用户笔记；
- 版本号是否在前端、原生配置和发布产物中一致；
- 安装包是否来自可重复执行的构建流程。

GitHub Actions 可以在版本标签触发后构建 Windows 产物，减少“只有开发电脑能打包”的情况。但自动构建通过仍然只是部分证据，最终还需要在接近真实用户的新环境中完成启动和基础流程验收。

## 从桌面化学到的事情

脚本关注的是处理逻辑，桌面产品还要关注权限、状态、依赖、升级、数据位置和错误恢复。Tauri 提供了前端界面与原生能力之间的桥梁，但不会自动替开发者决定安全边界和进程契约。

这次桌面化最重要的收获，是把“能运行”拆成更具体的问题：用户能否知道当前发生了什么，失败后能否继续，换一台机器能否启动，敏感信息保存在哪里，输出内容是否仍由用户控制。只有这些问题都有明确答案，本地工具才真正具备长期使用的基础。

回头看这三篇，学习线索其实是连续的：第一篇把来源和内容分开，第二篇把任务记录和执行结果分开，第三篇再把命令、进度和界面提示分开。分层不是为了让目录树显得专业，而是为了某一环出错时，能够准确知道应该去哪里查。
