知识图谱中的路径搜索和社区发现很容易被写成技术栈列表：支持 BFS、最短路径和社区算法。但用户并不关心系统调用了哪个函数，他关心的是两个实体为什么有关、关系经过了哪些中间节点，以及复杂网络中是否存在值得关注的群组。

上一篇讲了图谱前端的数据与状态，这一篇继续追问：页面高亮的那条路径究竟是怎样选出来的？文章基于团队项目的固定源码版本，把实际查询、我补做的算法学习，以及产品表达分别说明。

这里还需要把“功能名称”和“代码实现”分开。项目界面与接口沿用了“BFS 路径搜索”的叫法，仓库中的实际查询使用 Cypher 匹配可变长度路径，再按 `length(p)` 排序并取第一条。因此下面的 BFS 内容是我围绕无权图最短路径补做的原理学习，不是声称项目后端手写了 BFS 队列，也不能由界面名称推断数据库采用了什么执行计划。

## 图、顶点与边的基础概念

图由顶点和边组成。在知识图谱中，顶点通常对应实体，边对应实体之间的关系。

- **有向图**中的边有明确方向，例如“系统使用技术”。
- **无向图**只表示双方存在连接，例如“人物互为同学”。
- **带权图**会给边附加成本、距离或强度。
- **度**表示一个节点连接了多少条边；有向图还可以区分入度和出度。
- **邻居**是通过一条边可以直接到达的节点。

这些定义会影响查询结果。把有向关系错误地当成无向关系，可能得到语义不成立的路径；把所有关系权重视为相同，也可能让“最短”只代表经过边最少，而不代表业务上最相关。

## BFS 为什么适合无权图最短路径

BFS，即广度优先搜索，会从起点开始逐层访问邻居：先检查距离一条边的节点，再检查距离两条边的节点。对于每条边成本相同的图，第一次到达终点时得到的就是边数最少的路径。

```text
第 0 层：起点
第 1 层：起点的直接邻居
第 2 层：尚未访问的二级邻居
……直到找到终点
```

BFS 通常使用队列保存待访问节点，并记录已访问集合，避免在环形关系中无限重复。还需要保存每个节点的前驱，找到终点后才能反向还原完整路径。

DFS，即深度优先搜索，会沿一条分支尽可能向下探索。它适合遍历、连通性和回溯类问题，但在无权图中不能保证第一次找到的是最短路径。算法选择应该来自问题性质，而不是个人偏好。

## 用一个带环的小图，把 BFS 跑明白

只记住“广度优先”四个字很容易，真正写起来还要回答：什么时候标记访问过，如何保存路径，找不到时返回什么？下面是独立 Python 教学代码，图数据是手工构造的，不调用 Neo4j：

```python
from collections import deque

def shortest_path(graph, start, end):
    if start not in graph or end not in graph:
        return None
    queue = deque([start])
    parent = {start: None}

    while queue:
        node = queue.popleft()
        if node == end:
            path = []
            while node is not None:
                path.append(node)
                node = parent[node]
            return path[::-1]
        for neighbor in graph[node]:
            if neighbor not in parent:
                parent[neighbor] = node
                queue.append(neighbor)
    return None

graph = {
    "A": ["B", "C"],
    "B": ["A", "D"],
    "C": ["A", "D"],
    "D": ["B", "C"],
    "E": [],
}
assert shortest_path(graph, "A", "D") == ["A", "B", "D"]
assert shortest_path(graph, "D", "A") == ["D", "B", "A"]
assert shortest_path(graph, "A", "A") == ["A"]
assert shortest_path(graph, "A", "E") is None
assert shortest_path(graph, "X", "A") is None
assert shortest_path(graph, "A", "X") is None
assert shortest_path(graph, "A", "D") in (["A", "B", "D"], ["A", "C", "D"])
print("7 checks passed")
```

这个例子约定节点用字符串表示，邻接表完整，`None` 只用于起点的前驱。`parent` 同时承担“访问过”和“从哪里来”两个职责：**入队时就记录前驱**，避免同一层的不同节点把同一个邻居反复加入队列。队列存节点、字典存前驱，不需要给每个候选都复制一整条路径。

在邻接表表示下，BFS 的遍历时间为 `O(V + E)`，辅助空间为 `O(V)`；`V` 是顶点数，`E` 是边数。返回路径时再逆序一次即可。它提供的是结构保证，不是“在大型数据库里一定很快”的性能承诺。

`A → B → D` 与 `A → C → D` 都有两条边。同长路径取哪一条，会受邻居访问顺序影响；因此测试既要覆盖这里固定顺序下的结果，也要理解“最短”未必唯一。算法不会因为两条路线一样短，就替我们判断哪条更有业务意义。

## 回到项目，跳数与关系方向不能略过

项目路径查询限制在 `HAS_KEYWORD` 关系上，使用 `*1..100` 的变长模式，并把连接写成无向匹配；同时排除了起终点相同的情况，再按路径长度取一条结果。这与上面允许零跳 `["A"]` 的教学函数有明确差别。

| 场景 | 教学 BFS | 项目查询的边界 |
|---|---|---|
| 起终点相同 | 返回零跳路径 | 查询条件排除相同节点 |
| 普通连接 | 依照邻接表访问 | 只沿 `HAS_KEYWORD`，最多 100 跳 |
| 边方向 | 由邻接表决定 | 匹配可双向走，但返回关系仍有存储方向 |
| 找不到 | 返回 `None` | 服务包装为空 `nodes`、`edges` |

例如文档 A 与文档 B 都包含关键词 K，存储的是 `A → K`、`B → K`，无向探索可以沿 `A → K ← B` 连接两份文档。它表达“共享关键词”，不表达“A 依赖 B”，更不意味着可以把第二条关系的语义箭头反过来。

`LIMIT 1` 限制的是最终返回条数，不足以证明前面匹配与排序的工作量很小；100 跳只是上界，也不是轻量查询的证明。要判断大图上的开销，需要真实数据与执行计划，本次只阅读源码，不把推演当作性能测试。

## “最短”需要先定义成本

边数最少只是最短路径的一种定义。如果不同关系有不同时间或业务成本，就需要相应的带权最短路径方法；例如 Dijkstra 适用于非负边权。可信度如果越大越好，则不能未经定义就直接拿来当“越小越好”的路径成本。

知识图谱还存在另一层问题：路径在结构上成立，不代表在语义上有用。两个高连接度公共节点可能让许多实体都只有两三跳距离，却不能解释真正的业务关联。因此路径查询通常还需要：

- 限制允许经过的实体和关系类型；
- 限制最大深度与结果数量；
- 过滤低可信或缺少来源的关系；
- 在结果中保留每一步关系方向；
- 显示路径对应的原始材料。

算法回答“怎样连接”，业务规则决定“哪些连接值得看”。

## 路径结果如何在前端表达

后端返回路径后，前端不应只显示一串节点名称。更完整的表达需要：

1. 明确起点和终点。
2. 按顺序展示中间节点。
3. 在每一步标出关系名称和方向。
4. 将路径外节点弱化，减少干扰。
5. 允许点击节点查看属性和来源。
6. 空路径时说明是无连接、条件过严还是查询失败。

图上高亮与文字路径可以同时存在。图形帮助理解整体结构，文字列表则更适合精确阅读和复制。只有颜色变化而没有关系说明，用户仍然需要猜测连接含义。

这也把问题接回上一篇的接口契约：路径参数要完整，节点标识要稳定，高亮状态不能在重新布局后消失。当前前端在没有边数据时还会按节点顺序构造高亮键；这种展示兜底不能证明原图里真的存在那条关系。验证仍应回到后端返回的关系及其端点，而不只看页面有没有变色。

## 什么是社区发现

社区是图中内部连接相对紧密、与外部连接相对稀疏的一组节点。社交网络中可能对应朋友圈，论文网络中可能对应研究主题，知识图谱中则可能反映某类概念或文档形成的关系群。

社区发现与普通分类不同。分类通常依赖预先定义的标签，社区则从连接结构中寻找群组。Louvain 等算法会尝试优化模块度，用来衡量社区内部连接相对随机网络是否更集中。

但社区编号本身没有业务含义。`社区 1`、`社区 2` 只是算法结果，需要结合群组中的高频实体、关键节点和来源文档才能解释。不同参数或数据更新也可能改变分组，因此不能把一次运行结果当作永久分类。

在项目中，社区查询会在需要计算时建立名为 `myGraph` 的 GDS 投影，选取 `DocumentNode`、`KeywordNode` 和无向 `HAS_KEYWORD`，再调用 Louvain。**投影是给算法使用的图表示，不是新的业务数据库。** 节点标签、关系范围与方向发生变化，算法看到的问题也跟着变了。

这条接口还有 Redis 结果缓存；命中缓存时不会重新创建投影和计算。因而“文档刚更新”不自动等于“社区结果已刷新”。排查分组变化时，应先确认输入图和缓存时点，再讨论算法参数。关于投影与模块度的基础定义，可继续看 [Neo4j 的 Louvain 文档](https://neo4j.com/docs/graph-data-science/current/algorithms/louvain/)。

## 社区结果怎样避免成为彩色节点

最简单的社区可视化是给每个群组一种颜色，但真正有用的页面还应该回答：

- 每个社区包含多少节点和关系；
- 哪些节点最能代表这个群组；
- 社区之间通过哪些桥接节点连接；
- 当前分组来自哪次计算和哪些筛选条件；
- 用户能否聚焦某个社区并继续查看详情。

颜色需要稳定且对比清楚，社区数量过多时则应结合筛选、列表或聚合，而不是继续增加颜色。用户选中一个群组后，可以弱化其他社区，展示代表节点和关联文档，让算法结果进入下一步探索。

所读接口把社区编号用于计算节点颜色，但返回的节点结构没有单独保留社区编号，前端又按颜色归组。这是已有代码的具体表达方式，不是理想契约。更清楚的改进是分别保留 `communityId` 与颜色：前者表示分组身份，后者只负责显示。换个配色不应该顺便把社区“换了户口”；本篇只讨论这一取舍，不修改原项目。

## 关键节点不等于连接最多

度数高的节点很活跃，但不一定最关键。PageRank 会考虑连接来源的重要性，中介中心性关注节点是否位于许多最短路径上。一个度数不高的桥接节点，可能连接两个原本分离的社区。

因此页面如果展示“关键节点”，必须说明指标。只显示一个分数而不解释算法，会让用户误以为它是统一的权威排名。图算法结果应该附带计算口径，并回到实际关系中解释。

## 算法功能的验证重点

算法单元测试可以验证已知小图的结果，但产品验收还要覆盖：

- 起点或终点不存在；
- 两个节点相同；
- 图中存在环；
- 存在多条同长度路径；
- 路径超过深度限制；
- 社区数量过多或只有一个社区；
- 返回节点在前端无法匹配；
- 暗色模式下高亮不可辨认。

最终不能只确认接口返回数组，还要确认用户看到的路径和群组与权威节点关系一致。

## 从算法接入中学到的事情

图算法的价值不在支持数量，而在能否缩小问题范围。BFS 提供结构最短路径，社区发现帮助观察群组，中心性指标提供不同角度的重要性，但它们都需要业务约束、来源证据和可解释界面。
