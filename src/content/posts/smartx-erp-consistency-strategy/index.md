ERP 的一致性问题通常不会表现为一个接口完全失败，而是部分业务已经成功：销售单进入已发货状态，但库存没有扣减；采购付款已经确认，但财务流水没有生成；消息被重复消费，导致同一业务流水出现两次。

这些问题不能只靠数据库本地事务解决，因为订单、库存和财务属于不同服务。也不能把所有链路都塞进同一个分布式事务，因为提醒、审计和派生事件允许延迟完成，强行同步只会放大耦合和超时。

SmartX 的可靠性方案采用分层处理：Seata 负责指定同步写链路，RocketMQ 负责异步事件，Outbox 兜底消息投递，幂等与对账负责重复和局部失败。

真正开始选择机制前，我先学会回答三个问题：结果是否必须在当前请求内可见，失败后能否补偿，同一动作重复执行是否安全。它们分别决定同步边界、恢复策略和幂等设计。中间件名称应该最后出现；如果一开始就说“这里上 Seata”，业务问题往往会礼貌地退到一旁，等系统上线后再回来。

## Seata 只保护必须共同成功的动作

销售发货会改变销售状态和库存，销售付款、采购付款会影响财务流水。这些动作如果在当前请求结束时只完成一半，用户会立即看到矛盾状态，因此适合使用 Seata AT 控制明确的跨服务事务边界。

关键是“指定链路”。Seata 没有覆盖所有接口，也没有代替消息系统。范围越大，锁、代理、超时和故障传播成本越高。只有业务上要求同步确认的写操作，才值得进入全局事务。

这种选择避免了两个极端：

- 完全不做跨服务一致性，把所有补偿交给人工。
- 所有动作都使用全局事务，把提醒、日志和派生数据也绑进同步请求。

## RocketMQ 处理允许延迟的派生事件

财务提醒、通知和部分派生动作不要求在业务接口返回前完成。它们更适合通过 RocketMQ 解耦：业务服务发布事件，消费方异步处理。

但“发送一条消息”并不等于可靠。业务事务提交成功后，如果 RocketMQ 暂时不可用，消息可能没有发送出去；消费端也可能在处理完成前重启，导致重复投递。

因此还需要 Outbox 和消费幂等。

## Outbox 解决业务提交与消息发送之间的空隙

SCM 在本地业务事务中同时记录 Outbox 事件，状态经历：

```text
PENDING → SENT
        ↘ FAILED
```

RocketMQ 暂时不可用时，业务事实和待发送事件仍然保存在数据库中，后台可以继续重试。运维人员也能通过状态定位“业务已经完成，但消息尚未投递”的记录。

Outbox 的关键并不是多一张表，而是业务记录与待发送事件在**同一个本地事务**中提交。数据库要么同时保存业务事实和事件，要么同时回滚。这样系统不会落入“业务成功，但事件没有留下任何痕迹”的空隙。消息发送可以晚一点，事件记录不能凭空消失。

当前 Outbox 主要覆盖采购财务提醒链路，它不是一套已经覆盖所有事件的通用平台。若销售侧未来需要同等级别的可靠事件，应按真实业务风险扩展，而不是为了架构完整而预先复制。

## 幂等、死信和对账处理“至少一次”

消息系统通常更容易提供至少一次投递，而不是严格一次。消费方必须假设同一消息可能再次到达。

“至少一次”并不是消息系统偶尔不认真，而是一种明确的可靠性取舍：宁可把同一消息再送一次，也不要静默丢失。消费者因此必须把重复消息当作正常输入。幂等键应该来自订单号、付款业务号或事件 ID 这类稳定事实，而不是每次重试都会变化的请求编号。

Finance 侧通过业务标识防止重复生成流水，并记录近期消费失败和死信。超过重试边界的消息进入可观察状态，而不是只在日志中消失。对账接口再检查“提醒已完成但流水缺失”等账实差异。

这三层职责不同：

- **幂等**阻止重复副作用。
- **死信和失败状态**保留无法自动处理的问题。
- **对账**发现历史上已经产生的业务差异。

如果只做幂等，遗漏消息仍然无法发现；只做重试，没有幂等会重复写入；只做对账，问题发现得太晚。三者需要组合。

## 可靠性机制不能替代验证

在代码中出现 `@GlobalTransactional`、Outbox 表和死信监听器，只能证明机制存在，不能证明所有故障场景都能恢复。

更完整的验证至少包括：

1. 下游服务超时时，全局事务是否回滚。
2. Seata Server 暂时不可用时，业务接口如何失败。
3. RocketMQ 不可用时，Outbox 是否保留事件并重试。
4. 同一消息重复到达时，是否只产生一次业务结果。
5. 消息超过重试次数后，是否进入可排查状态。
6. 人工补偿后，对账结果是否恢复一致。

当前项目已经形成正常链路和恢复入口，但没有把故障注入、积压恢复时间和高并发压测包装成已完成成果。

## 根据业务风险选择一致性

Seata、RocketMQ 和 Outbox 并不是重复建设，而是处理不同时间尺度的问题：

- 当前请求必须共同成功：同步事务。
- 可以延迟但不能丢失：异步消息和 Outbox。
- 可能重复：幂等。
- 自动处理失败：死信和人工入口。
- 历史状态可能偏离：对账。

分布式系统无法凭机制承诺“绝对零不一致”。更可靠的目标是让失败可见、可重试、可核对、可恢复。

把这些机制按业务要求放在一起，会得到一张比“技术全家桶”更有用的决策表：

| 业务要求 | 主要机制 | 必备补充 |
|---|---|---|
| 当前请求必须共同成功 | 本地事务 / Seata | 超时、回滚和故障验证 |
| 可以延迟但不能丢 | RocketMQ + Outbox | 重试与积压观察 |
| 消息可能重复 | 消费幂等 | 稳定业务键 |
| 自动处理最终失败 | 死信与人工入口 | 原因记录和重新执行 |
| 历史状态可能偏离 | 对账 | 人工补偿和结果复核 |

## 从一致性设计中学到什么

这部分代码让我逐渐放弃了“找到一个最强中间件，就能统一解决一致性”的想法。更实际的认识是：

- 一致性等级由业务后果决定，而不是由架构图是否漂亮决定。
- 本地事务、Seata、RocketMQ 和 Outbox 解决的是不同时间尺度的问题。
- 幂等键属于业务模型，不能只依赖传输层临时生成的标识。
- 重试不是恢复的全部；死信、对账和人工补偿也是正式功能。
- 验证必须落到最终业务状态，不能停在“消息发送成功”或“全局事务提交成功”。

分布式系统很少承诺“永远不会出错”。更专业的做法，是提前设计错误发生后怎样被看见、怎样继续处理，以及最后由谁确认账确实对上了。
