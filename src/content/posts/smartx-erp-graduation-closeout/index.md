这组文章中的 SmartX ERP，对应项目资料里的 SmartX EKG，是一个从 2025 年 12 月 25 日持续到 2026 年 8 月 20 日的本科毕业设计。系统将销售、采购、库存、财务和主数据放在传统 ERP 业务流程中，再用 Neo4j、混合检索 RAG 和 MCP 工具提供自然语言查询、关系探索、实体跳转和受权限约束的智能能力。

这类项目很容易在功能数量上不断扩张：再加一种模型、再加几个工具、再做一个图表、再补一张管理页面。但毕业设计后期真正困难的不是“还能做什么”，而是“哪些内容已经形成闭环，哪些仍然只是代码存在”。

## 项目结束日期，不是所有证据的日期

整理这组文章时，有几种日期很容易被混在一起：

| 日期 | 在本文中表示什么 | 不表示什么 |
|---|---|---|
| 2025-12-25 | 已确认的 SmartX 项目开发起点 | 更早的其他项目经历也属于 SmartX |
| 2026-07-26 | 本文主要使用的项目归档和测试材料快照 | 后续所有修改都经过同一批测试 |
| 2026-08-20 | 已确认的项目开发周期结束日期 | 当天重新执行过归档中的全部验收 |
| 2026-08-27 | 本篇复盘的文章日期 | 项目当天才开始，或测试结果当天仍然有效 |

开发到 8 月 20 日，不代表 7 月 26 日的测试自动覆盖了后续修改。文章可以继续补充代码理解，但测试数量仍要标明原来的日期。开发、验证和写作是三件不同的事。

## 收尾首先是统一事实

项目在不同阶段留下了大量 README、运行记录、专项总结和测试结果。数字也会随时间变化：MCP 早期运行闭环为 26 个工具，2026-07-26 的归档材料记录为 28 个；同一批归档材料记录了前端 176 项 Node 测试和后端 374 项 Surefire 测试通过。

如果只选最大的数字写进项目介绍，很容易把不同日期、不同命令和不同环境拼成一次不存在的验收。更可靠的方法是建立事实优先级：

1. 当前运行行为。
2. 当前源码、配置和测试报告。
3. 对应日期的验证记录。
4. 历史总结和计划。

旧材料用于解释演进，当前检查用于判断现状。遇到记录不一致时，先对齐版本、日期和验证条件，不急着选一个更好看的数字。

## 安全收尾：让源码可以交付

密钥从源码和文档中移出，`.env.example` 只保留变量说明；JWT 和内部 HMAC 缺失时快速失败；Gateway 清洗外部身份头，CORS 改为白名单配置。

这些工作不会产生更漂亮的截图，却决定项目能否安全交接。一个仓库如果必须依靠作者记住本地密码和启动参数，就还没有完成工程化。

归档中的生产准备缺口包括密钥轮换、TLS 和更完整的内部请求认证。源码中的时间戳签名并不等于已经具备 nonce 重放防护；可选审计文件写入也不等于长期留存、访问控制和恢复流程已经验收。这些边界需要分别记录，不能用“已接入 HMAC”或“有归档目录”一并带过。

收尾时还需要整理可交付物：启动说明、环境变量示例、依赖清单、初始化顺序、测试入口和已知限制。把源码压成最终版 ZIP 当然很有仪式感，但压缩包本身不会告诉接手者先启动 Nacos 还是先怀疑人生。

## 可靠性收尾：让失败可以恢复

销售发货和付款等指定同步动作使用 Seata；采购提醒则包含直接调用 Finance、保存 SCM Outbox 和发送 RocketMQ 消息。这些步骤不处于同一个本地事务，不能概括为一条已经原子化的可靠链路。Outbox 提供记录与重试入口，消费幂等、死信和对账各自处理部分失败；具体调用顺序与缺口见[第 06 篇：一致性机制的分工](../smartx-erp-consistency-strategy/)。

这里的成果不是“部署了很多中间件”，而是每个机制有明确职责。后续仍需要故障注入和恢复时间指标，才能证明在异常环境中的表现。

## 智能能力收尾：让 AI 进入业务边界

RAG 的回答不再只是文本。订单实体可以尝试定位详情，客户和供应商实体可以带条件筛选，但能否定位成功仍取决于实体识别、候选匹配与页面查询。现有文本规则和字段校验用于减少误链接，并不保证永远不误判；具体边界见[第 05 篇：从回答回到业务页面](../smartx-erp-rag-entity-routing/)。写操作仍以草稿和人工确认为边界，不把模型建议直接当成业务已经执行。

MCP 使用用户级 Key 映射真实员工，下游继续执行 RBAC 和部门数据范围。审计用于核对模型发起了哪些工具调用、工具返回了什么、最终答案用了哪些结果；它记录接口可见的过程，不是模型内部推理。写入失败、字段截断和记录淘汰的限制，在[第 03 篇：模型审计](../smartx-erp-agent-audit/)中单独说明。

这条链路的价值不在于让模型拥有更多权限，而在于让模型使用的权限与用户原有权限一致。

## 前端收尾：让系统看起来属于同一个产品

页面 Hero、筛选栏、详情面板、状态色、暗色模式和 AgentDock 逐步形成共享契约。联调暴露的乱码、空态、CORS、组件 warning 和响应式裁切，需要分别处理，不能一并归为“数据问题”。其中乱码的展示回退只是避免把坏字符直接呈现给用户，并没有修复数据库或导入链路中的原始数据；这一区别已在[第 01 篇：真实数据与页面体验](../smartx-erp-frontend-retrospective/)中展开。

后期形成的 Aeria 组件体系进一步把 ERP 内部模式整理为开放代码组件、Registry、CLI、主题和业务 Blocks。这让我看到 UI 收尾不只是在现有页面修样式，也可以提炼出可复用的实现；但归档中记录的本地成果，仍需与当时远端正式版本区分，不能默认两边已经同步。

## 验证收尾：让完成有证据

2026-07-26 的归档材料可以核对到：

- 7 个 Spring Boot 服务。
- 28 个 MCP 工具入口。
- 后端 374 项测试通过。
- 前端 176 项 Node 测试通过。
- Vite 生产构建成功。
- 历史记录中存在真实浏览器、权限矩阵、高风险动作和模型链路验证。

但项目没有生产上线、统一性能基线、真实业务收益和 RAG 准确率，因此不会写“支撑大量用户”“效率提升百分比”或“达到生产级 SLA”。

这里还需要把“功能完成”和“工程完成”分开。前者关注某个入口能否工作，后者还要回答：换一个环境能否启动，失败后能否定位，测试产生的数据怎样处理。一次演示可以避开异常路径，交付说明却不能把这些路径一起略去。

## 给遗留项写下接手条件

项目后期最容易出现两种极端：继续添加新功能，或者凭感觉宣布结束。比再列一遍功能更有用的是给具体事项标注状态，并说明下一次怎样接着做。

| 事项 | 整理时可以给出的状态 | 下一次接手需要的条件 |
|---|---|---|
| 用户级 MCP 查询 | 有历史身份对照证据；当前环境未复验 | 启动依赖，用同一员工、同一条件对照 UI 和工具结果 |
| 采购提醒 Outbox | 有事件记录和重试实现；不能当成完整原子链路 | 准备隔离测试单据，检查远程成功、本地失败等分支及最终状态 |
| 前端裁切修复 | 有指定宽度下的历史记录 | 保留版本、侧栏状态和样本数据，再做同条件回归 |
| 生产准备 | 不在本地演示结论的覆盖范围内 | 另行确定部署环境、安全要求、容量目标和恢复标准 |

例如“继续优化 Outbox”几乎没有接手价值；写清“先验证 Finance 成功而 SCM 落库失败时，两侧留下什么状态”，下一次才知道从哪里开始。这里最重要的不是把每一项都标成完成，而是让“有实现”“历史验证过”“当前待复验”“暂不处理”不再混成一种状态。

## 一个毕业设计最终应该留下什么

交付材料需要彼此对得上：启动说明里的变量名应与配置示例一致，验证记录应指向对应版本和测试入口，遗留项应说明从哪条业务路径继续检查。接手者能从说明找到命令，再从结果找到判断依据，才不必每走一步都回来问作者。

2026-07-26 的归档表明，SmartX 当时已完成主要开发，本地构建、测试和部分浏览器链路留有验证记录，可支撑对应版本的毕业设计演示。本文引用的是这一历史快照；当前环境未整体复验，也没有生产运营结论。

## 从工程收尾中学到什么

这次复盘让我学会把“还要开发什么”和“还要验证什么”分开。前者可能要补代码，后者则要准备身份、数据和失败条件；已经有重试任务，不代表还需要再写一套，也可能是尚未检查它能否处理远程成功、本地失败的情况。

以后再接手一个搁置过的功能，我会先确认已有实现、上次验证的条件和剩下的疑问，再决定怎么改。遗留项写得具体，是为了下次能从已知位置继续，而不是重新猜一遍当初的想法。
