SmartX ERP 里原本已经有 RAG 助手和 AgentDock。MCP 控制台不是给普通员工看的，员工也不应该自己管理 Key 或工具列表。技术组件应该留在技术边界内，否则员工只是想查库存，最后却先上了一节密钥管理课。

Agent Bridge 把这件事留在后端：员工仍然在熟悉的助手里提问，系统根据他的身份和权限，把问题、工具和上下文交给外部模型，再让模型按需要调用 MCP 工具。读这部分代码时，我逐渐把它理解成一层适配边界，而不是另一个聊天入口。

## Agent Bridge 是一层适配边界

Bridge 并不是简单转发 HTTP。它要把业务用户、模型 provider、可用工具和审计上下文组合起来，再将模型的工具调用安全地交给 MCP 服务。

```text
员工问题
  → 识别身份与数据范围
  → 选择模型和允许工具
  → 执行模型步骤与工具调用
  → 汇总业务结果
  → 生成回答并记录审计
```

适配层的价值是隔离变化。前端不必理解不同模型 provider 的细节，下游业务服务也不需要直接信任模型。只要边界契约稳定，模型或工具实现变化时，业务入口不必跟着重写。

## 配置和可用不是一回事

API Key 验证通过、provider 中能看到模型，只说明配置检查走通了。前端助手能否查到库存，还取决于 Gateway、RAG、MCP 和业务服务是否真正连通；启动与配置的排查放在[第 04 篇：可复现环境](../smartx-erp-reproducible-environment/)展开。

回到审计，排查入口是找到这次问答对应的记录，再看它走到了哪一步。没有新记录，可能是请求没有进入 Bridge，也可能是审计写入失败；有记录，也不等于业务查询已经成功。不能只凭控制台里“有或没有一行数据”判断整条链路。

## 为什么要模型审计

当 AI 只是聊天时，排查通常只能看 prompt 和最终回答。但当 AI 可以调用 ERP 工具后，问题会变成一条链：

用户问了什么？模型看到了哪些工具？它有没有发起 tool call？工具按谁的身份执行？返回了什么业务事实？最终答案有没有忠实使用这些结果？

如果没有模型审计，管理员只能猜。

模型回答有一个特别之处：它即使出错，也常常语句完整、态度从容。传统异常会留下堆栈，模型错误则可能只留下一段非常自信的错误答案，因此更需要记录证据链。

模型审计页记录用户、问题、provider、模型、暴露工具、模型步骤、工具调用参数、工具返回、最终答案和错误。这里的“步骤”是接口可见的调用过程，不是模型的内部思考过程。审计能帮助核对答案依据，不能保证解释模型产生每一句话的原因。

## 如果助手说“没有缺货物料”，该从哪里查

假设员工问“查看缺货库存”，助手却回答“没有缺货物料”。这段回答本身看不出问题：确实没有、没权限查、工具没被调用、查询条件错误，都可能在最后变成类似的句子。

下面是沿着现有审计字段做的教学推演，不是某次已捕获事故的复现：

| 依次核对的记录 | 如果看到这种情况 | 接下来查什么 |
|---|---|---|
| 用户与暴露工具 | 工具列表没有 `inventory_page_overview` | 先查该员工的权限与工具过滤，不急着改 prompt |
| 模型步骤与工具调用 | 工具可用，但没有发起查询 | 再查工具描述、模型选择与本次上下文 |
| 工具参数 | 库存状态没有使用 `SHORTAGE`，或额外带了关键字 | 对照问题检查参数，而不是直接相信回答中的“缺货”二字 |
| 工具结果 | 查询成功，但记录为空 | 在相同员工、相同筛选条件下对照 UI，继续核对数据范围 |
| 最终答案 | 工具返回了匹配记录，回答却说没有 | 问题已经落到结果汇总阶段，不必从数据库重新查起 |

这些分支里，“工具不可用”和“工具查询为空”尤其值得分开。前者不能提供库存结论；后者也只说明当前身份、条件和分页下的查询结果。把它们都兜底成“暂无数据”，页面会显得很平静，排错的人却要重新走完整条链路。

代码在 Bridge 调用的 `finally` 中尝试记录审计，因此异常路径也有机会留下工具和错误信息。但审计写入失败会记录警告，并不保证每次问答一定成功留档；审计中的 `success` 也表示调用流程的成败，不等于答案的业务事实已经判定正确。这两个区别决定了控制台里的一个绿色状态到底能说明多少事情。

## 有记录，也不代表保留了全部现场

当前审计写入 Redis Stream，并以约 100,000 条为裁剪目标；问题、工具调用和最终答案等字段还分别有长度限制。长结果可能发生字段截断，早期记录也可能被淘汰。查不到某段返回值时，要先检查保存范围，不能马上判断模型当时没有看到它。

源码还提供了可选的文件归档入口，但“有归档开关”与“已经具备长期审计制度”不是一回事。保留多久、谁可以查看、写入失败如何发现，都需要另外规定。这让我认识到，审计本身也是一个有容量、有失败路径的子系统，并不是在主流程旁边加一句日志就结束了。

## 日志、追踪与审计不是同一件事

- **日志**记录某个组件发生了什么，适合排查局部异常。
- **追踪**使用 trace ID 串起一次请求经过的多个服务和步骤。
- **审计**记录谁在什么时间执行了什么动作，以及结果和责任边界。

模型链路跨越前端、Bridge、provider、MCP 和业务服务，仅靠每个服务各写一份日志，很难还原完整过程。为一次问答分配关联 ID，并在模型步骤、工具调用和下游请求中透传，才能把分散证据连起来。

审计记录也不能无限保存原始内容。用户问题、工具参数和返回值可能包含订单、客户或财务数据，需要脱敏、权限控制、保留期限和访问记录。可追踪不等于把所有敏感信息永久复制一份。

## 控制台应该服务排查

MCP 控制台最后更像一个小型运维台，而不是员工入口。管理员可以看工具、Key、服务状态、调用历史和模型审计；员工只需要在业务助手里完成工作。

这个边界让我觉得很关键。很多技术功能做着做着会忍不住暴露给所有人，但企业系统里不应该让业务用户承担技术组件的复杂度。

控制台更适合回答可操作问题：哪一步失败、使用了哪个身份、工具耗时多久、错误能否重试。仅仅展示大量 JSON 虽然很“技术”，但排查效率可能和直接翻日志相差不大。

## 从模型审计中学到什么

Agent Bridge 让我看到，AI 接入业务系统的重点不是"能不能叫大模型"，而是能不能被业务流程接住——身份、权限、工具、审计和错误处理得连在一起。

以后继续完善时，我会让审计页更适合定位差错，并用固定问题集验证工具选择、业务事实和引用结果。模型不需要每次都表现得无所不知；该查数据时愿意查数据，反而更像可靠的系统成员。
