SmartX ERP 里原本已经有 RAG 助手和 AgentDock。MCP 控制台不是给普通员工看的，员工也不应该自己管理 Key 或工具列表。技术组件应该留在技术边界内，否则员工只是想查库存，最后却先上了一节密钥管理课。

我需要设计一条后端链路：员工仍然在熟悉的助手里提问，系统根据他的身份和权限，把问题、工具和上下文交给外部模型，再让模型按需要调用 MCP 工具。这就是我做的 Agent Bridge。

## Agent Bridge 是一层适配边界

Bridge 并不是简单转发 HTTP。它要把业务用户、模型 provider、可用工具和审计上下文组合起来，再将模型的工具调用安全地交给 MCP 服务。

```text
员工问题
  → 识别身份与数据范围
  → 选择模型和允许工具
  → 执行模型步骤与工具调用
  → 汇总业务结果
  → 生成回答并记录审计
```

适配层的价值是隔离变化。前端不必理解不同模型 provider 的细节，下游业务服务也不需要直接信任模型。只要边界契约稳定，模型或工具实现变化时，业务入口不必跟着重写。

## 配置和可用不是一回事

做这条链路时，我反复遇到一个问题：配置存在，不代表系统活着。

API Key 可以验证通过，模型也能在 provider 里看到，但如果 Nacos、gateway、RAG 服务、MCP 服务没有运行，前端助手仍然不会真的使用这条链路。

所以我把判断拆成两层：配置层看 `.env`、provider、base URL、model、key；运行层看服务是否启动、端口是否监听、浏览器能不能访问、模型审计有没有新记录。不能把"配置好了"说成"系统已经可用"。

这对应监控中的几个层次：配置存在、进程运行、依赖健康、业务可用。端口监听只能证明某个进程占用了端口，不能证明它能完成一次真实库存查询。健康检查要逐层接近用户最终动作。

## 为什么要模型审计

当 AI 只是聊天时，排查通常只能看 prompt 和最终回答。但当 AI 可以调用 ERP 工具后，问题会变成一条链：

用户问了什么？模型看到了哪些工具？它有没有发起 tool call？工具按谁的身份执行？返回了什么业务事实？最终答案有没有忠实使用这些结果？

如果没有模型审计，管理员只能猜。

模型回答有一个特别之处：它即使出错，也常常语句完整、态度从容。传统异常会留下堆栈，模型错误则可能只留下一段非常自信的错误答案，因此更需要记录证据链。

我设计的模型审计页记录：用户、问题、provider、模型、暴露工具、模型步骤、工具调用参数、工具返回、最终答案和错误。目标是能回答一句话：AI 为什么这么说。

## 日志、追踪与审计不是同一件事

- **日志**记录某个组件发生了什么，适合排查局部异常。
- **追踪**使用 trace ID 串起一次请求经过的多个服务和步骤。
- **审计**记录谁在什么时间执行了什么动作，以及结果和责任边界。

模型链路跨越前端、Bridge、provider、MCP 和业务服务，仅靠每个服务各写一份日志，很难还原完整过程。为一次问答分配关联 ID，并在模型步骤、工具调用和下游请求中透传，才能把分散证据连起来。

审计记录也不能无限保存原始内容。用户问题、工具参数和返回值可能包含订单、客户或财务数据，需要脱敏、权限控制、保留期限和访问记录。可追踪不等于把所有敏感信息永久复制一份。

## 控制台应该服务排查

MCP 控制台最后更像一个小型运维台，而不是员工入口。管理员可以看工具、Key、服务状态、调用历史和模型审计；员工只需要在业务助手里完成工作。

这个边界让我觉得很关键。很多技术功能做着做着会忍不住暴露给所有人，但企业系统里不应该让业务用户承担技术组件的复杂度。

控制台更适合回答可操作问题：哪一步失败、使用了哪个身份、工具耗时多久、错误能否重试。仅仅展示大量 JSON 虽然很“技术”，但排查效率可能和直接翻日志相差不大。

## 从模型审计中学到什么

Agent Bridge 让我看到，AI 接入业务系统的重点不是"能不能叫大模型"，而是能不能被业务流程接住——身份、权限、工具、审计和错误处理得连在一起。

以后继续完善时，我会让审计页更适合定位差错，并用固定问题集验证工具选择、业务事实和引用结果。模型不需要每次都表现得无所不知；该查数据时愿意查数据，反而更像可靠的系统成员。
