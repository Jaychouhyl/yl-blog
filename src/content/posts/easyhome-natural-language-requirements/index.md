传统房源搜索使用区域、价格、面积、户型和楼层等筛选项，优点是确定、快速、结果容易解释。但用户真实表达需求时，往往会说“离公司近一点”“适合老人居住”“周围安静”“预算不要太高”。这些描述很难直接对应一个数据库字段。

EasyHome 让我开始思考：自然语言并不是替代筛选器，而是帮助用户把模糊需求逐步转化为可以执行的条件。这条链路主要来自我对团队用户端、接口和材料的后期学习。重要的不是模型能不能说出推荐理由，而是代码怎样保存约束、处理歧义并把结果交回确定性的房源数据。

## 当前代码先判断能否继续，并没有完整的条件解析器

这篇讨论的“结构化需求”是从项目继续推导的设计方法，不能直接当成既有功能。固定版本里，前端提交的是会话 ID 和消息正文；后端先让模型根据历史消息和本轮问题给出一个判断：

| 模型判断 | 服务中的处理 | 能说明什么 |
|---|---|---|
| AGAIN | 返回固定的非房源话题提示 | 本轮被判断为不适合继续 |
| MORE | 返回固定的补充信息提示 | 本轮被判断为信息不足 |
| 其余输出 | 进入房源检索与回答链路 | 代码走到了后续分支，不等于条件已被严格校验 |

提示词要求第三种回答为 `CONTINUE`，但实现通过字符串是否包含 `AGAIN` 或 `MORE` 来分支，剩余输出都会继续。也就是说，**提示词中的协议，比实际解析规则更严格**。后续若改成明确枚举解析，就可以对未知输出单独处理；这里不把这个建议写成当前已经完成的验证。

对于已有会话，项目还会结合历史把追问改写成独立问题，再做向量检索。普通房源列表另有价格、面积和户型等查询字段，但没有看到这条聊天链路自动生成这些结构化筛选参数。它目前更接近“话题判断＋问题改写＋语义召回”，不是完整的“槽位抽取＋硬条件查询”。

## 硬条件与软偏好需要分开

“总价不超过 200 万”通常是硬条件，不满足就应该排除；“尽量安静”属于软偏好，可以用于排序和解释。两者如果混在一段提示词中，模型可能为了满足软偏好而忽略预算。

可以将需求拆成：

```text
硬条件：预算上限、区域、户型、面积范围
软偏好：安静、采光、通勤、生活便利
排除条件：不要临街、不要顶层、不要无电梯
待确认信息：公司位置、可接受通勤时间、预算是否含税费
```

如果继续完善这条链路，代码层面最好使用结构化对象保存，而不是反复传递自然语言字符串。结构化条件可以被校验、记录和修改，也能明确哪些内容来自用户原话、哪些是系统推断。

## 意图识别与槽位抽取

自然语言理解中，意图表示用户想做什么，槽位表示完成这个意图需要哪些参数。例如：

```text
用户：想在滨江找一套两居室，预算 250 万以内。

意图：查找房源
区域：滨江
户型：两居室
预算上限：250 万
```

槽位抽取不是把所有名词都保存下来。数值需要单位换算，区域名称需要映射到系统内部编码，“两居室”和“两房”也可能需要规范化。

模型可以输出候选 JSON，但后端仍应校验字段类型、范围和允许值。不能因为返回内容看起来像 JSON，就直接拼接数据库条件。结构化输出的价值是方便校验，而不是让模型替代校验。

## 多轮对话需要合并条件，而不只是累积句子

“记住聊天记录”和“维护已确认需求”不是同一件事。下面用一个**设计推演**说明差别，不是项目实测对话：

| 本轮表达 | 应保留的旧条件 | 本轮应修改的条件 |
|---|---|---|
| 滨江，两居，预算 300 万 | 无 | 建立区域、户型和预算 |
| 预算改成 250 万，其他不变 | 滨江、两居 | 只更新预算上限 |
| 楼层先不限制 | 区域、户型、预算 | 显式取消楼层限制 |
| 最好再安静一些 | 之前确认的硬条件 | 增加安静偏好，不提高预算 |

这里至少有三种不同动作：没有提到某字段、给字段设置新值、明确取消字段。把三者都写成一个空值，就无法判断用户到底是“没改”还是“删掉”。不一定一开始就设计复杂的补丁协议，但这三个含义必须先在业务上分清。

所读代码把会话保存在进程内的 Map 中，内容是历史消息列表；问题改写依赖模型重新阅读这些消息，并不等于系统已经维护了一份可校验的预算、区域和排除条件表。模型可以帮助回忆语境，但预算最好不要只靠它的记性。

因此，后续实现时可以保留用户原话，再单独保存已确认条件及其变更来源。新的问题先解释“这轮改了什么”，然后再执行查询；这样用户也能看见系统有没有误解。

## 缺失信息应该追问，而不是猜测

用户说“想买一套上班方便的房子”，系统并不知道工作地点和可接受通勤时间。直接推荐可能得到看似合理但没有依据的结果。

理想的结构化需求解析完成后，可以检查必要槽位；当前的固定补充信息提示还不等于已经定位到了具体缺失字段：

- 缺少关键硬条件时，提出一个具体问题；
- 条件互相冲突时，指出冲突而不是静默放宽；
- 对模糊偏好保留原文，并说明系统怎样理解；
- 给用户提供修改结构化条件的入口。

对话的价值不只是聊天，而是逐步补全查询。每轮回答都应该让系统状态更明确，而不是生成更多无法执行的描述。

## 结构化筛选与语义检索如何配合

价格、面积和户型适合使用数据库条件精确过滤；“环境安静”“适合养老”等描述更适合从房源介绍、周边信息和知识材料中做语义检索。

一条合理流程可以是：

```text
自然语言需求
  → 提取硬条件与软偏好
  → 用硬条件缩小房源集合
  → 用软偏好检索和排序候选
  → 生成可以核对的推荐理由
```

先过滤再进行语义排序，可以避免向量结果推荐超预算或户型不符的房源。反过来，如果硬条件太多导致零结果，系统应明确告诉用户哪些条件限制了结果，再由用户决定是否放宽。

以上流程是改进方案，不是当前源码的调用顺序。现在聊天侧的向量搜索与普通列表条件查询仍是两条路径。把结构化条件真正交给查询层、将条件展示给用户确认，才算接上这个方案。

## 条件规范化是容易忽略的基础工程

自然语言中同一条件可能有多种写法：

- `200 万`、`200w`、`两百万`；
- `两室一厅`、`两居室`、`2 房`；
- `地铁附近`、`步行可到地铁`、`离地铁近`。

数值和枚举条件可以通过规则规范化，模糊语义则需要结合知识和业务定义。系统必须确定“地铁附近”到底代表 500 米、1 公里还是仅仅在描述中出现相关词。

以教学预算为例，200 万、200w 和两百万可以规范为同一个数值 2,000,000 元；但前提是接口、数据库与页面都明确使用“元”。如果既有接口采用“万元”，转换点就必须放在边界上，并保留单位说明，不能照搬这个教学数值直接传参。不存在一个脱离接口约定、放之四海而皆准的裸数字。

没有统一口径，模型每次可能给出不同解释，推荐结果也无法复现。规则与模型并不是对立关系：规则保证确定边界，模型处理语言变化。

## 推荐结果应该解释条件匹配

推荐理由不能只写“这套房非常适合你”。更有用的解释应该对应用户条件：

- 哪些硬条件已经满足；
- 哪些软偏好有数据支持；
- 哪些信息仍然缺失；
- 房源事实来自哪个字段或资料；
- 为什么它排在其他候选之前。

如果系统说“通勤方便”，就应该能够说明参考了哪个位置、距离或交通信息。没有数据支持的形容词应该保持克制。

前端还应把推荐理由重新连接到房源卡片、详情、收藏和预约，而不是让用户读完回答后重新搜索。

## 需求解析怎样验证

仅看几个演示问题不足以验证。可以建立包含不同表达方式的固定样本：

- 单一硬条件；
- 多个条件组合；
- 单位和同义表达；
- 缺少必要信息；
- 互相冲突的条件；
- 包含否定词；
- 无法映射到现有字段的偏好。

还要区分两套验收：对当前实现，检查话题分支、历史参与的问题改写以及是否进入检索；对新增的结构化方案，再检查字段合并、单位、否定和硬条件过滤。不能用后者的设计表格来宣称前者已经通过完整需求解析测试。

每条样本同时定义期望意图、结构化字段、追问行为和最终筛选结果。这样模型或提示词变化后，可以比较系统行为是否退化。

## 从需求理解中学到的事情

自然语言界面真正有价值的部分，是降低用户表达需求的门槛，再把这些需求转回可验证的数据结构。模型负责理解语言，规则负责约束字段，数据库负责权威事实，用户负责确认不确定信息。

这让我对“智能交互”有了更具体的理解：不是让模型替系统做决定，而是让模型成为结构化业务流程的入口。下一篇将继续讨论候选房源确定后，RAG、Embedding 和 pgvector 怎样为语义检索与推荐理由提供支持。
