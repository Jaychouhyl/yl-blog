收藏一篇网页、把视频放进稍后观看，或者把 PDF 下载到电脑里，都只能说明“资料已经保存”，不能说明“知识已经进入自己的系统”。真正需要使用时，仍然要回到原平台搜索、重新观看视频，或者在一堆文件名里猜测内容。

Auto Obsidian MD 的第一项工作，就是把不同来源变成结构统一的本地 Markdown。它处理的不只是网页，还包括 RSS、视频链接、字幕、PDF、图片、音频、视频和本地目录。来源不同，提取方式也不同，但最终都要进入同一条入库链路。

## 先理解 ETL：入库不是复制文件

数据工程中常见的 ETL 分为三个阶段：

1. **Extract，提取**：从网页、文件或媒体中取得原始内容。
2. **Transform，转换**：清洗噪声、统一编码、补充结构和元数据。
3. **Load，装载**：按照约定写入目标系统。

知识入库与 ETL 很像。复制网页正文只是完成了提取的一部分；如果没有标题、来源、时间、标签和稳定文件名，后续仍然难以检索。如果摘要生成成功，却没有保存原始链接，也无法回到权威来源核对。

因此项目把流程整理为：

```text
来源发现 → 采集与去重 → 内容提取 → 清洗与结构化 → 摘要与分类 → Markdown 输出
```

每一步只解决一个问题。采集器不负责决定笔记放在哪个目录，模型也不负责保存任务状态。职责分开后，新增一种来源时，不需要重新实现整套输出逻辑。

## 为什么不同内容需要不同提取方式

“提取文本”并不是一种固定算法。资料是否已经包含可读取的文字，决定了后续处理方式。

### 网页与文本型 PDF

网页通常同时包含正文、导航、推荐卡片、广告和脚本。提取器需要识别主要内容，而不是直接保存完整 HTML。文本型 PDF 内部已经保存字符和排版信息，可以直接读取文字，但还需要处理断行、页眉、页脚和错误的阅读顺序。

### 图片与扫描型 PDF

扫描件表面上是 PDF，本质上却是一组图片。这时必须使用 OCR，也就是 Optical Character Recognition。OCR 先定位文字区域，再把像素识别为字符。图片分辨率、倾斜角度、背景噪声和中英文混排都会影响结果，因此 OCR 输出应被视为“待校对文本”，而不是天然准确的原文。

### 音频与视频

视频如果有可靠字幕，可以优先处理字幕；没有字幕时再使用 ASR，也就是 Automatic Speech Recognition。Whisper、FunASR 等工具把音频信号转换成文字，但专有名词、口音、背景音乐和多人对话仍可能造成错误。保存时间信息和原始媒体地址，可以让用户在发现问题时快速回听。

这也说明一个基础原则：**先使用信息损失最少的来源**。已有正文就不要 OCR，已有字幕就不必重新识别音轨。更复杂的模型不一定带来更可靠的结果。

## 用统一内容对象隔离来源差异

如果网页采集器直接写 Markdown，视频处理器再设计另一套格式，笔记很快会变得不一致。更稳定的方法是先把来源转换成统一内容对象，例如：

```text
标题
正文
来源地址或本地位置
来源类型
采集时间
作者或频道
原始发布时间
处理状态
```

上面的列表是理解数据流的概念模型，不是项目中某一个类的完整字段。源码实际把信息分成了几层：`QueueItem` 保存来源、任务状态和输出位置，采集与转写结果保存提取过程，`NotePayload` 再承接摘要、正文和处理备注。输出器接收的是已经渲染好的内容，不必各自再识别一次网页或视频。

这让我对“统一接口”有了更具体的认识：统一的是下一阶段真正需要的信息，不是把所有阶段的字段塞进一个越来越大的对象。下载器仍要识别平台差异，但这些差异不应一路传到 Markdown 写入器。

同一份内容因此可以输出到普通文件夹、Obsidian vault、HTML、CSV 或 Notion。不过，共用输入不代表各个目标都是无损副本：CSV 更接近笔记索引，HTML 和 Notion 有各自的渲染规则。选择输出格式时，要先问“以后拿它做什么”，而不只是“这个格式能不能导出”。

## 跟着一条网页，看数据在哪一步发生变化

假设导入的是下面这个演示地址。它只是用来说明字段变化，不对应真实采集任务：

```text
导入地址：https://example.com/article?id=42&utm_source=reader
队列地址：https://example.com/article?id=42
```

项目的来源规范化逻辑会移除 `utm_` 一类已知跟踪参数，但保留这里的 `id=42`；地址发生变化时，入队逻辑还会在元数据中保留 `original_source`。这样既方便识别重复来源，也能知道最初导入的地址是什么。

不能为了让网址“看着干净”把所有参数都删掉。`utm_source` 通常回答“从哪里点过来”，`id` 可能回答“到底是哪篇文章”。删错字段，就不是去重，而是把不同资料误认成了同一份。

继续沿着这条资料往后读，可以把责任分成四段：

| 阶段 | 主要回答的问题 | 不应该替下一段做的决定 |
|---|---|---|
| 入队 | 来源是什么，是否已经存在 | 不把“成功排队”写成“内容完整” |
| 提取 | 正文在哪里，是否需要 OCR 或转写 | 不用一段摘要冒充原始提取结果 |
| 整理 | 哪些是要点，适合什么标签 | 不凭空补出原文没有的结论 |
| 输出 | 内容写到哪里，生成了什么路径 | 不靠文件存在就判断知识质量 |

还有一个容易混淆的字段是时间。笔记中的 `created` 来自任务创建时间，不等于原网页的发表时间。几个月前的文章今天才导入，两个时间不同完全正常。**字段都叫“时间”并不意味着它们描述同一件事**，这也是数据建模里很基础、却很容易省略的一步。

## Markdown 为什么适合作为默认格式

Markdown 的优势不只是“写起来简单”。它是普通文本，可以被编辑器、Git、搜索工具和程序同时读取；即使未来不再使用 Obsidian，文件本身仍然存在。

一篇可长期使用的笔记至少应保留：

- 清楚且稳定的标题；
- 原始来源与采集时间；
- 未被摘要替代的正文；
- 可选的摘要、标签和目录建议；
- 能够区分原文与程序补充内容的结构。

模型生成的摘要可以帮助快速理解，但不宜成为唯一内容。摘要会遗漏细节，也可能误解原文。Auto Obsidian MD 的默认笔记模板保留来源、处理备注和原始转写区域，模型能力则放在可选的整理阶段；模板配置也允许关闭原始转写，使用时需要知道这一取舍。

“原始转写”在这里指程序提取或识别得到的文本，并不等于原始网页、PDF 或音视频的逐字无损备份。遇到公式、表格或识别可疑的术语，仍然要回到来源核对。摘要适合做导读，不适合替原文签字。

## 任务完成，不等于内容完整

项目里有两种容易被一起理解成“成功”的状态：

- **队列状态**：处理和写入流程是否走完，例如 `done`。
- **笔记完整性**：是否取得了足够的原始内容，例如笔记中的 `status: incomplete`。

在当前处理链路中，如果缺少工具导致只能取得元数据，程序仍可能生成带来源和处理说明的降级笔记，并将写入成功的任务标记为 `done`；笔记则通过 `incomplete` 提醒内容还不完整。这不是两个状态互相矛盾，而是它们回答的问题不同。

因此验收时不能只数生成了多少个 `.md` 文件。对于一份扫描 PDF，还要确认正文不是空的、关键术语识别正确、页码或来源可回查。这类检查不会让文件数量变多，却能避免把一箱“待核对资料”当成已经整理好的知识库。

## 如何判断一次入库是否成功

程序没有报错，只能证明流程运行结束。更有意义的检查包括：

1. 标题、正文和来源是否完整。
2. 网页导航、广告和重复段落是否被清理。
3. OCR 或转写结果是否保留可核对入口，降级笔记是否明确标出不完整。
4. 相同内容再次导入时是否被识别。
5. 输出文件名是否稳定，链接和图片是否仍可访问。
6. 不启用模型时，基础笔记是否仍然能够生成。

最后一项尤其重要。知识入库的核心是可靠保存，而不是依赖某个模型才能运行。模型可以改善摘要和分类，但不应成为保存资料的前置条件。

## 从这条链路学到的事情

这个项目让我理解，个人知识管理首先是一个数据治理问题。资料来源越多，越需要统一契约、可追溯元数据和明确的处理边界。支持更多平台只是表面能力，真正决定工具能否长期使用的是：内容能不能稳定进入本地、能不能回到原始来源、能不能继续被搜索和编辑。

下一篇将继续讨论批量入库中更容易被忽略的问题：为什么任务需要落进 SQLite，为什么失败后应该单独重试，以及幂等和状态机如何避免重复处理。
