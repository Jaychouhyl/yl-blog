EasyHome 最容易吸引注意的是自然语言推荐，但我最先深入接触的是管理后台。房源能否展示、用户是否正常、预约有没有处理，都需要经过传统业务页面维护。推荐功能位于用户体验前台，管理端则决定系统使用的数据是否可靠。

这部分也是我在项目中实际编写和调整较多的代码。与其只记录完成了哪些页面，我更想整理自己从后台开发中理解到的编程问题：组件怎样划分、状态如何流转、接口为什么不能只看成功响应，以及 UI 一致性为什么会影响维护成本。

## 先分清页面原型与真实业务链路

这次对照源码时，一个重要发现是：**房源管理、用户管理和预约管理页面使用了本地模拟数据**。房源新增、修改、删除主要改变页面数组；预约审核处理也先修改本地状态，再显示提示。后端虽然另有审核接口，但不能据此认为这些页面已经调用了它们。

所以这篇保留两种层次：从现有页面学习组件、筛选与状态表达；从后端接口学习真正接通业务时必须遵守的契约。一个“操作成功”的通知可以证明提示组件工作正常，还不能替数据库签收。

实现依据为文末固定版本源码。以下改善建议不是把页面原型补写成已完成的线上系统，也不借此否定原型帮助理解业务的价值。

## 后台页面首先要理解业务对象

管理端中的用户、房源、审核记录和预约不是四张互不相关的表。它们存在明确关系：用户发布房源，房源经过审核后进入可展示状态，其他用户查看房源并创建预约，管理员再处理预约状态。

如果前端只按照接口字段生成表格，很容易遗漏业务语义。例如某些系统用数字表示房源状态，页面仍需知道每个值代表什么；而 EasyHome 所读页面与后端还存在另一种更具体的情况：两端使用的预约状态名称并不完全一样。不同状态下允许的操作，不能只凭文案相近来猜。

因此写页面前需要先整理：

- 当前页面管理的核心对象是什么；
- 对象有哪些状态；
- 哪些操作会改变状态；
- 操作是否可逆；
- 变化后会影响哪些其他页面；
- 用户需要看到哪些确认和失败信息。

这其实是在前端建立一个简化的领域模型。模型不一定写成复杂类，但代码必须体现业务规则，而不是让按钮在任何状态下都能出现。

## 同一个“审核通过”，两端可能不是同一个值

预约管理页使用 `approvalStatus`，后端预约记录使用 `status`，不仅字段名不同，枚举也不同：

| 业务含义 | 页面原型中的值 | 后端审核服务中的值 |
|---|---|---|
| 待处理 | PENDING | PENDING |
| 审核通过 | APPROVED | CONFIRMED |
| 审核拒绝 | REJECTED | CANCELLED |

后端审核入口接收预约记录 ID、是否通过和可选原因；服务先检查记录存在且处于 `PENDING`，再更新状态。前端原型则修改自己的数组。这说明接入接口之前，必须先确定字段映射、参数语义和刷新方式，而不是只把一个请求地址粘到按钮里。

这里最值得学的是**状态转换**：它描述“从什么状态出发，什么操作允许把它变到哪里”。用颜色区分状态只是展示规则，不是完整的业务规则。如果两个管理员同时处理同一条记录，还需要进一步核对服务端的并发更新约束；不能仅凭一次查询后检查，就声称已经解决所有竞争问题。

## 组件拆分不是越细越好

Vue 组件能够隔离模板、状态和样式，但把每一行表单都拆成组件并不会自然提高质量。更有意义的拆分依据是职责：

- 页面组件负责查询条件、分页和整体流程；
- 表格组件负责展示列表和触发操作；
- 编辑或审核弹窗负责字段校验和提交；
- 状态标签负责统一显示颜色与文案；
- API 模块负责请求参数和响应类型。

如果弹窗内部直接修改外层列表，又同时调用接口和控制通知，依赖会变得混乱。更清晰的方式是让弹窗提交成功后发出事件，由页面决定重新查询或局部更新。

组件边界应该回答三个问题：它负责什么、需要哪些输入、会向外产生什么结果。只按照视觉区域切割，往往会得到看似整齐但难以复用的代码。

## TypeScript 的价值是约束变化

后台字段多，状态和值域也较明确，很适合使用 TypeScript 描述。下面只用一个简化类型说明“有限状态比任意字符串更明确”，不是 EasyHome 实际接口结构：

```ts
type ReviewStatus = 'pending' | 'approved' | 'rejected'

interface HouseSummary {
  id: number
  title: string
  price: number
  status: ReviewStatus
  publisherName: string
}
```

类型可以在编译阶段发现字段拼错和空值处理问题，也能让状态对应的操作更清楚。但类型定义不能只复制后端 JSON。如果接口把所有状态都声明为普通字符串，前端仍然无法知道允许哪些值。

我逐渐理解，TypeScript 的重点不是给每个变量写类型，而是把真正影响页面行为的契约表达出来。接口变化时，编译错误会指出哪些页面依赖了旧结构，比运行后才发现某列空白更容易处理。

另一个边界是：TypeScript 的类型检查发生在开发与编译阶段，不能替运行时的响应校验。如果后端返回一个未约定的新状态，把响应声明为某个接口并不会自动把它变正确。界面应能识别未知值，避免把“不认识”默认为“已通过”；接口适配层再负责把服务端值转换成页面明确支持的值。

## 表格页面为什么仍然需要状态管理

管理列表至少同时存在这些状态：查询条件、当前页、每页数量、加载中、选中行、弹窗开关、编辑对象和请求错误。如果全部放进零散变量中，页面很快就会出现互相覆盖。

需要特别区分：

- **服务端状态**：来自接口的用户、房源和预约数据。
- **界面状态**：当前筛选、选中项和弹窗状态。
- **派生状态**：根据数据计算出的按钮权限和显示文本。

服务端数据更新后应重新取得权威结果，或者使用接口返回的新对象更新列表；不能只在页面上改颜色，就假设后端状态已经成功变化。界面反馈必须跟随真实请求结果。

## 分页和筛选需要统一参数契约

分页并不只是两个数字。前端和后端需要约定页码从 0 还是 1 开始，排序字段是否合法，空筛选条件怎样表示，以及总数何时更新。

一个稳定的查询流程可以是：

```text
用户修改筛选条件
  → 页码重置为第一页
  → 组装明确的查询参数
  → 显示加载状态
  → 更新列表和总数
  → 保留当前筛选条件
```

如果筛选后仍停留在原来的高页码，页面可能显示空列表；如果快速输入关键词触发多个请求，较早请求也可能晚于新请求返回，覆盖最新结果。搜索框可以使用防抖，页面也需要识别当前有效请求。

这些看起来是基础问题，却直接决定后台是否稳定。

## 先筛选、再排序、最后分页：顺序就是结果

房源管理页的本地处理顺序很适合拿来理解数据变换：从原始数组筛选出符合条件的记录，复制后排序，再按页码切片；总数取筛选后集合的长度。

用一组**教学价格**看会更直观。假设输入顺序为 90、40、80、30、70、20、60，筛选“价格不超过 60”，按价格升序，每页 2 条：

| 处理步骤 | 得到的价格 |
|---|---|
| 筛选 | 40、30、20、60 |
| 排序 | 20、30、40、60 |
| 第 1 页 | 20、30 |
| 第 2 页 | 40、60 |

如果先取原始第 1 页 90、40，再过滤，就只剩 40；后面的 20 和 30 根本没有机会参与。这不是表格没画好，而是计算顺序错了。接到服务端分页后，同样要让过滤与排序作用于整个候选集合，不能把“当前页排序”误认为“全库排序”。

复制数组还有一个细节：展开运算得到的是新的数组容器，并不会深拷贝内部房源对象。新数组排序不会改动原数组顺序，但修改其中某个对象的属性仍可能影响共享该对象的地方。页面草稿、原始记录和提交结果怎样隔离，要根据实际字段结构决定；不必为了一个简单表单提前引入庞大的状态框架。

## 审核操作需要确定性反馈

房源审核属于会改变业务状态的操作，不能像打开详情一样随意触发。页面至少需要：

1. 明确当前审核对象。
2. 在提交前确认操作和必要原因。
3. 提交期间阻止重复点击。
4. 后端成功后更新权威状态。
5. 失败时保留用户输入并说明原因。
6. 无权限或状态已变化时停止继续操作。

按钮显示“成功”却没有刷新列表，会让用户看到旧状态；先把列表改成通过，再调用接口，则可能在请求失败后制造假状态。更可靠的方式是等待后端确认，并让页面重新获取或使用服务端返回结果。对这里的模拟页面而言，这些是接入真实接口时的验收目标，而不是现有数组操作已经提供的保证。

## Element Plus 解决的是组件，不是设计一致性

Element Plus 提供表格、表单、弹窗和通知等基础组件，但同一种按钮在不同页面使用不同位置、颜色和文案，后台仍然会显得混乱。

项目中的 UI 调整让我理解，设计系统可以从很小的规则开始：

- 主操作、次操作和危险操作使用稳定层级；
- 状态颜色与文案在所有页面保持一致；
- 表格操作列、筛选区和分页位置统一；
- 空状态、加载和错误提示拥有共同模式；
- 表单校验既说明错误，也告诉用户怎样修正。

一致性不只是视觉效果。规则统一后，新页面可以沿用相同结构，开发者也不必重新决定每个按钮应该放在哪里。

## 从管理端代码中学到的事情

后台前端的核心是把业务状态准确映射到界面，再把用户操作安全地交给后端。组件、TypeScript 和 UI 库只是工具；真正决定代码质量的是对象边界、状态流转和接口契约。

EasyHome 的管理端让我第一次系统地把用户、房源、审核和预约放在同一条业务链路中理解。后来再接触更复杂的企业后台时，我会先画出状态和操作关系，再开始写表格和弹窗，而不是先完成页面外观再补业务判断。
