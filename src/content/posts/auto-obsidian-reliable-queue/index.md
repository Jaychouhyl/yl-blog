只处理一个网页时，可以用一段脚本从头运行到结束；但一次导入几十条收藏、多个视频和一整个本地目录后，问题会完全不同。网络可能中断，登录状态可能失效，OCR 或转写可能超时，某一条异常文件也可能让进程提前退出。

上一篇讲的是一条资料怎样变成笔记，这一篇则关心：有一批资料时，其中一条失败了怎么办？如果任务只存在内存里，程序关闭后就无法回答三个基本问题：哪些已经完成，哪些停在处理中，哪些应该重试。Auto Obsidian MD 使用 SQLite 保存任务和状态，为检查与重试提供依据；但状态保存下来，并不代表程序已经实现任意位置的自动断点恢复。

## 队列解决的不是并发，而是生命周期

提到任务队列，很容易先想到多个线程同时工作。并发只是队列可能提供的能力之一，更基础的价值是记录任务生命周期。

先用项目中的状态名称画出常见路径：

```text
pending（等待） → processing（处理） → done（完成）
                      ↘ failed（失败） → 手动重试 → pending
不再处理的任务 → skipped（跳过）
```

状态机不应只是一张展示图，还应该落实为状态转换规则。例如正在运行的任务因程序异常退出后，需要判断是否仍有工作进程负责它，才能决定如何恢复，而不是看见 `processing` 就立即重跑。

这里也要区分概念与实现：当前队列代码有这些状态及对应更新方法，但状态列只是文本字段，单条重试方法会直接把指定记录设回 `pending`，并没有在数据库层完整校验每一次转换。它建立了任务记录的基础，不等于已经拥有严格的状态机引擎。读源码时，方法叫 `retry` 只是线索，真正的行为还得看更新条件。

状态机的基础知识在很多系统中都适用：订单有待支付、已支付和已取消；审批有草稿、审核中和已通过；知识入库则有等待、运行、完成、失败和跳过。只要一个对象会经历多个阶段，就应该明确哪些转换合法。

## 为什么选择 SQLite

SQLite 是嵌入式关系数据库，数据库内容保存在本地文件中，不需要用户额外安装和维护数据库服务。对于单机桌面工具，它提供了几个合适的能力：

- 进程关闭后任务仍然存在；
- 可以按状态、来源和时间查询任务；
- 事务保证一组状态更新共同成功或共同失败；
- 唯一约束可以阻止部分重复记录；
- 备份和迁移比独立数据库服务更简单。

这里需要理解数据库事务的基本含义。假设程序先写入输出文件，再更新任务为完成，如果中间突然退出，就可能出现“文件已经生成，任务仍显示运行中”。更稳妥的设计需要明确哪些动作可以放在同一事务里，哪些跨越文件系统、网络和数据库，无法依靠一个本地事务一次解决。

SQLite 能保证数据库内部的一致更新，但不能自动让网页下载、模型调用和文件写入也具有事务性。这些外部动作仍然需要幂等检查和恢复逻辑。

### 从一条更新语句理解“状态转换条件”

如果只想让等待中的任务进入处理状态，可以用下面的 SQL 理解条件更新。**这是学习示例，不是当前项目的实现，也不是一套完整的多进程抢占方案。**

```sql
UPDATE queue
SET status = 'processing'
WHERE id = ? AND status = 'pending';
```

执行后检查受影响行数：1 表示这次更新找到了满足条件的任务；0 表示任务不存在或已经不处于等待状态，调用方不应把它当成成功领取。再执行一次同样的语句，状态条件已经不成立，也就不会再次成功。

这段 SQL 的重点不是少写一个 `if`，而是把“读取状态再决定更新”收进同一个数据库操作。不过，谁在执行、进程是否存活、领取后崩溃怎么办，都还没有被解决，不能凭这一句就宣布实现了可靠调度。

## 幂等：重复执行不应该制造重复结果

幂等可以简单理解为：同一个有效请求执行一次或多次，最终业务结果保持一致。HTTP 的 GET 通常被设计为幂等操作；知识入库也需要类似性质。

判断重复时可以组合多种信息：

- 规范化后的来源地址；
- 平台内容 ID；
- 本地文件的路径、大小和修改时间；
- 内容摘要或哈希；
- 目标笔记的稳定标识。

只使用标题去重并不可靠，因为不同内容可能同名，同一内容的标题也可能变化。只使用 URL 也不总是可靠，网址可能包含跟踪参数，同一文章还可能有移动版和桌面版地址。因此去重通常需要先规范化，再根据来源特点选择稳定标识。

幂等也不等于“遇到相同记录就永远跳过”。如果提取规则升级，用户可能希望重新生成；如果上一次只完成下载而没有输出笔记，也应该从合适阶段继续。系统需要区分重复、重跑和恢复，而不是把它们都归为一次新的导入。

### 项目已经防住了哪一层重复

当前入队逻辑会先规范化来源，并为 `url` 设置唯一约束；元数据提供 `source_identity` 时，还会先查找这个来源身份。这里的 URL 约束由数据库保证，而元数据身份查询不是一条独立的数据库唯一约束，两者的保证范围不能混为一谈。

输出端还有另一层规则：本地 Markdown 写入器收到已有的 `note_path` 时，会尝试沿用该相对路径；没有已知路径又遇到同名文件，则生成带数字后缀的新文件，以免直接覆盖。因此，这些机制能减少重复入队和部分重跑产生的重复笔记，但并不能保证任何失败时刻重试都只会留下一个文件。

**去重解决“是不是同一个任务”，幂等解决“重复做会不会多出一份结果”。** 两个问题有关，但不是在数据库里加一列 `UNIQUE` 就一起毕业了。

## 假设在写完文件后突然退出

处理管线的关键顺序是：先把任务标成 `processing`，再提取与整理内容、调用写入器，最后把输出路径和 `done` 写回 SQLite。沿着这个顺序，可以推演出几个不同的故障窗口：

| 中断位置 | 可能留下什么 | 恢复前要核对什么 |
|---|---|---|
| 提取过程中 | `processing`，以及部分缓存 | 原进程是否仍在运行，缓存是否完整 |
| 文件写入后、状态更新前 | 文件已存在，队列未记录新路径 | 现有文件是否属于该任务，是否已经被人工编辑 |
| 状态更新后 | `done` 和已记录的输出路径 | 笔记是否仍存在，正文是否完整 |

这张表是按源码顺序做的故障推演，不是已经完成断电测试的报告。特别是第二行：如果此时重新处理，而队列没有保留输出路径，本地写入器可能把原文件视为同名文件，另存一份带后缀的笔记。

多个输出目标也有类似问题。项目的主输出和附加输出依次执行；主笔记已经写成，并不保证后面的 HTML、CSV 或 Notion 写入都成功。一个附加输出失败后，整条任务可能被标为失败，但前面的文件不会因此自动消失。

由此学到的不是“赶紧再加一个数据库”，而是先说清楚恢复语义：目前能够依据记录检查、重试任务，但不能承诺自动续跑到上次中断的精确步骤。核对已有产物后再重试，比一看见红色状态就重新导入整批资料更稳妥。

## 重试只适合处理暂时性失败

并不是所有错误都应该重试。网络超时、临时限流和外部服务短暂不可用，可能在稍后恢复；文件格式不支持、登录凭据缺失和参数错误，重复一百次仍然不会成功。

因此重试策略至少要考虑：

1. 错误是否可能自行恢复。
2. 当前已经尝试了多少次。
3. 两次尝试之间等待多久。
4. 重试是否会产生重复文件或外部费用。
5. 失败信息能否告诉用户下一步怎么处理。

常见的退避策略会逐步增加等待时间，避免大量失败任务持续冲击同一个服务。这是理解重试设计的通用知识，不是本项目已经实现的自动调度策略：当前队列没有专门的尝试次数字段和下一次执行时间，`retry_item` 与 `retry_failed` 的主要工作是把选中任务重新置为等待。

对于当前工具，先保留失败原因、核对已有产物，并允许用户有针对性地重试，比无条件反复运行更有用。凭据缺失时应先处理登录或配置问题；“再试一次”不是所有错误的通用解药。

## 超时是可靠性的一部分

没有超时的网络请求可能长期等待，导致任务一直停留在运行状态。超时太短又会把正常的大文件下载或语音转写误判为失败。

更合理的做法是按操作类型设置边界：普通网页请求、视频下载、OCR、音频转写和模型摘要的合理时间并不相同。同时，界面应区分“仍在处理”和“已经失去响应”，而不是只显示一个无限旋转的图标。

超时发生后还要考虑外部动作是否已经部分完成。例如文件下载到一半时留下临时文件，下次运行不应把它当成完整输入；模型请求超时也不代表服务端一定没有执行，因此涉及计费或写操作时更需要幂等标识。

## 可观察性不只是日志文件

任务表本身就是一种可观察性。用户需要看到当前阶段、已完成数量、失败原因和可以采取的动作。开发日志可以保留堆栈和参数，但界面提示应该回答：发生了什么、哪些内容受影响、是否可以重试、是否需要重新登录或安装依赖。

批量任务至少应提供这些检查入口：

- 按状态查看等待、运行、完成和失败任务；
- 展示当前处理阶段而不只显示总进度；
- 保留失败原因和最近一次尝试时间；
- 允许重试单条任务，而不是重新导入全部内容；
- 能够确认最终 Markdown 是否真实写入目标目录。

中间状态正常不代表最终结果正确。权威验收点仍然是输出文件和任务最终状态，而不是某个下载器返回了成功。

## 从队列设计学到的事情

可靠性并不是企业后台才需要的能力。只要个人工具开始批量处理资料，就会遇到重复、局部失败、超时和恢复。SQLite、状态机和幂等并没有让采集器本身更“智能”，却让工具从可以演示变成可以反复使用。
