SmartX ERP 做 MCP 化时，我最先补上的认识是：MCP 不是“把接口包一层，让模型能调”。接口穿上一件工具描述的外套，并不会自动变成可靠的业务能力。

如果只是为了演示，工具列表能出现、能调通一个接口，似乎就够了。但 ERP 不一样。ERP 的核心不是“查得到”，而是“谁能查、能查多少、查完有没有记录、出了问题能不能追”。

## 先理解 MCP 在解决什么

MCP 可以把工具名称、用途、参数结构和调用结果以统一协议暴露给模型。模型不需要知道每个服务内部有哪些 Controller，只需要根据工具描述选择调用。

一项工具至少需要清楚定义名称、使用场景、输入 schema、稳定输出和错误类型。描述太宽泛，模型会在不合适的场景调用；参数全部是可选字符串，模型就只能靠猜。工具 schema 本质上是一份面向模型的 API 契约，写得含糊，模型也只会很有礼貌地含糊下去。

## 先跑通最小闭环

我最开始做的是 vertical slice：MCP 服务能启动，Spring AI 能注册工具，`/mcp/sse` 能通，`tools/list` 能看到工具，至少一个库存或销售查询工具能返回真实结构。

这个阶段暴露的并不是业务难题，而是工程地基问题。比如参数名要保留，否则模型看到的是 `arg0`；配置要真的被加载；种子用户和权限要能登录；只读聚合服务不要引入无意义的分布式事务。

配置好了和服务真能跑是两回事。任何一个地方没处理好，都会让"工具注册成功"和"业务可用"之间差一大截。

vertical slice 的基础思想，是先证明一条窄链路从入口走到真实结果，再横向增加功能。它比一次定义几十个工具更容易发现协议、身份和配置问题，也能防止“工具列表很热闹，真正能用的只有一个”这种尴尬。

## 不能让所有人共用一个身份

ERP 场景里，最危险的方案是让所有 MCP 调用都退回到一个共享 bot。

销售、采购、财务、管理员看到的数据本来就不同。如果 AI 调工具时不带员工身份，模型看到的就不是这个员工自己的业务视角，而是一个系统账号视角。这不是前端隐藏按钮能解决的问题，必须在后端调用链路里解决。

代码通过 per-user MCP Key 找到员工身份，再继续传递角色权限和 dataScope。顺着这条链路读下来，我才把“接入一个工具”与“允许某个人使用这个工具”区分开。

这里对应的是最小权限原则：认证回答“你是谁”，角色权限回答“你能做什么”，数据范围回答“你能看到哪些记录”。前端隐藏按钮只是体验控制，真正的权限判断必须发生在服务端，并延续到 MCP 调用和下游查询中。

## 沿着一次库存查询检查身份

以库存总览工具 `inventory_page_overview` 为例，它看起来只是一项分页查询，实际却要经过几道不同的检查。

外部 MCP 客户端先用 `X-MCP-API-Key` 进入服务。过滤器查询有效 Key，取出对应的用户 ID 和用户名；缺少 Key、Key 无效或已经撤销，都返回 401。这里确认的只是调用者身份，还不能据此认定他有库存查询权限。

工具权限表把这项查询映射到 `scm:inventory:list`。执行时还要检查员工是否拥有这个权限；缺少权限应返回 `PERMISSION_DENIED`，而不是一个空库存列表。两种结果不能混用：前者是“不允许查”，后者才可能是“允许查，但条件下没有数据”。

请求继续向 SCM 服务发送时，Feign 拦截器取得该员工的令牌，并补充角色、部门和数据范围。一个值得注意的分支是：**已有员工身份，但令牌签发失败时，代码直接报错，不退回 bot**。否则认证服务一出故障，员工反而可能得到系统账号的视角，失败处理就变成了权限升级。

2026-07-26 的归档台账记录过一组对照：`sales01` 通过 MCP 获得的数据与其 UI 数据一致，撤销 Key 后返回 401。这能支撑当时那组身份对照和撤销测试，不能外推成所有角色、所有工具都已经覆盖；本文也没有重新启动服务复测。

身份正确以后，还要看结果有没有被正确理解。这个工具默认每页 10 条、最多 100 条，返回 `records` 和 `totalRow`。如果某次返回 10 条记录、总数为 37，那么这 10 条只是当前页；模型可以总结“这一页有哪些物料”，不能把它们当成全部库存计算总量。这是根据分页契约举的例子，不是项目实际库存数字。

这条查询让我学到，可靠回答至少依赖两份契约：权限契约限定“谁能看”，结果契约限定“这些数据能说明什么”。缺了后者，即使权限完全正确，回答仍可能把一页数据说成整个仓库。

## 内部调用也要有边界

MCP 服务要调用下游微服务，下游又依赖登录态和数据范围。这里不能靠"都在内网"这种松散假设。

内部代签发接口使用 HMAC、时间戳校验和 fail-closed 策略。读这部分代码时，我关注的是调用方凭什么被信任：权限问题很多时候不会表现成 401 或 500，而是返回了“不该返回的数据”。正常的 HTTP 状态码，恰好可能把问题藏起来。

HMAC 的基础思路是调用双方共享密钥，对约定字段计算消息认证码。当前实现纳入签名的是调用来源、时间戳、HTTP 方法和请求路径；接收方重新计算并比较，可以验证这些字段以及调用方是否持有密钥。请求正文和 nonce 尚未进入签名，所以这里不能把“路径签名通过”写成“整个请求内容都未被修改”。

时间戳校验把可接受窗口限制在约五分钟，但不能单独阻止窗口内重放。若后续内部写操作也采用这套机制，还需要把正文摘要纳入签名，并结合 nonce 或请求 ID、去重存储、密钥轮换与时钟偏差策略完善边界。

`fail-closed` 表示验证不完整时默认拒绝，而不是“先放行，日志以后再看”。在权限链路里，宽容往往不是温柔，而是数据泄露的另一种写法。

## 写操作要保守

查询工具跑通后，很自然会想到：能不能让 AI 创建订单、审批、付款、发货？

我的判断是：ERP 里的 AI 写操作必须先从草稿开始。AI 可以帮助准备销售单、采购单或分析材料，但审批、付款、发货、结算这种不可逆动作，应该留在原有人工流程里。

这不是技术做不到，而是责任边界不该这么设计。

读工具和写工具的风险不同。查询失败通常影响一次回答，付款或审批重复执行则会改变真实业务。写操作至少要考虑幂等键、草稿状态、人工确认、权限复核和审计记录。模型可以准备动作，但最终提交应保持确定性的业务校验。

## 从 MCP 接入中学到什么

工具不是越多越好，关键是每个工具能不能被模型理解，能不能按正确身份调用，返回结构是否稳定，失败时能不能解释。工具数量属于展示指标，正确调用率才更接近工程指标。

后续我会做工具质量评估：哪些工具被模型频繁误用，哪些描述需要重写，哪些权限过滤还不够细，哪些返回结果应该更适合模型总结。

MCP 在 ERP 里最重要的价值，不是让 AI 看起来更厉害，而是让 AI 在受控边界内进入业务流程。
