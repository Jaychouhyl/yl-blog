SmartX ERP 做 MCP 化时，最容易被误解的一点是：MCP 不是"把接口包一层，让模型能调"。

如果只是为了演示，工具列表能出现、能调通一个接口，似乎就够了。但 ERP 不一样。ERP 的核心不是"查得到"，而是"谁能查、能查多少、查完有没有记录、出了问题能不能追"。

## 先跑通最小闭环

我最开始做的是 vertical slice：MCP 服务能启动，Spring AI 能注册工具，`/mcp/sse` 能通，`tools/list` 能看到工具，至少一个库存或销售查询工具能返回真实结构。

这个阶段暴露的并不是业务难题，而是工程地基问题。比如参数名要保留，否则模型看到的是 `arg0`；配置要真的被加载；种子用户和权限要能登录；只读聚合服务不要引入无意义的分布式事务。

配置好了和服务真能跑是两回事。任何一个地方没处理好，都会让"工具注册成功"和"业务可用"之间差一大截。

## 不能让所有人共用一个身份

ERP 场景里，最危险的方案是让所有 MCP 调用都退回到一个共享 bot。

销售、采购、财务、管理员看到的数据本来就不同。如果 AI 调工具时不带员工身份，模型看到的就不是这个员工自己的业务视角，而是一个系统账号视角。这不是前端隐藏按钮能解决的问题，必须在后端调用链路里解决。

所以我设计了 per-user MCP Key 方案、员工身份映射、角色权限和 dataScope 透传——这比堆工具数量更重要，也是我花时间最多的地方。

## 内部调用也要有边界

MCP 服务要调用下游微服务，下游又依赖登录态和数据范围。这里不能靠"都在内网"这种松散假设。

我自己实现了内部代签发和 HMAC 方案：签名路径、时间戳、fail-closed。不是为了显得复杂，而是权限问题很多时候不会表现成 401 或 500，而是返回了"不该返回的数据"。这种 bug 更危险，也更难发现。有了签名边界，排查起来至少有迹可查。

## 写操作要保守

查询工具跑通后，很自然会想到：能不能让 AI 创建订单、审批、付款、发货？

我的判断是：ERP 里的 AI 写操作必须先从草稿开始。AI 可以帮助准备销售单、采购单或分析材料，但审批、付款、发货、结算这种不可逆动作，应该留在原有人工流程里。

这不是技术做不到，而是责任边界不该这么设计。

## 做完之后的想法

工具不是越多越好，关键是每个工具能不能被模型理解，能不能按正确身份调用，返回结构是否稳定，失败时能不能解释。

后续我会做工具质量评估：哪些工具被模型频繁误用，哪些描述需要重写，哪些权限过滤还不够细，哪些返回结果应该更适合模型总结。

MCP 在 ERP 里最重要的价值，不是让 AI 看起来更厉害，而是让 AI 在受控边界内进入业务流程。
