微服务项目最容易制造一种错觉：只要每个模块能够编译，系统就应该可以启动。实际上，编译只证明源码能够生成产物，不能证明运行环境已经成立。

SmartX ERP 包含 Gateway、Auth、SCM、Sales、Finance、RAG 和 MCP 七个服务，同时依赖 MySQL、Redis、Nacos、Neo4j、Seata 和 RocketMQ。任何一个服务在 IDEA 中启动，都隐含了一组前置条件：环境变量是否存在，Nacos 是否可访问，对应配置是否已经发布，数据库和缓存是否可用，服务使用了哪个 profile，依赖服务是否已经注册。

当这些条件没有被统一管理时，错误会表现得非常分散：认证服务可能提示密钥缺失，财务服务可能在初始化数据源、Seata 或 MQ 时长时间没有完成，网关可以启动却把登录请求返回 404，RAG 服务能够编译却无法建立完整调用链。若只盯着最后一条异常，很容易把环境问题误判为业务代码问题。

## 先把“运行事实”拆开

一个服务是否可用，至少需要回答四个问题：

1. **配置从哪里来**：本地文件、环境变量还是 Nacos。
2. **依赖是否就绪**：数据库、缓存、注册中心和消息系统是否健康。
3. **服务是否完成启动**：端口监听不等于应用已经通过健康检查。
4. **业务入口是否可达**：Gateway 路由、认证和下游调用是否真实连通。

`.env.example` 只应该描述变量名称和配置方式，不能保存真实密码；真实 `.env` 应保持本地私有。Nacos 负责可共享的开发配置，关键密钥仍由环境变量注入。IDEA 和命令行需要读取同一套变量和 profile，否则“命令行能跑、IDEA 不能跑”会长期重复。

## 为什么不能为了启动简单就合并服务

当一个毕业设计需要同时启动多个服务时，最直接的冲动是删除模块或合并服务。但 SmartX 的销售、供应链、财务、智能决策和 MCP 本来就具有不同职责。为了减少启动项而破坏领域边界，只是把运行问题藏进一个更大的单体。

更合理的处理是保持边界，同时降低环境的不确定性：

- 明确七个服务及端口。
- 明确基础设施启动顺序。
- 关键配置缺失时快速失败。
- 使用 Actuator 判断服务是否真正健康。
- 使用 Gateway 业务请求验证跨服务链路。
- 在 IDEA 启动异常时，用打包后的 JAR 做交叉验证。

JAR 可以启动而 IDEA 失败，通常说明运行配置不同；JAR 和 IDEA 都失败，才更可能是源码、配置中心或基础设施问题。这种对照比反复修改代码更有效。

## 一个 404 暴露的配置链

Gateway 曾经能够启动，但登录接口返回 404。最终原因不是认证服务没有实现登录，而是 Gateway 没有导入对应的 Nacos 配置。路由定义存在于配置中心，应用却没有加载它。

修复不是在 Controller 里补接口，而是在启动配置中明确导入 Gateway 的开发配置。随后又发现 `localhost:5173` 可以访问，而 `127.0.0.1:5173` 被 CORS 拒绝。两个地址都指向本机，但对浏览器同源策略来说是不同来源，因此白名单需要明确包含两者，并在生产环境改为真实域名。

这类问题说明，微服务排查不能只沿着 Java 调用栈向下走，还要沿着“浏览器 → 网关 → 配置中心 → 服务注册 → 下游服务”检查整条路径。

## 可复现环境比一次启动成功更重要

一次手工启动成功并不意味着问题已经解决。真正的完成标准应该是：

- 新环境知道需要哪些变量。
- 服务知道从哪里获取配置。
- 基础设施具备健康检查。
- 启动顺序可以解释。
- 每个服务有独立健康入口。
- 最终业务请求能够穿过 Gateway。

对单人毕业设计来说，这种整理看似增加了文档和配置工作，实际上减少了后续每一次联调的随机性。微服务的价值来自边界，微服务的成本来自运行条件；只有让运行条件可见、可检查、可复现，服务拆分才不会变成启动负担。

后续如果继续生产化，仍需补充配置版本、密钥轮换、资源限制、启动诊断、滚动发布和故障恢复。当前本地环境解决的是“能够稳定开发和演示”，不是生产部署的全部问题。
