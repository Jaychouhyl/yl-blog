SmartX ERP 的前端、Spring Boot 后端、Neo4j 图谱、RAG 助手和 MCP 工具层让我第一次完整面对一个系统从“功能能点”到“长期能用”的距离。这篇不准备逐页罗列改了什么，而是记录前端代码让我理解的一件事：页面外观只是入口，真正的工程问题藏在数据、状态和交互规则里。

前端优化不是一次"把页面做漂亮"的任务。更准确地说，是把一个功能很多、风格不够统一的后台，往真正的企业运营控制台方向收。

我最初关注的是视觉问题：页面粗糙、卡片和阴影有点随意、不同模块像从不同模板里拼出来。但继续往下做才发现，真正的问题不是配色，而是系统缺少一致的表达规则。给所有卡片加阴影并不会自动产生“高级感”，最多能证明 CSS 的 `box-shadow` 工作得很勤快。

## 设计系统首先是一组约束

设计系统常被误解为颜色表和组件展示页。对企业后台来说，它更像一份界面契约：同一种状态怎样表达，同一级操作放在哪里，页面在加载、为空和失败时分别如何回应。

最基础的 design token 可以包含：

```text
颜色：背景、正文、弱文本、边框、成功、警告、危险
尺寸：间距、圆角、控件高度、内容宽度
层级：标题、正文、说明、表格密度
反馈：loading、empty、error、disabled
```

token 的价值不是少写几个十六进制颜色，而是让不同页面共享同一套决策。以后调整品牌色或信息密度时，修改规则比逐页寻找散落样式更可靠。

## 高级感不是装饰

后台系统的高级感，来自稳定和克制。

表格密度要统一，按钮层级要稳定，状态色要有明确语义，弹窗不能每个页面一套结构，空态不能只留一片空白。用户每天要在这里查库存、看订单、看财务、问 RAG、点知识图谱，页面应该帮助他快速判断状态，而不是让他被装饰吸引。

所以这轮优化最重要的不是改某一个页面，而是把页面收回到 tokens、组件和布局规则里。颜色、间距、表格、Tag、Alert、Dialog、Drawer 都尽量服从同一套语言。

## 真实数据会暴露设计稿看不到的问题

静态页面很容易"看起来不错"。一接真实后端，问题会立刻出现。

比如客户和供应商字段出现乱码，图谱返回 0 实体，表格数据为空，接口代理和 CORS 出问题，Element Plus 在某些交互下有 warning。这些问题不是设计稿能提前发现的，也不是改几行 CSS 能解决的。

排查不能停在页面，还需要追到接口响应、服务端和 Cypher 查询那层。企业后台的前端优化必须尽早进入真实数据环境——真实数据里的坏字符、空状态、异常接口和慢响应，才是后台系统真正的日常。

这里让我补上了“接口契约”的基础理解。前端依赖的不只是接口地址，还依赖字段名称、类型、空值规则、枚举范围和错误结构。接口返回 200 但把数字变成字符串，页面仍可能安静地出错；这种安静通常比直接报错更难排查。

因此联调时至少要检查成功响应、空集合、错误结构、超时、重复提交，以及页面是否仍对应服务端权威状态。

## 把乱码藏起来，不等于把数据修好了

代码中有一个很小的展示函数 `cleanDisplayText`：先处理空值与空白，再把整段问号或部分连续坏字符替换成回退文本。采购、库存和财务页面会在展示名称等字段时使用它。

以这段函数的规则举例，空字符串或 `???` 可以显示为 `-`；正常名称只会整理多余空白。页面不再出现一长串问号，确实容易读一些，但函数并没有办法从问号里还原原来的供应商名称。它解决的是展示退化，不是信息恢复。

2026-07-26 的归档台账也把这两件事分开了：展示层增加清洗和回退，SQL、导入流程与数据库字符集的根因仍需继续核查。不能因为页面变干净，就在总结里写“编码问题已经彻底修复”。

这让我认识到数据处理有两个方向：读取时让用户看得懂，写入和导入时保证数据本身正确。展示函数只返回一个字符串，不代表数据库、搜索索引或导出文件已经随之修正；这些出口仍要分别核对。把不认识的字换成横线，和真正知道它原来是什么，显然不是一回事。

## 空态也是系统能力

知识图谱页面的 0 实体状态给我印象很深。

没有空态时，用户看到的只是空白。空白不会解释任何东西。更好的空态应该告诉用户：当前没有数据，可能是同步任务未跑、Neo4j 没连上、筛选条件太窄，或者确实还没有实体。它还应该告诉用户下一步能做什么。

空态不是插画和文案，而是系统对当前结果的解释能力。零条记录本身未必异常；成功查询但没有结果，与请求失败、无权限读取，需要不同的提示。

从代码角度看，一个数据区域至少包含 `idle → loading → success / empty / error`。如果把它们都压缩成一个 `loading` 布尔值，页面很容易在请求失败后显示空白，或者把“没有结果”误写成“系统异常”。显式状态虽然多写几行，却能让代码和用户看到同一件事。

## AgentDock 应该是工具，不是主角

项目里的智能助手入口 AgentDock 很容易被做得很显眼，因为“AI 助手”听起来像亮点。

但在 ERP 里，主角应该是业务。助手应该随时可用，但不能挡住表格操作列，不能压过页面信息，也不能让用户觉得每个流程都必须先问 AI。

越智能的入口，越需要克制。它最好像一把顺手的工具，而不是一直抢镜的新功能。

这个取舍也属于信息架构。高频、确定性的订单和库存操作应该留在主流程；低频、探索性的问答适合作为辅助入口。不能因为一个功能用了模型，就自动获得首页中央的永久座位。

拖动位置的代码还给了我一个更具体的例子。`clampDockPosition` 会根据视口、入口尺寸和边距，限制最终坐标。窗口变小后，之前保存的坐标不一定仍然有效，所以“读回原位置”之后还得重新约束。

假设视口宽 1280px、入口宽 72px、边距 12px，那么右侧可用的最大横坐标是 1196px。保存过的 1600px 就应该收回到这个范围内。这是对函数规则的教学演算，不是项目界面尺寸的实测值。它说明持久化保存的是用户偏好，不是永远可用的布局结果。

但坐标不越界也只证明入口还在屏幕内，不能证明它没有盖住“保存”按钮。因此数学约束适合自动化检查，是否遮挡业务操作仍要回到实际页面，两种检查各管一件事。

## 从前端代码中学到什么

我对前端的理解从“页面好不好看”转向“系统能不能正确解释状态”。UI 不是给截图服务的，它要承接真实数据、坏数据、权限、加载、错误、空态和复杂操作。

以后再做后台，我会先整理对象、状态和操作，再设计组件；先接真实数据，再判断页面是否稳定；先把 loading、empty、error 和 disabled 补齐，再讨论动画是否优雅。毕竟用户可以接受按钮没有渐变，通常不太能接受付款后页面仍然说“暂无数据”。
