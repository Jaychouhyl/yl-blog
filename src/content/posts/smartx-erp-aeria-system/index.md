企业后台的 UI 问题很少来自某一个颜色。筛选栏字体不一致、按钮位置漂移、详情弹窗无法滚到底、暗色模式出现浅色断层、窄屏时操作按钮被裁切，这些现象看似分散，背后往往是同一个原因：页面没有共享稳定的视觉和布局契约。

SmartX 前端最初也经历了逐页修补。销售页修圆角，采购页调间距，库存页重新分配字段，财务页再单独处理按钮。短期内每个问题都能变好，长期却会形成更多选择器和覆盖规则。

## 为什么没有切换 React

当页面越来越难统一时，更换框架或组件库看起来很有吸引力。但 SmartX 已经拥有完整的 Vue 3、Vue Router、Pinia 和 Element Plus 业务实现。切换 React 会同时重写路由、权限、表单、表格、弹窗和大量业务交互，UI 收尾会演变为全项目迁移。

真正缺少的并不是新的运行时，而是：

- 统一字体和字号。
- 可解释的间距、圆角和阴影。
- 筛选栏字段长度规则。
- 单据详情与状态组件。
- 亮暗主题 token。
- 响应式和验收基线。

因此 Element Plus 继续负责成熟行为，项目自己的组件层负责视觉和业务组合。

## 先建立可重复的 ERP 模式

页面中长期重复的结构包括：

- Page / PageHero
- FilterBar / SearchToolbar
- MetricCard
- WorkspaceTabs
- DocumentHeader / DocumentShell
- InfoRows / DetailGrid
- DrawerForm / ConfirmDialog
- FloatingToast
- DraftDock / Composer
- ChartPanel / GraphCanvasShell

抽取这些组件不是为了增加组件数量，而是让“页面顶部怎么排”“筛选栏如何响应”“单据状态放在哪里”“详情如何滚动”只决定一次。

抽象应该由重复且稳定的规则驱动。只出现一次的页面结构可以先留在页面里；当多个业务模块共享布局、状态和交互契约时，再提取组件。过早抽象很容易得到一个参数很多、谁都不敢改的万能组件——它确实很通用，主要因为没人真正用得明白。

视觉规则也不能继续散落在页面 CSS 中。设计令牌把颜色、间距、字号、圆角和层级变成带语义的变量。组件依赖的是 `surface`、`text-muted`、`space-md` 这样的角色，而不是某个页面碰巧好看的十六进制颜色。主题切换时改变语义值，组件本身不需要重新猜一次设计意图。

销售筛选栏先作为基线：输入框、选择器和按钮使用统一高度、字体、圆角和焦点环；字段宽度按业务内容分配；查询与重置保留明确动作区；中等宽度提前换行。基线稳定后再推广到采购、库存、财务、客户、供应商、人员和 MCP。

## 从一个筛选栏看组件该管到哪里

`AeFilterBar` 的输入包含字段描述 `fields`、当前值 `modelValue` 和查询中的 `loading`。字段变化时，组件用原值加上当前字段构造新对象，再发出 `update:modelValue`；提交和重置分别发出 `submit` 与 `reset`。

这个分工很重要：组件知道怎样排输入框、怎样表达查询中，但不知道应该请求销售接口还是采购接口，也不知道重置后是否要立即查询。尤其是“重置”按钮，当前组件只是发出事件，并没有自动清空全部字段。父页面需要决定默认状态、页码和后续请求；如果误以为按钮替自己做完了这些事，组件看起来一样，业务行为仍然会不同。

输入类型也不能只看 TypeScript 声明。代码从原生输入框读取的是 `target.value`，即使字段显示为数字输入，事件交给父页面的值仍是字符串。金额、数量是否转换成数字，以及空字符串表示“不筛选”还是零，都需要在业务边界明确处理。这不是再增加一种通用 prop 就能替所有页面决定的。

我从这个小组件里学到的不是“组件越通用越好”，而是把两类变化隔开：高度、间距、焦点样式由组件统一；查询参数、默认条件和接口请求仍由业务页面决定。统一外观不需要把所有业务也挤进同一个文件。

## 真实宽度比浏览器宽度更重要

左侧导航一展开，同一个浏览器窗口留给筛选栏的空间就会变小。组件若只按视口宽度决定排布，即使命中了媒体查询，也可能容不下输入框和按钮。

当前 ERP 内的 `AeFilterBar` 已经使用容器查询：外壳声明 `container-type: inline-size`，内部按自己的可用宽度改变排布。关键不是把按钮再压窄一点，而是让布局规则跟随组件实际得到的空间。

源码中，容器不超过 900px 时字段区改为两列；不超过 760px 时动作区随整体网格进入单列布局；不超过 520px 时字段改为一列，动作区允许换行。这些数字是当前组件规则，不是所有页面的通用最佳断点，也不能证明所有业务筛选栏都已经采用该组件。

这让我重新理解了组件契约。它不只是一组 props，还包括插槽、事件、空状态、加载状态、错误状态和可用宽度。至于怎样证明这些规则在业务页面里成立，[第 09 篇的 1066px 裁切案例](../smartx-erp-validation-evidence/)会继续讨论侧栏状态、测试数据和回归条件。

## 暗色模式不是颜色取反

暗色问题曾表现为页面上半部分已经变暗，下半部分卡片或弹层仍然发亮。原因包括主题变量只作用于局部根节点、弹层挂载到 `body` 后没有继承、图表和表格仍使用硬编码颜色。

解决方式是让主题 token 进入页面根节点和 body 作用域，弹层、表格、筛选栏、图谱和 RAG 使用相同的层级关系。成功、警告、风险仍保留自己的语义色，但饱和度和背景对比需要适应暗色。

## Aeria Studio 为什么采用开放代码

ERP 内部组件层稳定后，复用能力被整理为独立的 Aeria Studio。它没有只提供不可修改的 npm 包，而是采用类似开放代码的模式：

- Registry 描述组件、文件和依赖。
- CLI 将源码安装进业务项目。
- 默认不覆盖本地修改，显式参数才允许替换。
- Studio 提供组件现场、源码目录、主题和业务 Blocks。
- ERP 运行时不依赖 Studio 服务。

这种方式允许业务项目直接拥有组件源码，同时保留统一目录和差异检查入口。它便于深度定制，但没有消除升级成本，只是把合并上游变化的责任交给了使用方。

CLI 的实际行为能说明这个取舍：目标文件已存在时默认跳过，只有显式使用 `--overwrite` 才替换；`diff` 可以检查本地文件与 Registry 的差异。假设业务项目已经修改了某个组件，上游后来修复一个问题，再次安装并不会自动把两边改动安全合并。默认跳过保护本地工作，同时也可能让上游修复没有进入项目；强制覆盖则可能丢掉业务改动。因此更新前要比较差异、决定如何合并，再回到业务页面验证。

依赖同样需要分开看：CLI 会解析 Registry 条目之间的依赖并写入相关源码，但 npm 包依赖只是输出安装提示，不等于已经自动装好。文件落盘、依赖齐全和页面可用，是三个不同的完成条件。

2026-07-26 的归档材料记录 Aeria 本地形成了 51 个组件、5 个 ERP Blocks、5 套主题、Registry、CLI 和文档站；其中大量内容在当时仍是本地工作区状态，不能直接写成远端正式版本已经全部发布。本文核对的是本地实现与归档，不把这些数字当成今日的重新清点结果。

## 设计系统的完成标准

设计系统不是建一个 token 文件，也不是组件目录数字增长。它应该让真实页面在以下条件下仍然稳定：

- 长名称、空数据、坏数据和错误状态。
- 亮色、暗色和不同桌面宽度。
- 抽屉、弹窗、Toast 和悬浮助手。
- 用户权限不同导致的按钮增减。
- 后端慢响应和 RAG 流式输出。

从页面补丁走向组件契约，真正减少的是未来返工，而不是当下 CSS 行数。

设计系统的价值还可以通过变化成本判断：修改一个 token 或基础组件后，有多少页面能获得一致结果，又有多少页面需要额外覆盖。如果一次主题调整仍然要搜索几十个硬编码颜色，说明目录虽然像设计系统，代码还没有真正依赖它。

## 从组件体系中学到什么

Aeria 的整理过程让我更关注组件边界是否清楚：重置事件不能冒充业务已经重置，数字输入不能冒充数值已经规范化，安装命令成功也不能冒充依赖与升级问题全部解决。把这些约定说清楚，比再多抽出几个小组件更有用。

设计系统最终提供的不是一批更漂亮的按钮，而是一套更少依赖临场发挥的工程约定。页面仍然会提出新问题，但至少不用每次都从圆角大小开始重新开会。
