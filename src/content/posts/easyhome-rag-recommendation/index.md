自然语言需求被整理后，系统仍然要回答一个核心问题：哪些真实房源最符合这些条件？数据库可以精确筛选价格、面积和户型，却很难直接处理“适合居家办公”“周围比较安静”这样的语义描述。

EasyHome 使用 RAG 和向量检索连接自然语言与房源知识。我对这部分的理解主要来自后期阅读团队代码和项目材料。这里更值得学习的不是调用模型接口，而是结构化数据、向量索引、召回结果和生成回答怎样各自承担职责。

## Embedding 是语义检索的表示方式

Embedding 将文本转换为一组数值向量。语义相近的文字通常在向量空间中距离更近，因此“适合老人居住”和“小区安静、配套电梯”即使没有完全相同的关键词，也可能被检索到。

向量相似度常见计算方式包括余弦相似度和欧氏距离。它们比较的是向量位置，不是直接理解文本事实。相似度高只能说明内容可能相关，不能证明房源一定满足条件。

这也是为什么向量检索适合候选召回，而不适合作为最终业务判断。价格是否低于预算、房源是否已审核和是否下架，仍应读取权威字段。

## pgvector 让向量靠近业务数据

pgvector 是 PostgreSQL 的向量扩展，可以在关系型数据库中保存向量并执行相似度查询。对于房源系统，这种方式的一个优势是向量结果能够继续与房源表、审核状态和区域条件组合。

这里需要区分“数据库具备组合能力”和“项目当时已经完成组合”。EasyHome 当前代码会先生成查询向量，在 `houses_vec` 中按 `<->` 距离取前若干房源 ID，再回表读取房源；普通房源列表则另有价格、面积、户型等条件查询。也就是说，现有 RAG 主链路证明了向量召回，但还没有把下面这些硬条件直接合并进同一条向量查询。

例如可以先用 SQL 限制：

```text
审核通过
AND 当前可用
AND 总价 <= 用户预算
AND 区域在可接受范围
```

再在剩余候选中按语义相似度排序，才可以避免“语义很像但已经下架”的记录仅凭向量分数进入最终推荐。这是从现有实现继续向前推导出的改进方案，不是把尚未接通的过滤能力写成项目既成结果。

向量索引需要在速度和召回率之间取舍。数据量较小时精确检索足够，数据量增大后可以使用近似索引提高速度，但必须通过样本验证是否漏掉重要候选。

## 向量什么时候需要更新

房源描述、价格、状态和周边信息都会变化。并不是每个字段变化都必须重新生成向量：价格适合结构化筛选，描述内容变化才更可能影响语义表示。

代码需要明确：

- 哪些字段组成向量文本；
- 新增或修改房源时怎样生成向量；
- 房源下架时向量记录如何失效；
- 模型版本变化后是否需要重新计算；
- 生成失败时房源能否继续进入普通搜索。

向量不是一次生成后永久有效的附件，而是由源数据派生出的索引。源数据与向量版本之间需要建立可追踪关系。

## RAG 不应该把房源事实交给模型记忆

RAG 的基本思路是先检索，再把材料交给模型生成回答。对房源推荐而言，上下文可以包含候选房源的权威字段、相关描述和知识材料。

```text
用户需求
  → 结构化过滤
  → 向量召回
  → 候选去重与排序
  → 组织房源事实和知识上下文
  → 模型生成推荐说明
```

模型负责把条件与房源信息组织成自然语言，但不应自行创造价格、地址、面积和可用状态。重要字段最好以结构化形式传递，并在回答后继续由前端使用原始房源对象渲染卡片。

这样即使模型漏写某个字段，详情页面仍然读取数据库；即使模型说法与房源事实冲突，也可以根据房源 ID 回到权威记录验证。

## 通用知识与房源数据需要区分

“朝南采光通常较好”属于通用知识，“某套房朝南”属于具体房源事实。两类信息都可能进入检索，但可信来源和更新方式不同。

如果上下文没有标明类型，模型可能把通用建议误写成某套房的真实属性。更清晰的组织方式是分别提供：

- 房源结构化事实；
- 房源描述和周边材料；
- 通用购房知识；
- 用户已经确认的偏好。

回答也应区分“数据表明”“材料描述”和“一般建议”。这比简单要求模型“不要幻觉”更可执行。

## 召回、排序与生成是三个评价阶段

推荐效果不能只用最终回答看起来是否流畅来判断。

1. **召回阶段**：符合用户需求的房源是否进入候选集合。
2. **排序阶段**：更匹配的房源是否排在前面。
3. **生成阶段**：理由是否忠于候选事实并表达清楚。

召回漏掉正确房源，模型无法补救；排序错误会让次要候选占用上下文；生成阶段则可能遗漏条件或夸大事实。分阶段记录输入输出，才能判断问题出现在哪里。

固定评测可以同时检查硬条件命中、候选覆盖、排序位置、引用事实和回答准确性。只让人主观判断“这段推荐不错”，很难在模型或索引变化后发现退化。

## 推荐系统仍然需要业务闭环

一段推荐回答只有连接到房源详情、收藏、预约和状态检查后，才真正进入业务流程。模型生成的房源名称不应该由前端模糊搜索，而应携带稳定房源 ID；下架或无权限访问时，页面也必须给出确定反馈。

推荐入口降低了查找成本，但不能绕过审核和权限。RAG 是新的查询方式，不是新的数据权威来源。

## 从 RAG 链路中学到的事情

向量检索处理语义相似，结构化筛选保证硬条件，模型负责组织表达。把这三层混成一个模型请求，虽然代码更短，却难以验证和纠错。

EasyHome 让我理解，AI 功能真正的工程量在模型调用之外：数据怎样进入索引、什么时候更新、候选怎样过滤、回答怎样回到真实房源。下一篇将从用户等待体验出发，整理 SSE 与 Kafka 分别解决什么问题，以及异步处理为什么仍然需要最终状态验证。
