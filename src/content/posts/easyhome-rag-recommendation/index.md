自然语言需求被整理后，系统仍然要回答一个核心问题：哪些真实房源最符合这些条件？数据库可以精确筛选价格、面积和户型，却很难直接处理“适合居家办公”“周围比较安静”这样的语义描述。

EasyHome 使用 RAG 和向量检索连接自然语言与房源知识。我对这部分的理解主要来自后期阅读团队代码和项目材料。这里更值得学习的不是调用模型接口，而是结构化数据、向量索引、召回结果和生成回答怎样各自承担职责。以下按文末固定版本核对，当前实现与改进方案分别说明；没有把源码阅读当成模型效果或数据库运行验收。

## Embedding 是语义检索的表示方式

Embedding 将文本转换为一组数值向量。语义相近的文字通常在向量空间中距离更近，因此“适合老人居住”和“小区安静、配套电梯”即使没有完全相同的关键词，也可能被检索到。

向量相似度常见计算方式包括余弦相似度和欧氏距离。它们比较的是向量位置，不是直接理解文本事实。相似度高只能说明内容可能相关，不能证明房源一定满足条件。

这也是为什么向量检索适合候选召回，而不适合作为最终业务判断。价格是否低于预算、房源是否已审核和是否下架，仍应读取权威字段。

## pgvector 让向量靠近业务数据

pgvector 是 PostgreSQL 的向量扩展，可以在关系型数据库中保存向量并执行相似度查询。对于房源系统，这种方式的一个优势是向量结果能够继续与房源表、审核状态和区域条件组合。

这里需要区分“数据库具备组合能力”和“项目当时已经完成组合”。EasyHome 当前代码会先生成查询向量，在 `houses_vec` 中按 `<->` 距离取前若干房源 ID，再回表读取房源；聊天服务传入的召回数量为 5，普通房源列表则另有价格、面积、户型等条件查询。也就是说，现有 RAG 主链路证明了向量召回，但还没有把下面这些硬条件直接合并进同一条向量查询。

例如可以先用 SQL 限制：

```text
审核通过
AND 当前可用
AND 总价 <= 用户预算
AND 区域在可接受范围
```

再在剩余候选中按语义相似度排序，才可以避免“语义很像但已经下架”的记录仅凭向量分数进入最终推荐。这是从现有实现继续向前推导出的改进方案，不是把尚未接通的过滤能力写成项目既成结果。

这里的 `<->` 是 L2 距离，越小越靠前，并非一个越大越好的“匹配分”。算子含义可查 [pgvector 查询说明](https://github.com/pgvector/pgvector#querying)。所读查询没有相关性阈值，因此“最近的五个”也可能只是“不相关数据里相对近的五个”。

上面的审核与可用性条件属于业务设计，不是可以直接粘贴的现有表字段：所读 `House` 实体没有一个统一的审核状态属性，接入时还需确定发布记录、房源记录和查询权限各自负责什么。

向量索引需要在速度和召回率之间取舍。数据量较小时精确检索足够，数据量增大后可以使用近似索引提高速度，但必须通过样本验证是否漏掉重要候选。

## Top-K 之后再过滤，为什么可能少掉正确答案

用一个**教学候选集**说明：预算上限为 200 万，按语义距离排列的前四套房如下，暂取 Top-3。

| 候选 | L2 距离 | 总价 | 是否满足预算 |
|---|---|---|---|
| A | 0.10 | 260 万 | 否 |
| B | 0.20 | 240 万 | 否 |
| C | 0.30 | 220 万 | 否 |
| D | 0.40 | 180 万 | 是 |

先取前三个再过滤，结果为空；先按预算过滤再比较距离，D 就有机会进入结果。因此，事后过滤虽然能剔除不合格项，却不一定补回被 Top-K 截断的合格候选。扩大召回量可以缓解，但也不是完整替代硬条件过滤的方法。

再往下读，还会遇到一个普通数据库问题：向量查询返回有距离顺序的 ID 列表，服务随后通过批量 ID 查询取得房源对象。**按一组 ID 查询，不等于自动保留这组 ID 的顺序**。所读服务没有显式按召回顺序重新排列回表结果，Mapper 也只返回 ID，没有把距离作为业务结果继续传递。因此不能把最终上下文排列或页面卡片顺序直接解释为相似度排名。

这两点让我认识到，检索质量不只取决于模型。候选集合什么时候被裁剪、查询结果在哪里丢失顺序，都是普通程序逻辑，却会直接改变用户看到的推荐。

## 向量什么时候需要更新

房源描述、价格、状态和周边信息都会变化。并不是每个字段变化都必须重新生成向量：价格适合结构化筛选，描述内容变化才更可能影响语义表示。

代码需要明确：

- 哪些字段组成向量文本；
- 新增或修改房源时怎样生成向量；
- 房源下架时向量记录如何失效；
- 模型版本变化后是否需要重新计算；
- 生成失败时房源能否继续进入普通搜索。

当前源码在新增、修改房源的方法里调用 Embedding，再写入或更新 `houses_vec`；删除房源的方法同时清理相关向量记录。新增和修改使用的是实体 `house.toString()`，并没有按“只有描述字段变化才重新计算”做细粒度区分。上面的字段选择与版本管理，是可以继续完善的方向。

这些操作还放在数据库事务标注的方法里。它表达了数据库写入希望一起提交或回滚的意图，但外部 Embedding 请求不是数据库事务的一部分：已经发生的模型调用不能靠数据库回滚撤销。这里要分清数据库一致性、外部调用耗时和重复调用成本，不能把一个事务注解当成包办所有失败的总开关。

向量不是一次生成后永久有效的附件，而是由源数据派生出的索引。源数据与向量版本之间需要建立可追踪关系。

## RAG 不应该把房源事实交给模型记忆

RAG 的基本思路是先检索，再把材料交给模型生成回答。所读实现先召回房源对象，通过专门的描述函数组织地址、ID、户型、面积、价格等字段，再放进提示词的材料区域；这与生成向量时调用实体 `toString()` 是两种不同的文本组织方式。下列包含结构化过滤、去重与排序的流程是改进设计，不是当前方法已经逐步执行的流水线：

```text
用户需求
  → 结构化过滤
  → 向量召回
  → 候选去重与排序
  → 组织房源事实和知识上下文
  → 模型生成推荐说明
```

模型负责把条件与房源信息组织成自然语言，但不应自行创造价格、地址、面积和可用状态。重要字段最好以结构化形式传递，并在回答后继续由前端使用原始房源对象渲染卡片。

这样即使模型漏写某个字段，详情页面仍然读取数据库；即使模型说法与房源事实冲突，也可以根据房源 ID 回到权威记录验证。

## 通用知识与房源数据需要区分

“朝南采光通常较好”属于通用知识，“某套房朝南”属于具体房源事实。两类信息都可能进入检索，但可信来源和更新方式不同。

如果上下文没有标明类型，模型可能把通用建议误写成某套房的真实属性。更清晰的组织方式是分别提供：

- 房源结构化事实；
- 房源描述和周边材料；
- 通用购房知识；
- 用户已经确认的偏好。

回答也应区分“数据表明”“材料描述”和“一般建议”。这比简单要求模型“不要幻觉”更可执行。

## 引用编号把文字接回卡片，但不自动保证证据正确

EasyHome 已经有一条具体的展示连接：提示词要求模型用 `[^房源ID]` 表示引用；前端从回答的聚合文本里提取编号、去重，再让房源卡片按 ID 请求详情。这里不是根据模型写出的房源名称进行模糊搜索。

这个设计值得借鉴，也要看清它的边界：

- 编号格式正确，只能说明文本可以被解析，不代表该 ID 一定属于本轮召回集合。
- 房源详情接口返回对象，可以让卡片读取数据库字段，但不能反过来证明模型的每句推荐理由都被这些字段支持。
- 当前前端把新编号加入已有推荐列表，最多显示 4 个卡片；它与后端召回 5 个候选的数量不是一回事，也不是一份明确的排名协议。

因此，后续可以让服务端输出明确的候选 ID 与引用关系，再由前端绑定展示。不要让“模型会按格式写编号”同时承担存在性校验、权限校验和证据校验三份工作。一个编号很有用，但它不是推荐理由的免检章。

## 召回、排序与生成是三个评价阶段

推荐效果不能只用最终回答看起来是否流畅来判断。

1. **召回阶段**：符合用户需求的房源是否进入候选集合。
2. **排序阶段**：更匹配的房源是否排在前面。
3. **生成阶段**：理由是否忠于候选事实并表达清楚。

召回漏掉正确房源，模型无法补救；排序错误会让次要候选占用上下文；生成阶段则可能遗漏条件或夸大事实。分阶段记录输入输出，才能判断问题出现在哪里。

固定评测可以同时检查硬条件命中、候选覆盖、排序位置、引用事实和回答准确性。只让人主观判断“这段推荐不错”，很难在模型或索引变化后发现退化。

## 推荐系统仍然需要业务闭环

一段推荐回答只有连接到房源详情、收藏、预约和状态检查后，才真正进入业务流程。这里的卡片详情已有按 ID 请求数据的实现，但聊天首页的收藏回调仍只记录日志；不能因为卡片上出现收藏按钮，就把整条收藏链路写成已经接通。模型生成的房源名称不应该由前端模糊搜索，而应携带稳定房源 ID；下架或无权限访问时，页面也必须给出确定反馈。

推荐入口降低了查找成本，但不能绕过审核和权限。RAG 是新的查询方式，不是新的数据权威来源。

## 从 RAG 链路中学到的事情

向量检索处理语义相似，结构化筛选保证硬条件，模型负责组织表达。把这三层混成一个模型请求，虽然代码更短，却难以验证和纠错。

EasyHome 让我理解，AI 功能真正的工程量在模型调用之外：数据怎样进入索引、什么时候更新、候选怎样过滤、回答怎样回到真实房源。下一篇将从用户等待体验出发，整理 SSE 与 Kafka 分别解决什么问题，以及异步处理为什么仍然需要最终状态验证。
