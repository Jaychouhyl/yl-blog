接着上一篇的文档入图链路，数据来到浏览器之后，还有一段路要走：节点和关系需要转成用户能够理解、查询和操作的界面。NeoKG 是团队项目，这里主要从前端代码中整理我学到的数据契约、状态管理和可视化知识。

先纠正一个容易被技术栈列表带偏的认识：所读版本虽然声明了 Cytoscape.js 依赖，但查询页 `Query.vue` 实际导入的是 **ECharts**，使用 `type: 'graph'` 与力导向布局。依赖存在，不等于当前页面就在使用它；下面对 Cytoscape.js 的讨论只作概念对照，不把它写成这条页面链路的实现。

把接口数据交给图表库后，通常很快就能出现一张“图”。但节点重叠、标签遮挡、关系方向不清和操作入口缺失，会让它停在“能看见”的阶段。真正可用的图谱前端需要先回答：用户为什么打开这张图，他要寻找什么，看完以后还要做什么。

## Vue 3 与 TypeScript 分别解决什么

Vue 3 负责把页面拆成组件，并根据状态更新界面。图谱页面通常包含查询条件、工具栏、画布、节点详情、图例和异常提示，不适合全部堆在一个组件里。

TypeScript 则帮助前端明确数据契约。下面是用于讨论的简化类型，不是项目 `Node`、`Edge` 的逐字复制；实际类型还包含大小、颜色等展示字段：

```ts
interface GraphNode {
  id: string
  label: string
  type?: string
  properties?: Record<string, unknown>
}

interface GraphEdge {
  id: string
  source: string
  target: string
  relation: string
}
```

这些类型能约束参与编译的代码，但不会替 HTTP 返回值做运行时检查。给请求写一个泛型，也不会让不合法的 JSON 自动变合法。JavaScript 迁移到 TypeScript 的价值，不是把所有变量加上类型，而是把前后端真正依赖的字段写清楚，再在数据进入页面时验证关键约束。

## 先分清数据、样式和布局，再选择图表库

无论使用 ECharts 的图系列，还是 Cytoscape.js 的元素集合，都需要分开理解三个概念：

- **元素**决定图中有什么。
- **样式**决定不同类型和状态如何区分。
- **布局**决定节点在画布中的位置。

同一份数据使用不同布局，阅读效果可能完全不同。层级关系适合使用方向明确的布局，邻域探索可以使用力导向布局，少量路径则更适合突出起点到终点的顺序。没有一种布局可以适用于所有查询结果。

当前查询页把 `node.label` 映射为 ECharts 的 `name`，把 `node.size` 映射为 `symbolSize`，再单独给边设置 `source`、`target` 和线条样式。这一层转换让我理解了“展示模型”：后端返回的业务对象不必直接承担图表库的全部配置。换一种布局，也不应该顺手把实体 ID 换掉。

图谱规模增大后，还应限制首次展示数量。一次渲染所有节点不仅影响性能，也会让用户失去视觉焦点。先显示目标节点和有限邻域、再按需展开，是后续设计方向，不代表当前查询页已经实现了大图按需加载。

## 节点的名字可以相同，身份不能靠猜

文档标题是给人读的，ID 是给程序连接关系的。文档—关键词图使用 `doc-`、`kw-` 前缀区分对象类型；即使两个对象的数字部分碰巧一样，`doc-101` 与 `kw-101` 也不应被当成同一个节点。

路径联调还存在另一种差异：后端路径节点带前缀，而边端点返回数字部分的字符串，页面随后建立映射来匹配原图。这能解释为什么“节点都找到了，线却没有高亮”。在当前数据上能匹配，不等于这套数字反查能处理所有同号、不同类型对象；更清楚的契约是让节点和边从接口开始使用同一套完整标识。

另一个基础问题是 JavaScript 大整数。下面的例子可以直接运行，数字是教学数据，不是项目中的真实 ID：

```js
const unsafe = JSON.parse('{"id":9007199254740993}')
const safe = JSON.parse('{"id":"9007199254740993"}')

console.log(String(unsafe.id)) // 9007199254740992
console.log(safe.id)           // 9007199254740993
console.log(BigInt(safe.id) === 9007199254740993n) // true
```

问题发生在数字解析成 `Number` 的那一刻。之后再调用 `String()` 或 `BigInt()`，只能转换已经丢失精度的值，不能把原数字找回来。仓库的 ID 工具函数中也有把超范围数字转成 BigInt 的处理，但查询页并未导入这套工具；既不能把工具文件存在当成链路已接入，也不能把事后转换当成无损修复。

更简单的约定是：后端序列化大整数 ID 时直接输出字符串，前端一路保持字符串。**标识符不是拿来做加减法的，不必为了看起来像数字就把它变成数字。** 安全整数范围可对照 [JavaScript 的 `Number.MAX_SAFE_INTEGER` 说明](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Number/MAX_SAFE_INTEGER)。

## 筛掉节点以后，边也必须重新检查

源码中先筛节点，再用 `Set` 保留两端都仍然存在的边。这是一个比“怎样调颜色”更基础的图约束：展示子图不能留下悬空端点。下面用小数据重现这个逻辑，不依赖任何图表库：

```js
const nodes = [
  { id: 'doc-101', type: 'DOCUMENT' },
  { id: 'kw-201', type: 'KEYWORD' },
]
const edges = [{ source: 'doc-101', target: 'kw-201' }]
const visibleNodes = nodes.filter(node => node.type === 'DOCUMENT')
const visibleIds = new Set(visibleNodes.map(node => node.id))
const visibleEdges = edges.filter(edge =>
  visibleIds.has(edge.source) && visibleIds.has(edge.target)
)

console.assert(visibleNodes.length === 1 && visibleEdges.length === 0)
console.log(visibleNodes.length, visibleEdges.length)
```

隐藏关键词后，只剩一个文档节点、零条边，这是正确的筛选结果，不是图表库把线弄丢了。这个例子也说明，页面状态最好从原始数据推导，而不是每次筛选都破坏原始数组；当前页面保留原图，再生成筛选结果，正是这种思路。

## 普通查询、路径搜索和社区发现不能共用一套强调方式

普通节点查询的任务是确认“目标是谁、与谁直接相关”。页面应该突出目标节点，并弱化无关分支。

路径搜索的任务是理解“两个对象怎样连接”。起点、终点、中间节点和关系方向需要具有稳定区别，路径外元素可以降低透明度。

社区发现关注“哪些节点形成群组”。页面需要使用分组颜色或边界表达社区，同时避免随机颜色在每次刷新后改变，否则用户无法形成稳定认知。

如果三类结果都只是把节点换一种颜色，功能虽然存在，用户却无法快速读出结论。视觉编码必须服务当前任务，而不是为了让页面更丰富。

## 交互设计要保留上下文

用户点击节点后通常需要查看类型、属性、来源和相邻关系。详情面板如果覆盖整张图，会失去点击前的上下文；如果只用浏览器提示框，又无法展示复杂信息。

进一步完善交互时，可以考虑下面这些设计；它们是学习后的检查清单，不表示当前页面全部具备：

- 单击节点显示侧边详情，同时保留画布位置；
- 双击或明确按钮展开邻居，避免误触导致图谱突然膨胀；
- 提供返回查询结果、适应画布和重置布局；
- 选中路径时保留起点、终点和关系说明；
- 支持按实体类型、关系类型或关键词筛选；
- 空结果、接口失败和权限不足使用不同提示。

图谱操作还需要考虑坐标变化。重新布局后，当前选中节点不应失去高亮；窗口尺寸变化时，画布需要重新适配，而不是简单把节点压缩到一角。

## 颜色、大小和标签都属于数据表达

节点颜色可以表达实体类型，大小可以表达连接度或重要性，边的线型可以表达关系类别。但视觉通道有限，同一属性不应同时承担多个含义。

一些常见问题包括：

- 节点越大并不一定越重要，可能只是文本更长。
- 暗色模式只反转背景会造成边和标签对比不足。
- 类型颜色太多时，图例比图本身更难理解。
- 边标签全部显示会互相遮挡。
- 只依靠颜色区分，不利于色觉差异用户理解。

因此项目中调整暗色模式、节点高亮和查询结果时，重点并不是增加装饰，而是让状态差异可读。必要时可结合颜色、边框、形状和文字说明，而不是只改变一种色值。

当前查询页确实把路径节点集合与路径边集合分开保存：节点可加边框、放大，路径外元素则降低透明度；社区也有独立开关和颜色状态。这让我学到，选中、路径命中、社区归属和主题颜色最好先作为不同状态理解，再明确渲染优先级，否则很容易出现“刚选中又被下一次染色覆盖”的混乱。

## API 联调真正困难的是语义

接口返回 200 不代表图谱可以正确展示。前端需要确认：

1. 节点 ID 在一次查询和后续操作中是否稳定。
2. 边的 `source` 与 `target` 是否对应正确方向。
3. 路径结果是节点序列、边序列还是完整子图。
4. 中文查询参数如何编码。
5. 空结果与后端异常怎样区分。
6. 社区编号是否在同一次结果中稳定。

查询页对路径响应尝试读取直接的 `nodes`、包装层中的 `data.nodes`，甚至继续查找其他含 `nodes` 的对象。这能看出适配不同响应形状的处理，也提醒我：接口能否正确展示，不能永远依赖前端“翻箱倒柜”找字段。固定响应形状后，应把合法空图与格式错误分开，而不是都解释成没有路径。

## 性能优化从减少无效工作开始

图谱性能不只取决于框架。节点数量、布局算法、标签绘制和事件监听都会产生开销。最先应该做的通常不是引入复杂缓存，而是减少一次性渲染范围：

- 对查询深度和结果数量设置上限；
- 只在需要时显示边标签；
- 合并频繁的搜索和布局更新；
- 组件销毁时解除监听和释放图实例；
- 把详情数据与画布元素分开管理。

大图谱还需要聚合、分页或分层探索。把几万个节点同时放进浏览器，即使能够渲染，也不代表用户能够理解。

这些是优化检查项，而不是压测结论。当前页面可以确认的生命周期处理是：重新初始化前释放旧 ECharts 实例，组件卸载时调用 `dispose()`。图表实例与 Vue 响应式数据不是同一种资源，组件不显示了，不代表第三方实例就会自动完成全部清理。

## 我从图谱前端中学到的事情

普通后台页面主要整理字段和流程，图谱前端还需要设计用户理解关系的路径。画布只是载体，真正的产品能力来自查询目标、视觉编码、交互反馈和接口契约共同配合。
