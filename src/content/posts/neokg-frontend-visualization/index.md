NeoKG 中我直接参与的工作主要集中在前端：Vue 页面、TypeScript 迁移、文档和关键词管理、图谱查询、路径交互、社区结果、登录注册、暗色模式以及接口联调。图谱页面是其中最特别的一部分，因为它展示的不是固定表格，而是一组数量和结构都可能变化的节点与关系。

第一次把接口数据交给 Cytoscape.js 后，页面很快就能出现一张“图”。但节点重叠、标签遮挡、关系方向不清和操作入口缺失，会让这张图只能用于截图。真正可用的图谱前端需要先回答：用户为什么打开这张图，他要寻找什么，看完以后还要做什么。

## Vue 3 与 TypeScript 分别解决什么

Vue 3 负责把页面拆成组件，并根据状态更新界面。图谱页面通常包含查询条件、工具栏、画布、节点详情、图例和异常提示，不适合全部堆在一个组件里。

TypeScript 则帮助前端明确数据契约。例如节点和关系可以分别定义：

```ts
interface GraphNode {
  id: string
  label: string
  type?: string
  properties?: Record<string, unknown>
}

interface GraphEdge {
  id: string
  source: string
  target: string
  relation: string
}
```

类型不能保证接口一定正确，但能让“节点 ID 可能缺失”“关系方向字段写错”“属性并非固定结构”等问题更早暴露。JavaScript 迁移到 TypeScript 的价值，不是把所有变量加上类型，而是把前后端真正依赖的字段变成可以检查的契约。

## Cytoscape.js 的核心是元素、样式和布局

Cytoscape.js 使用节点和边组成元素集合，再通过样式和布局决定呈现方式。三个概念需要分开：

- **元素**决定图中有什么。
- **样式**决定不同类型和状态如何区分。
- **布局**决定节点在画布中的位置。

同一份数据使用不同布局，阅读效果可能完全不同。层级关系适合使用方向明确的布局，邻域探索可以使用力导向布局，少量路径则更适合突出起点到终点的顺序。没有一种布局可以适用于所有查询结果。

图谱规模增大后，还要限制首次展示数量。一次渲染所有节点不仅影响性能，也会让用户失去视觉焦点。更合理的方式是先显示目标节点和有限邻域，再按需展开。

## 普通查询、路径搜索和社区发现不能共用一套强调方式

普通节点查询的任务是确认“目标是谁、与谁直接相关”。页面应该突出目标节点，并弱化无关分支。

路径搜索的任务是理解“两个对象怎样连接”。起点、终点、中间节点和关系方向需要具有稳定区别，路径外元素可以降低透明度。

社区发现关注“哪些节点形成群组”。页面需要使用分组颜色或边界表达社区，同时避免随机颜色在每次刷新后改变，否则用户无法形成稳定认知。

如果三类结果都只是把节点换一种颜色，功能虽然存在，用户却无法快速读出结论。视觉编码必须服务当前任务，而不是为了让页面更丰富。

## 交互设计要保留上下文

用户点击节点后通常需要查看类型、属性、来源和相邻关系。详情面板如果覆盖整张图，会失去点击前的上下文；如果只用浏览器提示框，又无法展示复杂信息。

更合适的交互包括：

- 单击节点显示侧边详情，同时保留画布位置；
- 双击或明确按钮展开邻居，避免误触导致图谱突然膨胀；
- 提供返回查询结果、适应画布和重置布局；
- 选中路径时保留起点、终点和关系说明；
- 支持按实体类型、关系类型或关键词筛选；
- 空结果、接口失败和权限不足使用不同提示。

图谱操作还需要考虑坐标变化。重新布局后，当前选中节点不应失去高亮；窗口尺寸变化时，画布需要重新适配，而不是简单把节点压缩到一角。

## 颜色、大小和标签都属于数据表达

节点颜色可以表达实体类型，大小可以表达连接度或重要性，边的线型可以表达关系类别。但视觉通道有限，同一属性不应同时承担多个含义。

一些常见问题包括：

- 节点越大并不一定越重要，可能只是文本更长。
- 暗色模式只反转背景会造成边和标签对比不足。
- 类型颜色太多时，图例比图本身更难理解。
- 边标签全部显示会互相遮挡。
- 只依靠颜色区分，不利于色觉差异用户理解。

因此项目中调整暗色模式、节点高亮和查询结果时，重点并不是增加装饰，而是让状态差异可读。必要时可结合颜色、边框、形状和文字说明，而不是只改变一种色值。

## API 联调真正困难的是语义

接口返回 200 不代表图谱可以正确展示。前端需要确认：

1. 节点 ID 在一次查询和后续操作中是否稳定。
2. 边的 `source` 与 `target` 是否对应正确方向。
3. 路径结果是节点序列、边序列还是完整子图。
4. 中文查询参数如何编码。
5. 空结果与后端异常怎样区分。
6. 社区编号是否在同一次结果中稳定。

我在联调中处理过路径参数、节点高亮、暗色显示和异常状态。这些问题让我认识到，前端不能被动适配任何 JSON。接口字段必须对应清楚的业务语义，否则页面只能用大量条件判断猜测后端意图。

## 性能优化从减少无效工作开始

图谱性能不只取决于框架。节点数量、布局算法、标签绘制和事件监听都会产生开销。最先应该做的通常不是引入复杂缓存，而是减少一次性渲染范围：

- 对查询深度和结果数量设置上限；
- 只在需要时显示边标签；
- 合并频繁的搜索和布局更新；
- 组件销毁时解除监听和释放图实例；
- 把详情数据与画布元素分开管理。

大图谱还需要聚合、分页或分层探索。把几万个节点同时放进浏览器，即使能够渲染，也不代表用户能够理解。

## 我从图谱前端中学到的事情

普通后台页面主要整理字段和流程，图谱前端还需要设计用户理解关系的路径。画布只是载体，真正的产品能力来自查询目标、视觉编码、交互反馈和接口契约共同配合。
