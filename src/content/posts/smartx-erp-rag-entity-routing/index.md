在 ERP 中加入 RAG 很容易停留在“回答看起来正确”。用户输入一个问题，模型返回订单、库存或供应商信息，页面以流式方式显示文字，这已经可以完成一次演示，但距离真实工作仍然差一步：回答能否回到系统里的权威记录。

如果用户看到采购单号后还需要复制、切换菜单、重新输入筛选条件，那么自然语言只减少了第一次搜索，并没有缩短完整业务链路。更糟糕的情况是，回答中的超链接只打开采购页面首页，或者把“物料”“库存情况”这样的普通词也渲染成链接。链接越多，可信度反而越低。

![RAG 对安全库存预警的结构化回答](../../../../public/images/projects/smartx-erp/05-rag-answer.png)

## 不直接信任模型生成的链接

模型擅长生成语言，不适合决定前端路由。它可能输出 Markdown 链接、HTML 标签，也可能把名称的一部分误认为编码。若前端直接渲染这些内容，业务页面将接受一个概率模型构造的地址。

SmartX 的处理方式是先移除模型原始链接，再由前端基于结构化实体和受控规则重新识别：

- 完整销售单号、采购单号和明确编码可以成为候选实体。
- 足够具体的客户、供应商和物料名称可以成为候选实体。
- “物料”“订单”“详细信息”等通用词保持普通文本。
- 不从更长名称中截取一段 ASCII 字符作为编码。
- 字符区间与当前回答不一致时直接拒绝。

这相当于把模型的输出从“可执行路由”降级为“实体候选”，最终路由仍由确定性代码构造。

从编程角度看，这里是在区分“非确定性建议”和“确定性执行”。模型可以输出实体候选，但实体类型、编号格式、目标路由和权限校验必须由普通代码完成。否则模型偶尔多写一个斜杠，前端就可能带着用户去一次没有安排的系统旅行。

更稳妥的数据契约至少要包含实体类型、显示文本、权威标识和原文区间。前端只消费通过 schema 校验的字段，不再从自然语言里临时猜参数。实体识别也不是简单地给字符串上色，而是一段完整的解析流程：候选提取、格式校验、歧义处理、权限验证、路由构造。任一步失败，都应回退为普通文本，而不是勉强制造一个看起来很积极的链接。

## 订单与主数据不能使用同一种跳转

订单通常拥有唯一业务编号，适合直接定位详情；客户和供应商名称可能重复，更适合先筛选，再由用户确认。

因此路由契约分为两类：

```text
订单：
focusOrderId / focusOrderNo + autoOpen=view

客户、供应商等主数据：
focusId / focusName + autoOpen=filter
```

订单页面收到参数后先加载权威数据，匹配成功才打开详情。主数据页面根据 ID 或名称形成筛选条件，而不是默认打开列表第一条。

这里最重要的不是参数名，而是失败行为：

- 找不到时明确提示，不制造“已经定位”的错觉。
- 匹配到多条时保留筛选结果，不静默选择第一条。
- 用户无权限时按业务权限处理，不能因为入口来自 RAG 就绕过限制。

## “继续查看”为什么必须是一条完整链

一个“继续查看”按钮通常跨越多个模块：

1. RAG 后端从回答中提取实体。
2. SSE 把实体类型、ID、编号和名称传给前端。
3. 消息组件展示可点击实体。
4. 路由构建器选择目标页面和参数。
5. 目标页面读取参数并自动筛选或打开详情。
6. 页面处理零条、多条和权限不足。

只完成第四步，就会出现“跳转成功但没有定位”的假修复。只完成第五步，却没有实体质量控制，又会出现普通词满屏可点。RAG 实体交互必须按端到端链路验证，而不是分别证明后端返回了实体、前端也能跳转。

## 流式回答还需要状态和滚动治理

RAG 的可用性不只取决于实体。工具规划、检索和模型调用可能让首个 token 延迟出现，如果页面没有状态提示，用户会误以为按钮没有生效。消息区、草稿抽屉和外层页面如果共享滚动锁，还会造成抽屉看不到底部、离开 RAG 后其他页面无法滚动。

因此工作区需要把职责拆开：

- 外层页面负责稳定布局。
- 消息区独立滚动。
- 草稿和审核面板独立滚动。
- 路由离开时恢复全站滚动状态。
- 首个 token 前显示正在整理上下文或查询业务数据。

代码层面还需要把流式回答建模成明确状态，而不是散落几组互相覆盖的布尔值：

```text
idle → planning → retrieving → streaming → complete
                                      ↘ error
```

状态机让发送按钮、加载提示、停止生成和重试入口都由同一状态推导。否则很容易出现文字已经输出，按钮却仍然在“思考”；或者请求已经失败，界面还在认真旋转。显式状态并不会让网络更快，但能让用户知道系统此刻到底在做什么。

## RAG 的评价标准应该改变

对企业系统来说，RAG 不应只问“回答像不像正确答案”，还要问：

- 引用是否来自正确资料。
- 实体是否完整、准确。
- 点击后是否到达正确业务对象。
- 零匹配、多匹配和权限不足是否被正确处理。
- 写操作是否停留在草稿和人工确认边界。

下一步最值得建立的是固定评测集：每个问题同时定义期望答案要点、引用来源、实体、路由结果和权限结果。只有这样，RAG 才能从主观体验进入可重复验证。

## 从 RAG 交互中学到什么

这次改造让我更清楚地看到，RAG 的难点并不只在检索和提示词，而在模型输出怎样安全地进入现有业务系统：

- 模型适合解释问题和生成候选，不适合直接决定业务执行。
- 类型化契约比从文本中猜路由更可靠，也更容易测试。
- 跳转成功不等于业务定位成功，必须在目标页面验证最终状态。
- 零匹配、多匹配和无权限不是边角情况，而是路由契约的一部分。
- 流式交互需要状态机、错误恢复和滚动边界共同成立。

从“回答一段话”到“完成一次可信操作”，中间隔着解析、验证、权限和页面状态。把这些确定性环节补齐后，模型才更像系统入口，而不是一个很会聊天、但不太认路的同事。
