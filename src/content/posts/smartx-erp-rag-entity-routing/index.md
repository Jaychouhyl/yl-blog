在 ERP 中加入 RAG 很容易停留在“回答看起来正确”。用户输入一个问题，模型返回订单、库存或供应商信息，页面以流式方式显示文字，这已经可以完成一次演示，但距离真实工作仍然差一步：回答能否回到系统里的权威记录。

如果用户看到采购单号后还需要复制、切换菜单、重新输入筛选条件，那么自然语言只减少了第一次搜索，并没有缩短完整业务链路。更糟糕的情况是，回答中的超链接只打开采购页面首页，或者把“物料”“库存情况”这样的普通词也渲染成链接。链接越多，可信度反而越低。

![RAG 对安全库存预警的结构化回答](../../../../public/images/projects/smartx-erp/05-rag-answer.png)

## 不直接信任模型生成的链接

模型擅长生成语言，不适合决定前端路由。它可能输出 Markdown 链接、HTML 标签，也可能把名称的一部分误认为编码。若前端直接渲染这些内容，业务页面将接受一个概率模型构造的地址。

SmartX 的处理方式是先移除模型原始链接，再由前端基于结构化实体和受控规则重新识别：

- 完整销售单号、采购单号和明确编码可以成为候选实体。
- 足够具体的客户、供应商和物料名称可以成为候选实体。
- “物料”“订单”“详细信息”等通用词保持普通文本。
- 不从更长名称中截取一段 ASCII 字符作为编码。
- 字符区间与当前回答不一致时直接拒绝。

这相当于把模型的输出从“可执行路由”降级为“实体候选”，最终路由仍由确定性代码构造。

从编程角度看，这里是在区分“非确定性建议”和“确定性执行”。模型可以输出实体候选，但实体类型、编号格式、目标路由和权限校验必须由普通代码完成。否则模型偶尔多写一个斜杠，前端就可能带着用户去一次没有安排的系统旅行。

更稳妥的数据契约应包含实体类型、显示文本、权威标识和原文区间。当前实现检查了实体字段、名称具体程度、字符边界和区间内容，同时还保留基于文本规则的业务实体识别；不能把它写成已经完全依赖 schema、完全不做文本推断。前端路由检查也不能替代后端权限校验。

其中 `positions` 不是可有可无的装饰。`renderWithEntities` 按区间切出原文，再与实体名称比较；内容不一致就跳过这项标记。例如先识别实体、随后又改写了回答文本，原来的起止位置便可能失效。这个检查宁可少生成一个链接，也不把相邻的其他文字绑定到错误对象。这里强调的是处理顺序：实体区间与它引用的文本必须属于同一个版本。

## 订单与主数据不能使用同一种跳转

订单通常拥有唯一业务编号，适合直接定位详情；客户和供应商名称可能重复，更适合先筛选，再由用户确认。

因此路由契约分为两类：

```text
订单：
focusOrderId / focusOrderNo + autoOpen=view

客户、供应商等主数据：
focusId / focusName + autoOpen=filter
```

订单页面收到参数后先加载权威数据，匹配成功才打开详情。主数据页面根据 ID 或名称形成筛选条件，而不是默认打开列表第一条。

这里最重要的不是参数名，而是失败行为：

- 找不到时明确提示，不制造“已经定位”的错觉。
- 匹配到多条时保留筛选结果，不静默选择第一条。
- 用户无权限时按业务权限处理，不能因为入口来自 RAG 就绕过限制。

## 同名客户不能靠“取第一条”解决

`resolveMasterDataFocus` 把定位结果分成 `found`、`missing` 和 `ambiguous`。有 ID 时先查询 ID，并核对返回记录的 ID；无法获得匹配记录时，再按名称加载候选，并用名称完全相等筛选。

假设“青禾商贸”是一个示例名称，不代表项目里的真实客户。只看按名称返回的候选，会遇到三种不同结果：

| 候选中的精确匹配 | 解析结果 | 页面应该怎样理解 |
|---|---|---|
| 只有一个名称完全相同的客户 | `found` | 获得这条候选中的匹配记录 |
| 有两个名称完全相同的客户 | `ambiguous` | 暂时无法唯一定位，不自动拿第一条冒充目标 |
| 只有“青禾商贸二部”等相近名称 | `missing` | 模糊搜索找到了相关项，但没有找到指定名称 |

客户页拿到唯一记录后，会把它放进列表并显示筛选成功；多条精确匹配则提示无法唯一定位。这说明“搜索出一些结果”和“准确找到那个对象”是两个步骤。搜索可以宽松一点，自动打开业务对象不能同样宽松。

还需要诚实保留当前实现的限制。ID 查询的异常会被捕获，然后继续尝试名称定位，并没有在这个函数里分别处理网络错误、无权限与记录不存在。它也只判断 `loadByName` 返回的候选，若返回集不完整，不能据此证明全库唯一。更严格的定位契约应保留错误原因，并明确候选范围；这不是权限服务已经失效的证据，而是不能把一个定位辅助函数当成完整的权限与唯一性保证。

这组代码里最值得学习的是返回值的设计。若只返回一条记录或 `null`，调用方就无法区分“没找到”和“找到太多”；给失败情况起清楚的名字，页面才能给出下一步，而不是统一弹出一句“操作失败”。

## “继续查看”为什么必须是一条完整链

一个“继续查看”按钮通常跨越多个模块：

1. RAG 后端从回答中提取实体。
2. SSE 把实体类型、ID、编号和名称传给前端。
3. 消息组件展示可点击实体。
4. 路由构建器选择目标页面和参数。
5. 目标页面读取参数并自动筛选或打开详情。
6. 页面处理零条、多条和权限不足。

只完成第四步，就会出现“跳转成功但没有定位”的假修复。只完成第五步，却没有实体质量控制，又会出现普通词满屏可点。RAG 实体交互必须按端到端链路验证，而不是分别证明后端返回了实体、前端也能跳转。

## 流式回答还需要状态和滚动治理

RAG 的可用性不只取决于实体。工具规划、检索和模型调用可能让首个 token 延迟出现，如果页面没有状态提示，用户会误以为按钮没有生效。消息区、草稿抽屉和外层页面如果共享滚动锁，还会造成抽屉看不到底部、离开 RAG 后其他页面无法滚动。

因此工作区需要把职责拆开：

- 外层页面负责稳定布局。
- 消息区独立滚动。
- 草稿和审核面板独立滚动。
- 路由离开时恢复全站滚动状态。
- 首个 token 前显示正在整理上下文或查询业务数据。

下面是帮助理解流式回答的状态划分建议，不是对当前源码状态枚举的逐字摘录：

```text
idle → planning → retrieving → streaming → complete
                                      ↘ error
```

状态机让发送按钮、加载提示、停止生成和重试入口都由同一状态推导。否则很容易出现文字已经输出，按钮却仍然在“思考”；或者请求已经失败，界面还在认真旋转。显式状态并不会让网络更快，但能让用户知道系统此刻到底在做什么。

## RAG 的评价标准应该改变

对企业系统来说，RAG 不应只问“回答像不像正确答案”，还要问：

- 引用是否来自正确资料。
- 实体是否完整、准确。
- 点击后是否到达正确业务对象。
- 零匹配、多匹配和权限不足是否被正确处理。
- 写操作是否停留在草稿和人工确认边界。

下一步最值得建立的是固定评测集：每个问题同时定义期望答案要点、引用来源、实体、路由结果和权限结果。只有这样，RAG 才能从主观体验进入可重复验证。

## 从 RAG 交互中学到什么

这部分代码让我把一个很小的“继续查看”按钮看成三次核对：回答里的文字是否对应实体，实体是否对应受控路由，目标页是否确实找到权威记录。任何一层都不能只用上一层的成功来代替。

比起让更多文字变成链接，我更关心一次点击失败时能不能说清原因。同名对象、过期区间和接口异常都不是模型多解释两句就能解决的，它们需要普通程序把输入和状态处理清楚。模型可以很会聊天，认路这件事还是交给可检查的规则更稳妥。
