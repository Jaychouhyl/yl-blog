这个小站从今天开始使用。它不会只保存零散的感想，也会逐步承担项目复盘、学习记录和个人展示的功能。

写下第一篇文章时，页面结构、分类和导航都还很简单，但有一件事最好先说明：这个站为什么存在，以及什么内容值得长期留在这里。否则文章越写越多，最后可能得到一个文件很多、方向很少的仓库。

因此，这篇文章不负责介绍某项技术，而是作为“站点建设”系列的序章。后面的文章会继续整理技术选型、内容结构、阅读体验、功能集成、部署与维护；这里先把它们共同服务的目标说清楚。

## 为什么要建立这个站

学习和做项目时，我已经习惯把材料保存在本地：代码在仓库里，笔记在 Markdown 中，截图和报告散落在各自目录。它们能够证明事情做过，却不一定方便之后理解“当时为什么这样做”。

个人博客提供了一层重新组织的机会。它不是把原始材料全部搬到网页上，而是从中选择已经确认、适合公开、对后续学习仍有价值的部分，再整理成可以连续阅读的内容。

这也意味着博客不是简历的加长版。简历负责快速说明经历，博客更适合保存问题、取舍和变化过程。一个功能最终能够运行当然重要，但它中间为什么失败、怎样定位、后来为什么换了做法，往往更值得留下。

## 这个站点会沉淀什么

### 项目复盘

项目文章会从实际代码和材料出发，说明系统解决什么问题、使用哪些技术，以及不同模块之间怎样协作。相比逐项罗列功能，我更想记录自己从代码和项目中学到了哪些编程及系统设计知识。

复盘也不等于为项目补一层漂亮包装。团队项目会区分个人直接参与、团队整体成果与后期代码阅读；尚未验证的计划不会提前写成已经完成的能力。少写一句夸张结论，通常比以后花三段话解释它更省事。

### 基础知识与工程理解

项目中出现的重要知识会单独展开，例如异步任务为什么需要状态机、图谱查询为什么不能只依赖关键词、静态站点为什么仍然要处理基础路径。知识点会尽量放回真实场景，不把文章写成术语排队点名。

重点不是给每个概念下一个最标准的定义，而是说明它在当前项目里解决了什么问题、带来了什么代价，以及什么时候不应该使用。能够说清“不用它会怎样”，通常才算真正理解了它。

### 琐碎记录

技术和项目之外，也会保留少量阅读、生活与阶段变化。它们不需要强行总结出方法论，只要真实、克制，并且过一段时间再看仍能理解当时的想法就足够。

“琐碎”不是随手把所有东西倒进来，而是给那些不属于项目、又值得记住的内容留一个位置。毕竟人的生活不能永远只有构建日志，偶尔也要允许终端安静一会儿。

## 公开内容的边界

公开写作首先要对事实负责。站内优先展示能够由源码、项目材料、运行结果或 Git 历史确认的信息；对仍在计划中的功能，会明确写成方向，而不是让未来完成时态提前上班。

其次是贡献边界。团队项目可以介绍完整系统，但不会把所有模块都写成个人完成。对于后期阅读和理解的部分，会重点说明从中学到了什么，而不是重新分配项目经历。

最后是隐私边界。学校、私人经历、内部账号、未公开数据和无关个人信息不会因为“写得更完整”就自动适合公开。博客需要提供足够上下文帮助理解内容，但不需要把个人档案整箱搬到网页上。

## 如何用于展示

### 求职与复试材料

这个站点会作为一个公开入口，帮助别人快速了解我的学习方向、项目经历和表达方式。它不会替代简历或正式材料，而是补充展示更完整的思考过程。

### 持续更新的作品集

当项目、文章或复盘有新进展时，我会优先补充到原有页面，而不是只新增碎片内容。希望这里能呈现真实、可追踪的成长记录。

## 内容会怎样继续更新

博客中的文章不是不可修改的纪念碑。项目事实补充后，可以修正文中的范围；依赖和实现变化后，可以更新技术说明；原来的判断被运行结果推翻时，也应该保留更准确的新结论。

但更新不意味着每次都把历史擦得干干净净。过程文档和 Git 记录会继续保存重要修改的原因与验证结果，让“现在为什么是这样”能够找到来路。对长期站点来说，可追踪比看起来从未犯错更有用。

## 从第一篇记录中学到什么

第一，开始写作之前，先确定内容边界。没有边界的博客很容易同时像笔记仓库、简历、动态广场和文件中转站，最后哪个角色都承担不好。

第二，公开展示不只是在增加内容，也是在主动删除不必要的信息。真正重要的是读者能否理解项目、知识和思考过程，而不是页面上出现了多少个人资料。

第三，站点结构应该服务长期写作，而不是要求写作不断迁就页面。接下来的技术选型也会从这个目标出发：先确定怎样写、怎样维护，再决定为什么选择 Astro。
