“测试通过”是一句容易失去含义的话。它可能表示代码能够编译，也可能表示单元测试没有失败，还可能只是页面没有抛出 console error。不同证据回答不同问题，如果把它们合并为一句“已经全部验收”，项目状态就会被高估。

SmartX 的验证方式经历了从脚本检查到真实浏览器的升级。这个过程并不是自动化失效，而是逐渐明确自动化的边界。

## 构建证明什么

Maven 或 Vite 构建成功，首先证明当前源码能够生成产物，依赖和语法基本一致。它不能证明服务能够连接数据库和 Nacos，也不能证明业务链路和页面交互正确。

后端测试报告与构建还需要分开：历史材料中有一次 Maven 构建明确使用了跳过测试参数，它只能作为构建证据。2026-07-26 的归档 Surefire 报告汇总为 374 项通过，才可以表述为该日期下的后端测试证据。不同日期、不同命令不能拼成同一次“完整验收”。

## 自动化测试证明什么

前端 Node 测试适合验证路由参数、组件契约、文本规则和回归条件。权限矩阵可以比较角色、路由、按钮和后端权限点。几何检查可以发现元素越界和页面横向滚动。

但自动化无法稳定判断：

- 字体是否僵硬。
- 页面是否显得拥挤。
- 状态颜色是否过重。
- 真实长名称是否破坏布局。
- 卡片间的视觉重心是否均衡。

“没有溢出”不等于“排版好看”，“按钮可点击”也不等于“用户知道下一步做什么”。

## 把证据排成一张地图

后来我更愿意把验证看成一张证据地图，而不是一条从“运行测试”直达“项目完成”的捷径：

| 证据层 | 主要回答的问题 | 不能替代的部分 |
|---|---|---|
| 静态检查与构建 | 代码能否被解析并生成产物 | 服务是否真的可用 |
| 单元与契约测试 | 局部规则和接口约定是否稳定 | 多服务组合后的行为 |
| 集成与运行检查 | 数据库、中间件和服务链路能否协作 | 页面是否易用 |
| 浏览器与业务验收 | 用户能否在真实数据下完成任务 | 容量、安全和灾备 |
| 生产准备验证 | 系统能否在正式约束下持续运行 | 真实业务收益 |

这几层证据并不是谁比谁高级，而是分别回答不同的问题。绿色 CI 很有价值，但它更像一张体检报告，不是系统从此百毒不侵的证书。

## 真实数据会改变页面

静态数据下正常的页面，接入后端后出现了乱码、空图谱、长客户名、组件 warning 和异常状态。知识图谱在 0 实体、0 关系时如果只显示空白，自动化可能认为 Canvas 正常存在，用户却无法判断发生了什么。

因此浏览器验收需要覆盖：

- 真实开发数据。
- 1280、1366、1600 等桌面宽度。
- 左侧导航展开和收起。
- 亮色与暗色主题。
- 表格、筛选、抽屉、弹窗、Toast 和悬浮入口。
- 空数据、错误、加载、禁用和权限不足。

真实页面截图不是装饰证据，而是证明布局在具体数据和尺寸下成立。

## 高风险动作不能只看入口

一个用户看不到“删除”按钮，不代表后端已经拒绝删除接口；看到按钮也不代表调用一定被允许。

权限验收应区分：

1. 菜单和路由可见性。
2. 按钮权限。
3. 后端权限注解和数据范围。
4. 允许动作成功。
5. 越权动作明确失败。
6. 测试数据和业务影响可回滚。

早期只做可见性检查，是为了避免在开发库中无控制执行审批、结算、发货和重建。只有明确测试标识和回滚方式后，才适合做高风险闭环。

## 验收还需要成本边界

RAG 和知识图谱引入了新的验证成本。反复点击重建图谱、全量索引或 Embedding，不仅慢，还会产生模型和向量调用成本。UI 检查不需要每次重建数据。

因此验证应分层：

- UI 布局使用已有快照或只读数据。
- RAG 规则使用固定回答和实体样本。
- 真实模型只在验证模型链路时调用。
- 图谱重建只在验证任务状态和同步结果时执行。

测试越接近真实，不代表每次都要执行最昂贵的路径。好的验证既要可信，也要可重复、可控成本。

## 确定性系统与概率性系统要分开测

ERP 规则通常可以给出明确预期：库存不能无故变成负数、越权请求必须被拒绝、同一幂等键不能重复生成单据。它们适合使用断言、状态机和固定输入反复验证。

RAG 与模型回答则带有概率性。只检查“有没有返回文字”几乎没有意义，更合适的办法是固定问题集、知识版本和引用规则，再比较实体识别、引用命中、拒答边界和业务跳转是否符合预期。模型可以换一种说法，但不能悄悄换掉业务事实。

这让我理解到，自动化测试不是越统一越好。确定性业务要把结果钉牢，概率性能力要把评价标准钉牢；两者都需要稳定基线，只是稳定的对象不同。

## 一份更准确的完成定义

对 SmartX 这样的系统，完成标准可以分为五层：

1. **静态正确**：源码、依赖和配置结构成立。
2. **测试正确**：单元、契约和回归测试通过。
3. **运行正确**：服务健康，真实请求能穿过完整链路。
4. **交互正确**：页面在真实数据、权限、宽度和主题下可用。
5. **生产正确**：容量、安全、告警、备份和故障恢复经过正式验证。

当前项目已经具备前四层中的大量本地证据，但不能把它们包装成第五层。诚实区分证据，比一句笼统的“全部完成”更能体现工程判断。

## 从验证工作中学到什么

这部分工作让我重新理解了“测试通过”的含义：测试不是给项目盖章，而是缩小未知范围。每增加一种证据，都应该先说明它证明了什么，再说明它没有证明什么。

我也学会按风险安排验证。普通查询可以大量自动化，高风险写操作则需要身份、权限、数据影响和回滚一起检查；视觉问题必须回到真实浏览器，模型能力必须使用固定样本和引用规则。这样做看起来比一句“全绿”麻烦，却能避免把演示顺利误认为工程可靠。

最后，验收本身也是一种系统设计。验证入口、测试数据、成本边界和证据留存如果没有提前设计，项目越接近收尾，越容易靠记忆补结论。把这些内容变成可重复流程后，测试才不只是找错，也是在为后续修改保留安全感。
