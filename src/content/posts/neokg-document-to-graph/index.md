知识图谱页面最终呈现的是节点和边，但这些结构并不会天然存在于 PDF、Word 或普通文本中。一份项目文档可能同时包含标题、段落、表格、页眉、缩写和指代，系统必须先取得可处理的文字，再判断哪些内容是实体、实体之间存在什么关系，最后才能写入图数据库。

NeoKG 的后端解析与存储并不是我独立实现的部分。这篇文章来自项目完成后的源码阅读、接口联调和材料复盘，重点记录我对“文档如何进入知识图谱”的理解，不把团队后端能力归为个人成果。

## 先理解知识图谱的基本元素

知识图谱通常用三类元素描述知识：

- **实体**：现实世界或业务语境中可以被区分的对象，例如人物、组织、系统、技术和文档。
- **关系**：两个实体之间的联系，例如“使用”“属于”“依赖”和“开发”。
- **属性**：描述实体自身的信息，例如名称、时间、版本和来源。

最常见的表达方式是三元组：

```text
（NeoKG，使用，Neo4j）
（NeoKG，前端框架，Vue 3）
```

三元组适合表达关系，但不能忽略来源。系统如果只保存“某系统使用某技术”，却没有记录它来自哪份文档、哪个段落，就很难在出现冲突时核对。因此实际图谱还需要文档 ID、原文片段、抽取时间和置信信息等溯源字段。

## 文档解析的目标是取得可用文本

Apache Tika 能够识别多种文档格式，并抽取正文和元数据。它解决的是“怎样从文件容器中取得文本”，不是“怎样理解文本中的知识”。

解析阶段常见问题包括：

1. PDF 阅读顺序与视觉排版不一致。
2. 页眉、页脚和目录重复进入正文。
3. 表格被拆成失去列关系的文本。
4. 扫描型 PDF 没有可直接读取的字符层。
5. Word 文档中的标题层级、批注和正文混在一起。

因此解析成功不能只看有没有返回字符串。还要检查文字是否完整、顺序是否合理、编码是否正常，以及文件类型是否需要 OCR。文本质量会直接影响后面的实体识别：一句话被错误断开，关系就可能丢失；表格列错位，也可能把属性分配给错误实体。

## 实体识别与关系抽取是两件事

实体识别回答“文本中有哪些对象”，关系抽取回答“这些对象之间如何连接”。例如：

```text
NeoKG 使用 Spring Boot 构建后端服务，并通过 Neo4j 保存图数据。
```

实体候选可能包括 NeoKG、Spring Boot 和 Neo4j；关系则可能是“使用后端框架”和“保存图数据”。即使实体全部识别正确，关系方向仍可能出错。`NeoKG → 使用 → Neo4j` 和 `Neo4j → 使用 → NeoKG` 表达的是完全不同的事实。

模型可以帮助抽取候选结构，但输出仍需遵守约定：实体类型是否合法、关系是否位于允许集合、起点和终点是否存在、来源片段是否可追溯。模型输出适合进入校验流程，而不适合未经检查直接写入权威图谱。

## 实体消歧与合并决定图谱质量

同一个对象可能有多种写法，例如 `PostgreSQL`、`Postgres` 和 `PG`；不同对象也可能使用相同简称。如果每次出现都创建新节点，图谱会产生大量重复实体；如果只按名称强行合并，又可能把不同对象错误连接。

实体规范化通常需要组合：

- 大小写、空格和标点清洗；
- 别名与缩写表；
- 实体类型约束；
- 所在上下文和相邻关系；
- 人工确认或可撤销合并记录。

这里可以看到知识图谱与普通搜索索引的区别。搜索结果允许出现多条相似记录，而图谱中的错误合并会传播到路径搜索、社区发现和问答上下文，影响远不止一个节点。

## PostgreSQL、pgvector 与 Neo4j 为什么可以共存

不同存储处理的问题不同：

- **PostgreSQL** 适合保存用户、文档、任务、配置和结构稳定的业务记录。
- **pgvector** 为 PostgreSQL 增加向量字段和相似度检索能力，适合按语义寻找相关文本片段。
- **Neo4j** 以节点和关系为核心，适合路径、多跳关联和邻域查询。
- **Redis** 适合保存需要快速访问、生命周期较短的缓存或会话状态。

混合存储不代表同一份数据随意复制到多个数据库。更重要的是确定权威来源：文档处理状态由谁负责，原始文本放在哪里，节点关系从哪里读取，删除文档时如何同步清理关联数据。如果边界不清楚，多个数据库只会扩大一致性问题。

## 图数据库的基础查询思维

关系型数据库通常通过表和外键连接数据，图数据库则从节点出发沿关系遍历。Neo4j 使用 Cypher 描述图模式，例如查找某个系统使用的技术：

```cypher
MATCH (system:System)-[:USES]->(tech:Technology)
WHERE system.name = 'NeoKG'
RETURN tech
```

Cypher 的价值不只是语法直观，而是让关系成为一等结构。查询两个节点之间的路径时，不需要提前知道中间会经过哪几张表。但遍历范围越大，查询成本也可能越高，因此仍需要标签、索引、方向和深度限制。

## 一条更完整的入库链路

结合项目结构，我把文档入图流程理解为：

```text
上传与文件校验
  → Tika 提取正文和元数据
  → 文本清洗与分段
  → 实体、关系候选抽取
  → 类型、方向和来源校验
  → 实体规范化与去重
  → 元数据及向量保存
  → Neo4j 节点关系写入
  → 前端查询与可视化
```

每一步都需要失败状态。解析失败不应伪装成“没有实体”，模型返回格式错误也不应生成半套图谱。只有过程可观察、结果可追溯，用户才能判断图上的关系来自真实材料还是一次错误抽取。

## 后期复盘得到的认识

知识图谱构建首先是数据质量问题，然后才是图数据库和模型问题。抽取更多节点并不一定更好；实体重复、关系方向错误、来源缺失都会让图谱看起来丰富却无法信任。

对前端而言，理解这条链路也很重要。页面上一个节点没有名称、路径缺少方向或关系无法追溯，往往不是单纯的显示问题，而是上游契约没有定义完整。下一篇将从我直接参与的部分出发，讨论知识图谱前端怎样从“把图画出来”走向“让图可以查询和操作”。
