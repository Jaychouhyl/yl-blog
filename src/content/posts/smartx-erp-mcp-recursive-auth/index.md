`StackOverflowError` 很容易让排查方向落到递归数据结构、对象互相引用或 JSON 序列化。MCP 工具恰好需要把复杂 Java 对象转换为协议结果，因此最初怀疑 Jackson 并不奇怪。

但 SmartX MCP 的这次栈溢出并不是数据对象递归，而是调用链递归。

## 身份透传为何引入新的调用

MCP 不应该使用统一管理员账号调用所有 ERP 工具。用户的 API Key 先映射为真实员工，MCP 服务再向 Auth 服务申请该用户的内部令牌，最后携带令牌调用 Sales、SCM、Finance 或 RAG。

为了让每次 Feign 调用自动带上正确身份，MCP 服务使用了鉴权拦截器。正常链路应当是：

```text
MCP Tool
  → Feign 拦截器补充用户令牌
  → 业务服务
```

但用户令牌本身也需要通过 Feign 请求 Auth：

```text
McpAuthFeignInterceptor
  → McpUserTokenCache.issueTokenFor
  → Auth Feign Client
```

如果拦截器对 Auth 的内部代签发请求也生效，就会形成：

```text
拦截器
  → 获取令牌
    → Feign 请求 Auth
      → 再次进入拦截器
        → 再次获取令牌
          → ...
```

栈不断增长，最终抛出 `StackOverflowError`。

## 为什么错误看起来像序列化问题

工具调用的外层同时包含协议适配、结果序列化、异常捕获和审计。栈溢出最终会从工具执行或结果转换位置冒出来，因此如果只看最外层错误，很容易继续修改 JSON 结构。

判断是否为数据递归，可以做两个对照：

1. 在进入序列化前记录工具业务调用是否已经返回。
2. 检查堆栈中重复出现的是实体 getter/Jackson，还是拦截器、令牌缓存和 Auth Feign。

这次重复帧属于后者。继续给对象加 `JsonIgnore` 不会解决问题，只会掩盖真正的身份调用环。

## 最小修复是切断自举请求

最终修复是在 `McpAuthFeignInterceptor` 中排除内部令牌签发接口 `/auth/internal/issue-token-for`。这一请求的目的就是获得令牌，不能要求它事先已经带有同一个用户令牌。

修复后调用链变为：

```text
工具请求
  → Key 映射真实用户
  → 内部代签发请求（不进入用户令牌拦截）
  → 获得 JWT
  → 业务 Feign 请求进入拦截器并携带 JWT
  → 下游执行 RBAC 和数据范围
```

协议级验证中，`tools/list` 可以返回工具目录，库存和销售查询可以成功，日志不再出现栈溢出。

## 为什么不应该完全绕过内部认证

排除代签发接口并不等于让它成为公开裸接口。它仍然需要内部调用边界，例如 HMAC 签名、来源限制和时间窗口。修复只解决“不能用待获取的用户令牌保护获取令牌本身”，不是取消服务间认证。

这里存在两类身份：

- **服务身份**：证明请求来自受信任的 MCP 服务。
- **用户身份**：证明后续业务操作代表哪个员工。

代签发接口使用服务身份，业务接口同时使用服务链路和用户身份。把两者混成一个拦截器，才会出现自举递归。

## 这次故障留下的工程规则

1. 认证客户端不能无差别应用需要由它自己获取的凭据。
2. Feign 拦截器应有明确适用范围，而不是默认覆盖所有请求。
3. 排查栈溢出应先看重复栈帧，不要只根据业务场景猜序列化。
4. 用户身份与服务身份需要分别建模。
5. 修复后必须做协议级工具调用，而不是只验证服务能启动。

后续可以把内部 Auth Client 与普通业务 Client 进一步隔离，为递归路径增加测试，并对 SDK 升级后的拦截顺序保持监控。一个排除条件解决了当前故障，但清晰的身份模型才能防止同类问题重新出现。
