`StackOverflowError` 很容易让排查方向落到递归数据结构、对象互相引用或 JSON 序列化。MCP 工具恰好需要把复杂 Java 对象转换为协议结果，因此最初怀疑 Jackson 并不奇怪。

但 SmartX MCP 的这次栈溢出并不是数据对象递归，而是调用链递归。

## 身份透传为何引入新的调用

MCP 不应该使用统一管理员账号调用所有 ERP 工具。用户的 API Key 先映射为真实员工，MCP 服务再向 Auth 服务申请该用户的内部令牌，最后携带令牌调用 Sales、SCM、Finance 或 RAG。

为了让每次 Feign 调用自动带上正确身份，MCP 服务使用了鉴权拦截器。正常链路应当是：

```text
MCP Tool
  → Feign 拦截器补充用户令牌
  → 业务服务
```

但用户令牌本身也需要通过 Feign 请求 Auth：

```text
McpAuthFeignInterceptor
  → McpUserTokenCache.issueTokenFor
  → Auth Feign Client
```

如果拦截器对 Auth 的内部代签发请求也生效，就会形成：

```text
拦截器
  → 获取令牌
    → Feign 请求 Auth
      → 再次进入拦截器
        → 再次获取令牌
          → ...
```

栈不断增长，最终抛出 `StackOverflowError`。

递归本身不是错误，缺少终止条件才是。排查这类问题时，可以把每一层调用画成节点和边：谁调用谁，哪一条边重新回到旧节点，哪个条件本应阻止它。调用图一旦形成环，问题通常比继续盯着最外层异常清楚得多。

这也让我意识到，调用链和普通数据结构一样可以被分析。看到重复栈帧时，先找重复周期，再找终止条件，比从异常出口反向猜测整个系统更有效。

## 为什么错误看起来像序列化问题

工具调用的外层同时包含协议适配、结果序列化、异常捕获和审计。栈溢出最终会从工具执行或结果转换位置冒出来，因此如果只看最外层错误，很容易继续修改 JSON 结构。

判断是否为数据递归，可以做两个对照：

1. 在进入序列化前记录工具业务调用是否已经返回。
2. 检查堆栈中重复出现的是实体 getter/Jackson，还是拦截器、令牌缓存和 Auth Feign。

这次重复帧属于后者。继续给对象加 `JsonIgnore` 不会解决问题，只会掩盖真正的身份调用环。

## 最小修复是切断自举请求

最终修复是在 `McpAuthFeignInterceptor` 中排除内部令牌签发接口 `/auth/internal/issue-token-for`。这一请求的目的就是获得令牌，不能要求它事先已经带有同一个用户令牌。

这属于典型的认证自举问题：获得用户凭据的请求，不能反过来依赖尚未获得的同一凭据。最小修复是排除当前签发路径；更清晰的长期设计，则是把内部签发 Client 与普通业务 Client 分开配置，让适用范围由代码结构表达，而不是依赖一个以后可能越写越长的排除列表。

修复后调用链变为：

```text
工具请求
  → Key 映射真实用户
  → 内部代签发请求（不进入用户令牌拦截）
  → 获得 JWT
  → 业务 Feign 请求进入拦截器并携带 JWT
  → 下游执行 RBAC 和数据范围
```

2026-07-26 的归档台账记录了工具调用恢复、日志不再出现栈溢出，并记录过库存和销售数据的协议烟测。这是当时的验证结论；本次阅读源码没有重新启动服务重放该故障。

## 为什么不应该完全绕过内部认证

排除代签发接口并不等于让它成为公开裸接口。它仍然需要内部调用边界，例如 HMAC 签名、来源限制和时间窗口。修复只解决“不能用待获取的用户令牌保护获取令牌本身”，不是取消服务间认证。

这里存在两类身份：

- **服务身份**：证明请求来自受信任的 MCP 服务。
- **用户身份**：证明后续业务操作代表哪个员工。

代签发接口先验证服务身份，得到的员工令牌再用于后续业务请求。问题不在于两类身份不能同时存在，而在于签发请求错误地套用了“先取得员工令牌”的规则，把依赖绕回了自己。

内部签名具体保护哪些字段、时间窗口又不能防住什么，见[第 02 篇：MCP 的身份与权限边界](../smartx-erp-mcp-boundary/)。这里修的是调用环，不能把切断递归等同于全部认证风险都已解决。

## 已有测试保护了什么，还缺什么

当前 `McpAuthFeignInterceptorTest` 中有一项名字很直白的测试：`userContextTokenIssueFailureDoesNotFallbackToBot`。它构造一个已知员工，让令牌缓存返回空，同时准备一个拥有管理员角色的 bot，最后断言拦截器抛出异常、没有填入 Authorization。

这里 bot 的存在很重要。如果测试环境里根本没有可用 bot，即使代码错误地尝试回退，也可能碰巧没有写入令牌。主动提供一个“能被误用的备用身份”，才能检查拒绝回退的分支是否真的守住了边界。

但这项测试保护的是签发失败时的身份行为，不是栈溢出本身。针对这次递归，回归条件应继续拆开：

| 检查点 | 要证明的结果 | 当前阅读能确认的范围 |
|---|---|---|
| 员工令牌签发失败 | 不静默改用 bot | 上述测试源码有明确断言 |
| 内部签发请求进入拦截器 | 直接跳过，不再次调用令牌缓存 | 当前实现有前置返回；仍需针对该路径的回归验证 |
| 普通业务请求进入拦截器 | 继续取得员工身份并带到下游 | 不能因修递归而把全部拦截都关掉 |
| 完整协议查询 | 返回业务结果且权限正确 | 需要运行环境中的端到端验证，不能由单个 mock 测试代替 |

源码中的排除判断使用路径或 URL 的 `contains`，并不是按方法与标准化路径做严格相等匹配。它解释了当前怎样切断调用环，但也提醒我不要把这项修复描述成一套完整的客户端隔离机制。若继续完善，应该测试签发路径、普通路径及相近但不等同的路径，并考虑给签发 Client 单独配置拦截器范围。

本文未在本轮运行后端测试，也没有把“读到测试源码”改写成“测试刚刚通过”。已有测试、还需补的分支和历史协议记录分别说明，才知道下一次升级 Feign 或 MCP 依赖后究竟该复查什么。

## 从这次递归故障中学到什么

以后再遇到类似递归，我会先找“为了完成这个操作，又调用了什么”。鉴权拦截器为了补令牌去申请令牌，而申请令牌又经过同一拦截器，这比“JSON 有问题”更能解释重复调用从哪里来。给环找一条合理的出口，才是修复；增大栈空间只能让它多绕几圈。

`StackOverflowError` 虽然声音很大，真正犯错的可能只是一个过于勤快的拦截器：每次请求都想帮忙，最后连自己去拿令牌也没放过。
