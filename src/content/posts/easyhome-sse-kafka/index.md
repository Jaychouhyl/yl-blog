生成推荐回答可能经历需求理解、向量检索、候选排序和模型调用。如果页面一直等待完整结果，用户很难判断系统是在工作、已经失败，还是按钮根本没有生效。EasyHome 使用 SSE 逐步返回回答，后端代码中也使用 Kafka 处理部分异步任务。

这两个技术都与“异步”有关，却解决不同层面的问题。这篇按文末固定版本，整理从团队代码里学到的网络传输、消息队列、状态管理和最终结果验证知识；协议示意、源码观察与改进方案分开说明，不把它们当成本次原项目运行记录。

## 普通 HTTP 响应为什么会产生等待感

传统请求通常在服务端准备完全部结果后一次返回。对于快速查询，这种方式简单可靠；对模型生成而言，首个结果可能早已产生，却要等到完整文本结束后才能显示。

流式响应把结果拆成多个片段发送。用户可以先看到正在生成的内容，前端也能展示检索、生成和完成等阶段。但流式只是改变传输过程，服务端总耗时不一定减少。

代码需要区分两个指标：

- **首个结果时间**：从请求开始到用户第一次看到有效反馈。
- **完整结果时间**：从请求开始到任务最终完成。

SSE 主要改善前者。模型仍然需要完成完整推理，检索和排序也仍然存在。

## SSE 的基本工作方式

SSE，即 Server-Sent Events，使用一个持续的 HTTP 连接，由服务端不断向浏览器发送文本事件。下面是用来解释事件边界的协议示意，并非 EasyHome 已捕获的响应报文：

```text
event: message
data: {"content":"推荐内容片段"}

event: done
data: {"status":"completed"}
```

浏览器原生 `EventSource` 更适合 GET 和自动重连；如果请求需要提交复杂 JSON、鉴权头或对话历史，也可以使用 `fetch` 读取响应流，但解析和重连需要自己处理。

无论采用哪种方式，都应定义清楚事件类型，而不是把所有内容都当成一段字符串。开始、内容、房源卡片、完成和错误拥有不同语义。

## 项目发送的是聚合回答，不是只追加一个新字

所读前端没有使用原生 `EventSource`，而是通过 `fetch` 向 `/api/chat/stream` 发送 POST 请求，携带会话 ID、消息正文和 `Accept: text/event-stream`。后端返回的对象包含四个字段：

| 字段 | 所读代码中的用途 |
|---|---|
| content | 当前输出片段 |
| role | 消息角色 |
| finished | 这次回答是否完成 |
| aggregationMessage | 到目前为止的聚合回答 |

前端用 `aggregationMessage` **覆盖**当前回答，再从中解析房源编号，并不是把每次完整聚合文本追加到末尾。假设连续收到“推荐”“推荐 A”“推荐 A 房源”，每次覆盖会得到“推荐 A 房源”；每次追加则会变成“推荐推荐 A推荐 A 房源”。这是一道数据契约题，不是打字动画题。

项目的完成标志也是对象里的 `finished`，不是上面示意中的独立 `event: done`。实现一个客户端时，先分清“增量片段”与“累计快照”，比先把光标做得会闪更重要。

## SSE 与 WebSocket 的区别

SSE 是服务端到客户端的单向推送，建立在 HTTP 上，适合通知、日志和模型输出。WebSocket 提供双向长连接，更适合聊天、协作编辑和高频实时交互。

模型回答通常是客户端先发送一个问题，随后服务端持续返回结果，因此 SSE 已能满足主要方向。使用 WebSocket 不会自动让生成更快，反而会增加连接管理、心跳和协议设计。

技术选择应该服从通信模式：只有确实需要双方持续高频发送消息时，双向连接才值得增加复杂度。

## 前端如何管理一次流式回答

流式消息不是收到一段就直接追加到页面。前端至少需要保存：

- 当前请求 ID；
- 连接或读取状态；
- 已接收文本；
- 结构化房源结果；
- 完成或错误状态；
- 用户是否主动取消。

如果用户连续发送两个问题，旧请求的片段不能继续写进新回答。页面离开时也应取消读取，避免组件销毁后仍更新状态。

流式文本可能在任意字符位置分块，不能假设每个网络片段都是完整 JSON 或完整汉字。解析器需要缓存未完成内容，并按协议边界组合事件。

## 字符解码完成，不等于一条事件已经收齐

所读前端调用带流式选项的 `TextDecoder`，它有助于处理 UTF-8 字节跨块的问题；但随后把**本次读取的块**按换行拆开并直接解析 JSON，没有保留跨块的残余文本行。这是两个不同层次的问题：字节到字符的缓存，不会替你缓存半个 JSON。

例如一条教学消息被网络拆在 `aggregationMessage` 字段名中间，两次读取都可能得到完整的字符，却各自不是完整 JSON。按源码中的逐块拆行方式分别解析会失败；把余下文本保留到下一次读取后，才有机会得到完整事件。这是离线分块反例，不代表抓到了线上丢消息。

标准 SSE 还使用空行结束一条事件，多条 `data:` 行可以属于同一事件；不能把“每读到一行就 JSON.parse”当成通用 SSE 解析器。规则见 [HTML 标准的事件流解释](https://html.spec.whatwg.org/multipage/server-sent-events.html#interpreting-an-event-stream)。后续完善时，应区分字节流、文本行、完整事件和业务 JSON 四层，再决定复用成熟解析器还是实现当前协议需要的最小处理。

## 完成事件比连接关闭更可靠

连接关闭可能代表正常结束，也可能代表网络中断。服务端应发送明确完成标识，前端只有收到标识后才把回答状态设为成功。项目已有 `finished` 字段，但前端在读取器返回结束时也会直接重置加载状态，没有单独保留“正常完成”和“未完成就断开”的业务结果；因此现在还不能把加载动画消失等同于回答完整到达。

错误事件也需要包含可处理信息：是否可以重试、检索是否已经完成、是否产生了部分回答。直接把后端异常堆栈显示给用户没有帮助，完全隐藏错误又无法判断问题。

当前的 fetch 客户端没有实现原生 EventSource 式的自动重连；如果后续加入重试，还需要区分会话 ID 与请求 ID：同一会话可以提多个问题，重试的却应该是某一次确定的请求，而不是重放整段历史。

前端已有取消请求和组件卸载时清理的处理，但“新建会话”只是清空消息并更换会话 ID，没有在该函数内取消旧读取。旧异步任务还持有自己的执行进度，新的界面变量不会自动让它失效。后续可以通过取消旧请求、校验本轮请求身份来隔离结果；这属于源码揭示的边界，不是已经复现了在线串话。

## Kafka 解决的是服务之间的时间解耦

Kafka 是分布式事件流平台。生产者把消息写入 topic，消费者按分区读取并处理。它适合某个业务动作已经发生，但后续工作不需要阻塞当前请求的场景。

EasyHome 代码中的实际例子是两条业务事件：房源发布信息进入 `house-publish-topic`，消费者将发布记录标记为已接收；预约信息进入 `appointment-topic`，消费者再交给预约服务处理。向量更新仍在房源新增或修改流程中同步执行，不能把它误写成已经由 Kafka 驱动。

Kafka 与 SSE 的职责不同：

- SSE 关注服务端结果怎样逐步到达当前浏览器。
- Kafka 关注服务之间怎样异步传递事件和解耦处理时间。

一个面向用户，一个位于后台；它们可以同时存在，也可以彼此独立。

## 消息队列默认要面对重复

消息系统通常更容易保证“至少一次”投递，而不是每条业务事件严格只处理一次。消费者处理完成前崩溃，消息可能再次到达。

因此消费者需要幂等设计，例如为一次明确的业务事件分配稳定标识；房源 ID、事件类型和版本也可以在语义明确时组合使用。但不能简单按“用户＋房源”把所有预约去重，因为用户可能合法地再次预约另一个时间。重复处理和新的业务请求，首先要在业务上区分清楚。

还要处理：

- 消息格式版本变化；
- 消费失败和重试次数；
- 无法处理的死信；
- 事件顺序；
- 积压监控；
- 房源已经发生更新时，旧事件是否仍应执行。

接入 Kafka 只是获得传输机制，不代表异步链路已经可靠。当前生产者调用 `send` 后就记录发送日志，消费者捕获异常后也没有在这段代码中展示幂等键、死信或最终补偿；因此仓库能够证明“事件已经接入”，却不足以证明完整的可靠消息闭环已经验收。这些缺口正好成为我学习消息可靠性时最具体的反例。

## 异步发送的异常，不一定被外层 try-catch 接住

生产者在调用 `KafkaTemplate.send` 后立刻写发送日志，没有处理返回的 Future。同步抛出的异常可以进入当前 catch，但稍后才完成的发送失败，需要观察异步结果；不能根据日志中的“成功”就判断 broker 已经确认。相关机制见 [Spring Kafka 发送结果说明](https://docs.spring.io/spring-kafka/reference/kafka/sending-messages.html)。

消费端也有相似的边界：捕获处理异常后只写日志并正常返回，容器就不能根据这次没有抛出的异常进入对应错误处理流程。至于是否重投、何时提交 offset，还取决于实际容器与事务配置；本次没有启动 Kafka，不据此推断所有消息都一定丢失或一定重试。参见 [Spring Kafka 异常处理说明](https://docs.spring.io/spring-kafka/reference/kafka/annotation-error-handling.html)。

以预约为例，控制器发送消息后返回，消费者稍后调用服务插入 `PENDING` 预约记录。可以把验证拆成四层：

| 层次 | 应检查的结果 | 仍不能证明什么 |
|---|---|---|
| 请求已受理 | 接口返回，参数进入发送流程 | broker 已确认 |
| 消息已确认 | 发送 Future 成功 | 消费业务已完成 |
| 消费已执行 | 对应事件进入服务处理 | 最终记录必然可用 |
| 业务已落地 | 预约记录可查询，状态正确，重复事件不会多建记录 | 尚未发生的人工审核已经通过 |

异步处理最容易丢失的不是某个技术名词，而是“这一层到底承诺了什么”。把四张回执混成一张“成功”，排查时就只能互相询问到底是谁成功了。

## 中间件成功不等于业务成功

Kafka 生产者得到发送确认，说明达到了相应配置下的消息确认条件，不等于消费者业务完成；SSE 收到回答完成标志，也不等于回答里的业务事实已经核对。最终仍要到权威业务表面验证结果。

例如当前房源修改会同步调用向量更新，真正的完成标准仍是新描述能够参与正确检索，而不是某处日志写了“更新成功”。如果未来把向量更新改为消息驱动，再额外检查异步事件与索引结果的对应关系，不能把这个未来方案倒写成当前 Kafka 消费任务。推荐回答流式展示结束后，也要确认其中的房源仍然存在、状态可用且详情能够打开。

这让我形成了一个通用判断：技术链路中的成功状态必须对应到最终业务对象。中间服务的绿色状态只是证据的一部分。

## 从异步链路中学到的事情

SSE 让等待过程可见，Kafka 让服务不必在同一个请求里完成所有工作。两者提升体验和解耦能力，但也引入请求身份、重复处理、状态恢复和最终一致性问题。

EasyHome 让我理解，“实时”和“异步”都不是单一技术名词。实时要说明用户什么时候看到第一条有效反馈，异步要说明任务最终由谁确认完成。只有协议、状态和业务验证共同闭环，中间件才真正解决问题。
