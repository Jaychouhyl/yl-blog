# SmartX ERP 05—08 学习型文章增强设计

## 目标

在不改变四篇文章事实范围和现有主题的前提下，将叙述主线统一为“从代码和项目中学到了哪些编程及系统设计知识”。正文保持专业，加入少量克制的工程趣味，但不扩写成教材，也不虚构源码、性能数据或项目成果。

## 范围

- 第 05 篇：RAG 实体路由与业务页面跳转。
- 第 06 篇：Seata、Outbox、RocketMQ 与一致性策略。
- 第 07 篇：身份透传造成的递归调用与 `StackOverflowError`。
- 第 08 篇：Aeria 组件体系与后台设计系统。
- 同步当前状态文档和追加进度记录。

不修改文章日期、项目时间范围、页面组件、样式、路由或其他项目文章。

## 内容设计

### 05：RAG 实体路由

保留“回答回到业务页面”的现有结构，补充结构化输出、实体识别、可信路由、状态机和流式交互知识。明确模型负责理解意图，业务系统负责验证实体、权限与目标页面，避免直接执行模型生成的链接。

### 06：分布式一致性

围绕业务风险解释本地事务、Seata、Outbox、RocketMQ、幂等、死信和对账的职责。重点说明强一致与最终一致的取舍，以及任何中间件都不能代替最终业务状态验证。

### 07：身份递归故障

通过调用图、递归终止条件、认证上下文和自举请求解释故障。保留最小修复思路，同时说明为什么“完全绕过认证”虽然省事，却会破坏系统边界。

### 08：Aeria 组件体系

补充组件抽象、设计令牌、接口契约、响应式布局、暗色模式和开放代码策略。用真实复用证据判断是否值得抽象，避免为了组件化而组件化。

## 统一写作约束

- 每篇增加清晰的学习总结，突出代码理解和系统设计认识。
- 贡献说明只保留必要的事实边界，不作为文章主线。
- 基础知识与项目场景相连，不单独堆概念。
- 幽默只用于帮助理解，不削弱专业表达。
- 不出现生成来源、工具署名或额外贡献者信息。
- 延续现有 Markdown、frontmatter、系列编号和站点字体风格。

## 验证

1. 检查四篇 frontmatter、系列顺序、标题层级和站内链接。
2. 执行 `npm run check`、`npm test` 和 `npm run build`。
3. 启动本地预览并运行站内链接扫描。
4. 浏览器抽查至少两篇，确认标题横幅、正文、目录与左侧栏正常。
5. 更新 `docs/yilin-blog-current-status.md`，并在 `progress.md` 末尾记录验证结果和回滚方式。

## 完成标准

- 四篇文章均形成明确的学习主线，并保持事实边界。
- 技术内容比原稿更完整，但没有不必要的大幅扩写。
- 自动检查、测试、构建和链接扫描通过。
- 页面抽查没有新增视觉或导航问题。
